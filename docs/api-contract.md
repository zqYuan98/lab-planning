# API contract

Shared types in shared/types.ts are authoritative. JSON responses return the object/array directly, errors return {error:string}. Authentication uses HttpOnly same-origin cookie. All mutations (except login/setup/register) require authenticated identity and application/json. Entity update requires version; mismatches return 409. Use strings for IDs, ISO timestamps, YYYY-MM months and YYYY-MM-DD dates. No automatic company data import.

- GET /api/auth/status -> {initialized:boolean}; POST /api/auth/setup {name,email,password} -> User first manager; POST /api/auth/login {email,password}->User; POST /api/auth/logout; GET /api/auth/me -> User.
- GET /api/bootstrap -> Bootstrap; members receive participating monthly goals and only their own tasks/weekly records. Deleted weekly rows are omitted for all roles; active pending-review rows remain editable. Former participants receive authorized historical goal snapshots; reference/historical projections are not current task candidates. Shared merged goals redact other members’ source prose, including carry chains. Manager sees all authorized current work. users returns safe User objects, never password hashes.
- POST /api/users {name,email,password,position,role}; PATCH /api/users/:id {version,name?,position?,active?,role?,password?} manager only. Cannot remove/demote last active manager.
- GET /api/users/:id/deletion-preview -> {user:User,canDelete:boolean,blockers:{key:string,label:string,count:number}[],retainedHistory:true}; active manager only. Lists business, historical, import and frozen-snapshot references, self/last-manager protection. Safe user only, never credentials.
- DELETE /api/users/:id {version,confirmName} -> {deleted:true,id}; active manager only. Requires current exact name and version, transactionally rechecks all preview conditions, removes the unreferenced account and its sessions/integration tokens. Business and frozen history are never cascaded. Account lifecycle audits remain with safe identity snapshots and stay excluded from business migration packets. Any business/history association returns 409; use deactivation instead.
- POST /api/projects {name,code,description,ownerId}; PATCH /api/projects/:id {version,...}. Manager only; archive instead of delete.
- POST /api/annual-goals {title,year,target,progress,description,ownerId}; PATCH /api/annual-goals/:id {version,...}. Manager only. Independent of monthly.
- POST /api/plans {month,title,projectId?,category,ownerId?,collaboratorIds?,expectedOutcome,acceptanceCriteria,dueDate,priority?,sourcePlanId?,isTemporary?,temporaryReason?} -> MonthlyPlan; creates draft. Ordinary goals require manager. Members may create their own temporary goal with isTemporary:true and a nonempty temporaryReason. Due date stays within month; cross-month carry is manager-only.
- PATCH /api/plans/:id {version,...editable fields} -> MonthlyPlan. Manager, or owner of a temporary draft/returned goal. Members cannot change goal type/ownership or edit submitted goals. Manager may edit submitted/approved; published changes require nonempty reason and create new publication snapshot. Preserve audit before/after; do not overwrite original submissions. Published owner/collaborator changes cannot orphan assigned tasks.
- POST /api/plans/:id/submit {version}; POST /api/plans/:id/review {version,decision:'approve'|'return',comment}; POST /api/months/:month/publish {planIds:string[],reason?}. Submit allows manager or temporary goal owner. Review and publication require manager. Manager publishes approved items, revision snapshot contains all published month plans. Publication does not accept results.
- POST /api/plans/merge {planIds:string[],title:string,reason:string}. Manager combines at least two submitted/approved proposals in same month and same project (or same department category), before tasks exist. New approved plan preserves owner-specific source outcomes/criteria and all owners as participants; mergedFromIds links originals, sources become merged with mergedIntoId. No source deletion; merged sources cannot be independently published or edited. Manager can edit merged target then publish.
- POST /api/plans/:id/result {version,actualOutcome,acceptanceStatus:'submitted'|'accepted'|'not_completed',acceptanceNote?}. Owner submits actual results, manager confirms accepted/not_completed; accepted requires outcome.
- GET /api/plans/:id/history -> AuditEvent[]. Authorized member/manager.
- POST /api/plans/:id/carry {month,dueDate,reason} -> MonthlyPlan draft linked to source. Manager only; old month unchanged.
- DELETE /api/imports/:id {version} -> {ok:true,deletedHistoryCount:number}; batch owner or manager. Removes batch and its archived historical records; shared source files remain until unused. Formal plans/tasks/weekly records and reports are preserved. Active analysis or stale version returns 409.
- DELETE /api/imports/history/:id {version} -> {ok:true}; manager, importer or record owner. Removes only the archived record and preserves deduplication metadata.
- POST /api/tasks {title,monthlyPlanId?,ownerId?,description,dueDate,isTemporary?,temporaryReason?} -> Task. Bound plan must be own/collaborating; nonmanager owner is always the authenticated actor. Temporary needs reason; formal task requires monthly plan. Weekly draft allowed before plan publication, submission gate below.
- PATCH /api/tasks/:id {version,title?,description?,dueDate?,status?}. Owner/manager.
- POST /api/tasks/:id/relink {version,monthlyPlanId,reason} -> Task. Manager only, target published; preserves task identity and prior weekly monthlyPlanId snapshots.
- POST /api/tasks/:id/cancel {version,reason} -> Task with `cancellation:{cancelledAt,cancelledBy,reason}`. Manager only, current version and nonblank reason required. Any undeleted weekly record (including drafts and other weeks) prevents cancellation with 409. Preserves task status, progress, deleted weekly records, frozen submissions/reports and audit; closes pending task followups, deadline requests, tracking and blockers. Cancelled tasks leave ordinary bootstrap, task totals, work registers, search and actionable notifications; full exports retain them. Further edits, relinking, scheduling and imported rescheduling are rejected. Repeated cancellation returns 409; there is no automatic cancellation after weekly deletion and no restore endpoint.
- POST /api/weekly-records {taskId,weekStart,commitment,actualOutcome?,evidenceUrl?,blocker?,nextAction?,status?,submitted?} -> WeeklyRecord. Unique (taskId,weekStart) among non-deleted rows; owner=task owner; normalize Monday. submitted=true requires published monthly link or explicit temporary task, and does not bypass applicable plan review. done requires actualOutcome; blocked/not_done require blocker. Evidence URL http/https only. Approval and deletion metadata are server-managed.
- PATCH /api/weekly-records/:id {version,...content/status/submitted fields,completeTask?:boolean,taskVersion?:number}; cannot change task/week/owner. Ordinary weekly completion does not change the overall Task or accept the month. Explicit `completeTask:true` requires final weekly status `done`, a nonempty actualOutcome and the current linked taskVersion; it copies actualOutcome into the task completionNote and completes the task in the same transaction, including existing collaboration lifecycle hooks. Already completed tasks retain their original explanation. Stale task/weekly versions return 409 without partial writes.
- POST /api/weekly-records/:id/carry {weekStart,commitment?} -> WeeklyRecord. Same task, next week new planned/draft record; no inherited outcome/status. Record original monthly link, unless task was relinked.
- DELETE /api/weekly-records/:id {version,reason} -> WeeklyRecord with `deletion:{deletedAt,deletedBy,reason}`. Manager only; reason required. Transactionally checks version and writes the tombstone plus before/after audit. Repeated deletion or stale version returns 409; deleted rows cannot be edited or carried. Retains the Task and its completion state, monthly goal, other weeks, progress, submission receipts and frozen reports. Closes this row's pending followups/blocker support and invalidates its pending acknowledgement obligations without clearing historical responses or unrelated task followups. The same Task/week may receive a new record with a new ID; no undelete endpoint. For a corrected monthly association, relink the retained Task first, then create the replacement row under the existing publication/participation/month-overlap gates.
- GET /api/reports; POST /api/reports {type,period} -> Report. Manager only. Weekly period is Monday date; monthly period YYYY-MM. Full immutable source snapshot, metrics independent of narrative/TOP picks; repeated generation creates revision.
- PATCH /api/reports/:id {version,narrative,title?}; POST /api/reports/:id/finalize {version}; POST /api/reports/:id/polish {version}; GET /api/reports/:id/export?format=docx|md. Manager only. Polish only when configured, never fabricate facts, no stats mutation; finalized immutable.
- GET /api/report-schedule; PUT /api/report-schedule {version,enabled,weeklyDay,weeklyTime,monthlyDay,monthlyTime}. weeklyDay 1..7; monthlyDay 0=last day else 1..28. Default disabled. Asia/Shanghai; durable per-period idempotency for scheduled draft generation, no external notifications.

## Imported temporary work

- Import rows keep `kind:'monthly'|'weekly'`. Optional `isTemporary:boolean` and `temporaryReason:string` describe temporary work independently of the destination period; there is no separate `temporary` kind. A missing flag is compatible with legacy rows and does not classify unlinked imported work as temporary. Non-boolean flags are rejected.
- `POST /api/imports/structured`, `PATCH /api/imports/:id` and historical corrections accept these fields. `GET /api/v1/schema` advertises them. `history` may retain an incomplete reason as source material; writing temporary work into `draft` or `existing` requires a nonempty reason. Temporary weekly work cannot also link a monthly goal (`monthlyPlanId` or `linkedRowId`).
- Members may import their own temporary monthly goals as drafts, with normal draft requirements and monthly review/publication afterward. Ordinary monthly drafts remain manager-only. `existing` still requires manager confirmation; members may request confirmation, including for temporary work.
- Business JSON export/restore preserves these optional fields in archived rows and their audit snapshots, along with temporary goal/task fields. Legacy packages without them remain valid. CSV/XLSX retain them in the archived `row` JSON cell and audit snapshot cells; temporary goal/task fields have their own columns. No business packet or database schema version change is needed for these optional JSON properties.

## Backend integration

### Collaboration and native channels (2026-09-20)

Types and input contracts are in `shared/collaboration.ts`, `shared/collaboration-notifications.ts`, and `shared/native-actions.ts`. All routes below are under `/api`, require an active authenticated session and retain same-origin JSON write guards. Business commands use `requestId` plus current versions: exact retries reuse the result; conflicting payloads or stale previews return 409. Manager routes enforce the role in the router or service.

- GET `/collaboration`, `/collaboration/tasks/:id`, `/work-risks`: permission-scoped work, tracking, followups, risks and personal digests. GET `/collaboration/resolve/:type/:id` resolves a task/followup/deadline request only after current task access succeeds.
- GET/PUT `/collaboration/settings` (manager): feature flags, pilot users, explicit manager routing, workday overrides and thresholds. Initial reads do not write defaults. GET `/collaboration/rules-preview?at=<ISO>` (manager) is read-only and does not consume reminder quotas.
- PUT `/collaboration/preferences` `{requestId,version,memberActionsEnabled}` changes only the current user's optional action summary. It does not remove required followup obligations.
- POST `/tasks/:id/progress` appends progress and validated task/weekly changes. Ordinary saving does not respond to a followup or formally submit a week. Proxy progress requires a reason and does not reset the owner's meaningful-progress clock.
- POST `/tasks/:id/followups`, PUT `/followups/:id`, POST `/followups/:id/close` (manager): one open request per task; changes/closure retain reasons. POST `/followups/:id/respond` is an explicit owner response with request/task/optional weekly versions and progress payload.
- POST `/followups/preview`, `/followups/batch` (manager): 1–100 unique tasks, frozen requirement/deadline, recipient grouping and shared daily quotas; commit requires the actor/settings/task/tracking/request-bound preview token and explicit enrollment when needed.
- PUT `/tasks/:id/tracking` (manager): explicit enrollment, pause/review/resume or close with task/tracking versions. Resuming starts a new observation baseline without rewriting deadlines or past progress.
- POST `/tasks/:id/deadline-requests` (owner), POST `/deadline-requests/:id/decide` (manager): retain original deadline until approval; compare request and deadline versions. POST `/blockers/:id/handle` (manager) records support, deferral or verified closure without completing work.
- GET `/digests/:id`: recipient-only digest, filtered against current ownership/access. Rendered lines distinguish historical facts from current obligation status; no stored item is rewritten by reading. Notification previews use the same projection; actual sends also omit resolved actionable items.
- Weekly duty views include an optional progress-event manifest. Formal submission validates the reviewed IDs; new relevant progress after the preview returns 409. Existing receipts and first punctual/late facts are retained.
- GET `/notification-diagnostics` (manager): cursor-based full-history delivery filtering/counts and redacted runtime/backup diagnostics.
- GET/PUT `/native/settings`, POST `/native/identities/:userId/verify`, GET `/native/operations`: permission-scoped status and manager configuration. Capability enablement requires configured server parameters and recorded real tenant verification; defaults remain disabled.
- POST `/native/links/:id/reconcile`, `/recreate`, `/delete` (manager) queues controlled native work; explicit recreation is restricted to verified external-missing objects. POST `/native/intents` and `/native/intents/:id/confirm` preview then confirm one bound action using a short-lived single-use token.

Official Stream callbacks use the configured SDK connection and durable inbox rather than an unauthenticated public business mutation endpoint. External network work occurs outside Store transactions. Unknown native acceptance blocks same-obligation retries and channel fallbacks. See [operations](dingtalk-collaboration-operations.md) and [native protocol/tenant requirements](validation-2026-09-20-dingtalk-native.md).

server/store.ts exports Store: constructor(path:string), get<T>(collection,id):T|undefined, list<T>(collection):T[], insert<T extends Entity>(collection,input:Omit<T,keyof Entity>&Partial<Entity>):T, update<T extends Entity>(collection,id,expectedVersion:number,patch:Partial<T>):T, transaction<T>(fn:()=>T):T, close(). New entity ID/time/version are assigned by store; revision starts 1. Store throws with status 404/409. Store collections: users (internal passwordHash extra, sanitize outputs), sessions, projects, annualGoals, plans, tasks, weeklyRecords, events, publications, reports, settings, scheduleRuns. No network I/O inside transaction.

server/auth.ts exports requireAuth(store):RequestHandler attaching req.user:User; requireManager middleware; safeUser strips secrets. server/domain.ts exports Domain(store) containing business logic used by router and tests. server/app.ts exports createApp({store?,dbPath?,enableScheduler?}={}): Express. Root agent implements server/reports.ts and server/report-routes.ts exporting createReportRouter(store):Router, mounted behind requireAuth at /api; server/scheduler.ts exports startScheduler(store):()=>void. API/domain agent integrates those imports only after files exist. Route bootstrap may import report methods only if needed; store.list('reports') manager only.

Frontend src/api.ts exports api<T>(path,options?) using /api prefix, credentials same-origin and error handling. App consumes bootstrap, displays create/review/publish weekly operations and reports, refreshes bootstrap after successful mutation. Root owns src/pages/Reports.tsx and server report modules; frontend agent owns remaining src and styling. Reports page exported default with props {data:Bootstrap,refresh:()=>Promise<void>,notify:(message:string)=>void}; use api and src/ui.tsx shared helpers if available.

## Team registration (2026-09-09)

- POST /api/auth/register {name,email,position?,password} -> 202 {message}. Requires an initialized active manager; creates inactive pending member, never a session. Email is case-insensitive and unique. Separate IP budget:20 attempts per15 minutes, including unsuccessful requests;429 returns Retry-After.
- POST /api/users/:id/registration-review {version,decision:'approve'|'reject',comment?} -> User. Manager only; reject requires comment. Only pending/rejected can be reviewed. Approval fixes role=member and active=true. Both transitions invalidate old credentials versions and audit atomically.
- User.registrationStatus is optional for compatibility with existing accounts. Access requires active=true plus absent/approved registrationStatus. Pending/rejected accounts are excluded from ordinary member directories and report snapshots. Manager bootstrap includes review comments. Normal account PATCH cannot activate or promote unapproved applications.
- All password creation/reset rules accept8–256 characters, without mandatory character classes. Registration form additionally checks confirmation equality.

## Friday whole-sheet submissions (2026-09-11)

Types in `shared/weekly-submissions.ts` define the response. W is the Monday of the cutoff cycle: `results` covers W, `plan` covers W+7. Deadline is Friday 16:00 Asia/Shanghai; only server submission time strictly before the cutoff is on time. This receipt is independent of `WeeklyRecord.submitted` and task completion.

- GET /api/weekly-submissions?week=YYYY-MM-DD -> WeeklySubmissionView. Returns rule, server clock, cutoff, cycle and duty views. Members receive only their own duties, records, receipts and roster entry; managers receive the frozen roster. Each duty includes its version and complete sorted record ID/version manifest.
- POST /api/weekly-submissions/submit {dutyId,version,requestId,manifest,progressEventIds?,draftAction?:'include'|'retain',note?,reason?} -> immutable WeeklySubmission. Owner or manager; manager proxy requires reason. Every source row, including retained drafts, must match the preview manifest or the transaction returns 409. Where related progress exists, progressEventIds must also match the preview. Results require actual progress; plans require commitments; an empty sheet needs a note. Stable requestId retries return the existing receipt. Revisions preserve first valid submission and cutoff-missing facts. Plan submission enters applicable review; it does not approve its rows.
- PUT /api/weekly-submissions/rule {version,enabled} -> WeeklyRule. Manager only. Default starts next full week; pause/resume affects next week, preserving historical active windows.
- POST /api/weekly-submissions/adjust {dutyId,version,action:'exempt'|'revoke_exemption'|'invalidate'|'restore',submissionId?,reason} -> WeeklyAdjustment. Manager only. Submission ID required for invalidate/restore. All changes append an audit fact rather than delete history.
- POST /api/weekly-submissions/roster {week,version,rosterIds,reason} -> WeeklyCycle. Manager confirms only a cycle marked needsReview. Normal rosters freeze eligible members as of Monday; later joins enter next cycle. Frozen roster changes use individual exemptions.

Reconciliation runs on startup, scheduler ticks and relevant API access. It catches up every enabled cutoff cycle idempotently. Unknown historical rosters wait for confirmation. Exemption affects current compliance counts, while missing-at-deadline evidence stays available. Reconciliation itself does not send external messages; the opt-in DingTalk worker below handles new, currently valid reminder events.

New report snapshots may contain optional `weeklySubmissions` summaries, frozen independently of delivery metrics. Legacy reports without this field remain valid. Business migration v2 includes weekly rules, cycles, duties, receipts, missing facts and adjustments with strict reference checks; v1 packages add no invented weekly facts. Member exports contain only personal facts, without departmental rules/rosters, and require matching destination cycles for restore. Safe goal projections cannot be restored as complete goals; use the administrator’s complete package.

Migration requires canonical ISO UTC milliseconds for new weekly timestamps (including nested report/audit facts), preventing timezone-string comparisons from changing compliance. Restore preview exposes `notices` and per-collection `replace` counts when accepting a source rule over an untouched, unused server default; configured or used rules remain conflicts. Replacement preserves source metadata, is audited, and is revalidated transactionally.

## Weekly plan review and deletion (2026-09-20)

- POST `/api/weekly-submissions/review` `{dutyId,version,submissionId,decision:'approved'|'returned',reason?,requestId}` -> immutable `WeeklyPlanReview`. Manager only; return requires nonblank reason. `version` is the duty version shown in the preview. The transaction requires the latest valid, non-exempt plan receipt and rechecks the complete planning manifest; changed/deleted/added rows, stale versions or an already reviewed receipt return 409. One decision per submission. An identical reviewer/requestId retry returns its existing result; reuse for different content returns 409.
- Duty views add `planReviewRequired`, `planReviewStatus:'not_required'|'unsubmitted'|'pending'|'approved'|'returned'|'changed'`, `latestPlanReview` and `planReviews`. Existing compliance `status`, first submission time, deadline and missing facts remain separate. A returned plan is revised by a new whole-sheet submission; the original receipt and decision remain readable.
- New plan receipts add `planManifest?:{id,fingerprint,submitted}[]`, including retained drafts, `planTaskSnapshots?:{id,title,dueDate,description}[]` and `planGoalSnapshots?:{id,month,title}[]`. Context is frozen at submission. The command's complete ID/version `manifest` protects submission concurrency; the plan manifest protects review against business-content changes while permitting later execution progress.
- `WeeklyRecord.planApproval?:{required:true,approvedSubmissionId:string|null,approvedFingerprint:string|null,suspended?:true}` records the row's effective approval. The fingerprint is `JSON.stringify([taskId,ownerId,weekStart,monthlyPlanId,commitment])`; execution status, progress, evidence, storage version and approval metadata are excluded. A changed row stops contributing to effective weekly counts until approved again; unchanged rows keep their own prior approval. A required row is effective only while active and submitted, with a matching approved fingerprint or a rule-derived suspension. Missing metadata remains compatible with history; normal writes and restore normalization prevent applicable new member work from bypassing review.
- A manager's explicit formal assignment is confirmed; an assigned draft and a proxy recording are not approvals. A member's change to an assigned commitment requires review in applicable cycles. Ordinary client writes cannot set approval/deletion metadata. Monthly publication, ownership/participation, temporary-work and month-overlap validation continue independently.

`WeeklyRule.planReviewEffectiveWeek` is the persisted first **submission cycle**, not the content week: cycle W reviews content W+7. First initialization chooses the next full cycle; restarts retain it and do not create historical approval facts. Review applies only when W also belongs to a rule window. Pausing/resuming the submission rule changes windows from the next full cycle and synchronizes affected future rows. Closed cycles retain `suspended:true` and their old approval fields; only newly reopened cycles resume the requirement. Already elapsed paused cycles stay exempt after later resumption. Original duties, reviews and cutoff facts are retained. Explicitly invalidating an approved receipt clears current row approvals referencing it; restoring that receipt can reinstate its approval only for unchanged, active, submitted rows without another current approval. Frozen history is unchanged in both cases.

Business packets keep the existing v2/v3 format selection, adding optional review metadata and a default-empty `weeklyPlanReviews` collection; older v1/v2/v3 inputs remain accepted. Reviews contain duty/owner/cycle/submission IDs, decision, reviewer, review time, reason and requestId. Strict schemas cover nested snapshots; task/goal contexts and approval references travel with their dependencies. Administrator exports include tombstones even though bootstrap omits them. Restore checks Task/week uniqueness only among non-deleted rows and remaps owner IDs inside historical fingerprint tuples as well as reviewer/deleter IDs.

Restore rejects broken approved snapshots or reviews, duplicate decisions and a live approval pointing to an invalidated receipt; frozen reports/audits may retain the original historical approval. A live `suspended:true` must correspond to a post-activation cycle outside the current rule windows; historical snapshots are not reinterpreted against today's window. Applicable active member rows in an old packet without approval metadata normalize to pending during the shared preview/restore pass, except already issued manager assignments. Assigned drafts still normalize to pending. If an incoming legacy rule lacks the optional review boundary, it inherits a persisted target boundary with a preview notice. This does not rewrite nested history or create approvals. Restore produces no new inbox notifications or external deliveries. Member packets remain scoped to personal facts and require destination policy/cycle dependencies; administrator export is the complete migration path.

## DingTalk access and notifications (2026-09-18)

`shared/notifications.ts` defines inbox, targets, delivery and settings response types. All writes retain the existing JSON/same-origin guard. No incoming callback endpoint is required for this phase.

- GET `/api/auth/dingtalk/config` returns only configured state, corpId and public clientId. POST `/api/auth/dingtalk/exchange` `{code}` verifies internal-app identity and returns `{authenticated:true,user}` plus a normal session, or `{authenticated:false,bindingRequired:true}` with a five-minute HttpOnly browser proof. It never creates users. Exchange is rate-limited and codes are single-use.
- GET `/api/dingtalk/binding` requires ordinary authentication and returns `{bound,corpId?,boundAt?,pending?:{corpId,userid,expiresAt}}`. POST `/bind` with `{}` explicitly consumes the same browser proof for the logged-in, active approved account. POST `/unbind` with `{}` removes binding and revokes existing sessions. Provider identity and local account are each unique; names are never matched automatically.
- GET `/api/notifications?filter=all|unread|pending&cursor=...&limit=50` filters the recipient's complete projected inbox before cursor pagination. The limit defaults to 200 and is capped at 200 per page. Returns `items`, `unreadCount`, `pendingCount`, `totalCount`, `filteredCount`, and `nextCursor`; counts cover the complete authorized inbox, including records older than the first 200. Cursors are bound to recipient/filter and sort by createdAt plus ID. GET `/:id` is read-only; POST `/:id/open` and `/:id/acknowledge` with `{}` separately record local opening and owner acknowledgement. POST `/open-all` affects only the current recipient's viewed state, never acknowledgement. A notification ID grants no business access. Lost permissions redact details; expired assignment versions cannot be acknowledged.
- GET `/api/notification-status?type=plan|task|weeklyRecord&id=...` is manager-only and returns `{items:NotificationView[]}` for the source detail panel. POST `/api/notifications/:id/remind` is manager-only, requires a still-pending acknowledgement, and permits one reminder per recipient/target/Shanghai day without creating a new acknowledgement version.
- GET and PUT `/api/notification-settings` are manager-only. PUT takes `{version,externalEnabled,pilotUserIds,sendStartHour,sendEndHour}`. Enabling requires configured credentials, HTTPS, server opt-in, a deployment ID and a nonempty pilot. POST `/api/notification-deliveries/:id/retry` retries only explicitly failed deliveries with unchanged activation and binding; unknown sends cannot be blindly replayed. Settings, retries, bindings and manual reminders have dedicated audit records outside business exports.
- POST `/api/weekly-assignments` `{requestId,taskId? OR task:{...taskInput},record:{...weeklyInput}}` creates the task if needed, weekly row and notification atomically. Actor-scoped requestId is 16–100 letters/digits/underscore/hyphen. An identical retry returns current entities; changed content with the same key is a 409. A failed row creation leaves no orphan task or notification. Task creation kind governs the new task+row pair.

Live actions enqueue inbox and outbox in the same SQLite transaction. Draft/unpublished, self-created, proxy and imported work remain silent. Repeated publication of unchanged weekly work does not reset owner acknowledgement. Provider acceptance, provider-reported success, system opening, acknowledgement and formal business receipts are distinct. Safe retries use 1/5/15/60-minute delays with five attempts; missing/uncertain async send receipts become unknown, and known receipts are polled up to 24 hours. Changed assignments coalesce pending external deliveries for five minutes; ordinary backlog expires after seven days. Friday reminders use formal duty views and expire at cutoff, with only the latest current slot eligible; summaries expire at Friday midnight.

Identity, binding audit, notification/obligation/work-version state, activation settings, delivery records, reminder quotas and atomic-request receipts are excluded from business JSON transfer. Whole-database backups retain them. Before cloning/restoring, disable external send and use a new deployment ID as described in `docs/dingtalk-public-server.md`.

## Problem feedback (2026-09-21)

`shared/feedback.ts` defines all request and response types. Routes require an active approved session; writes use the existing same-origin JSON guard. Members can create and read only their own feedback. Managers can read and process all feedback; confirmation of a working fix belongs only to that feedback's reporter, including when the reporter is a manager. Feedback is separate from plans, task completion, KPI and import batches.

- GET `/api/feedback/meta` -> `{managers:[{id,name}],defaultAssigneeId}`. The default receiver is the first available manager. Only active, approved managers are assignable.
- GET `/api/feedback?scope=mine|all&status=...&assigneeId=...&cursor=...&limit=...` -> `{items,counts:{all,new,in_progress,verification,closed},nextCursor}`. `scope` defaults to `mine`; `all` and receiver filtering are manager-only. `limit` defaults to 30 and accepts 1–100. Receiver/permission filters precede counting and pagination; status counts cover that complete scope, independent of the selected status tab. Opaque cursors order by descending update time and ID. Items include reporter/receiver names and screenshot counts, never screenshot bytes. An unavailable receiver is marked in `assigneeName` and `assigneeAvailable:false`; reads do not silently reassign responsibility.
- GET `/api/feedback/:id` -> `{feedback,events,attachments,allowedActions}`. The timeline and attachment list contain metadata only. Unauthorized or missing feedback returns 404. Members receive only `duplicateLinked`, without the primary issue ID or access to that other reporter's feedback.
- POST `/api/feedback` `{requestId,description,kind?,impact?,context?,attachments?}` -> 201 with the same detail response. Description is required, up to 10,000 characters. `kind` is `bug` (default), `usability` or `suggestion`; `impact` is `normal` (default) or `blocking`. Context only retains `path`, `appVersion`, `userAgent`, `viewport` and `errorRequestId`; the path retains known page names and date filters while stripping credentials, other query values and fragments.
- POST `/api/feedback/:id/actions` `{requestId,version,action,...}` -> updated detail. See the action rules below. Every accepted write, including its events, attachments, responsibility changes, command receipt and in-app notifications, commits in one synchronous SQLite transaction.
- GET `/api/feedback/:id/attachments/:attachmentId` returns the authorized image bytes. Every request checks the current session and feedback scope; another feedback ID cannot be used to fetch the attachment. Responses use the validated image MIME, `X-Content-Type-Options:nosniff`, a sandbox policy and `Cache-Control:private,no-store`.

The four statuses are `new` (待受理), `in_progress` (处理中), `verification` (待验证) and `closed` (已关闭). Additional waiting information lives in `waiting:{kind:'request_info'|'defer',reason,reviewAt}` rather than inventing another completion state. Current allowed actions are returned by the detail endpoint:

- `comment`: reporter or manager; requires `text` or at least one screenshot. A reporter's supplement clears an outstanding `request_info` flag. Comments may be appended to closed feedback without reopening it.
- `assign`: manager; requires an available manager's `assigneeId`. `start` moves a new/in-progress issue into active processing and clears its waiting flag.
- `request_info`: manager; requires `reason` describing what to supplement. `defer` requires both `reason` and a future `reviewAt`; the timestamp is stored in canonical UTC. Both remain `in_progress`.
- `ready`: manager; requires nonblank `resolution`, `releaseVersion` and explicit `released:true`, meaning the fix is actually available for verification. It enters `verification` and does not close the issue. A release already rejected in this feedback cannot be announced as a new fix using the same version.
- `confirm`: reporter only, from `verification`; records `closure.kind:'confirmed'`. `reopen` is available to the reporter or a manager from verification/closed, requires `reason`, retains the timeline and records which release failed verification.
- `close`: manager; requires `reason` and records `closure.kind:'manager'`. This is displayed separately from reporter-confirmed resolution.
- `duplicate`: manager; requires `duplicateOfId` and `reason`; rejects self-links, cycles, missing primaries and redundant links. It keeps the local issue open, forwarding only generic result text and an available release version through open descendants. Primary descriptions, comments, screenshots and reporter identities do not propagate. Linking a chain to an already released/confirmed primary also updates its open descendants. Each reporter confirms independently; primary confirmation and repeated announcements of the same rejected version cannot override a linked reporter's failure. Independently closed feedback remains closed.

When a successful write finds a receiver who is disabled, unapproved, missing or no longer a manager, the transaction selects the first available manager and records a system assignment event plus in-app notifications. This also applies when reopening closed feedback and when propagating a result to an open linked issue. With no available manager, the operation fails with 409 without recording a misleading acceptance; the client retains its input for recovery.

Each command needs an actor-scoped `requestId` of 1–160 letters, digits or `_.:-`. The content fingerprint includes the operation and submitted version. An identical retry returns the currently authorized detail before performing stale-version checks, without repeating events or notifications. Different content using the same ID, or a fresh command with an outdated version, returns 409. After a version conflict, refresh, review the retained input and submit with the current version and a new request ID. API error bodies include the server-generated `requestId`, matching `X-Request-Id`; it is distinct from the client command ID.

Attachments use `{name,mimeType,dataBase64}`: PNG, JPEG or static WebP only, at most three per operation and at most 2 MiB decoded bytes each. Feedback creation/actions have a 9 MiB JSON limit; other API body limits are unchanged. The server checks canonical base64, declared type, container structure, dimensions, PNG checksums/decompressed rows, JPEG tables/nonempty scans and WebP payload/partition bounds. This is not a complete JPEG/WebP pixel decoder; the browser also attempts actual image decoding before adding a screenshot. Unsupported, damaged, oversized or excessive images reject the whole operation. Binaries are stored only in the protected `feedbackAttachments` collection.

Feedback notifications use a `feedback` target and remain strictly in-app: enqueueing creates no external delivery or work-acknowledgement obligation, and the worker refuses feedback even if an otherwise eligible external delivery was erroneously queued. Reading a message never confirms a fix. The `feedback`, `feedbackEvents`, `feedbackAttachments` and `feedbackCommands` collections are retained by whole-database backup and excluded from business JSON transfer. Reporter, receiver, attachment and historical operation references participate in account deletion blockers. This API documentation describes the local implementation, not a production deployment.
