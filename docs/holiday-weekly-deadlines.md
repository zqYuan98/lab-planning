# 假期与调休周提报截止

本功能对应专家审查 ER-01 / B1。默认仍为周五北京时间 16:00；管理者可以显式选择“当周最后一个工作日 16:00”。本次交付的是代码和本地验收，没有修改正式环境的日历、截止或提交记录。验证见[本阶段验收记录](validation-2026-09-24-holiday-deadlines.md)。

## 设置后续周期

1. 管理者进入「每周执行 → 提报规则 → 截止方式与工作日历」。
2. 选择固定周五或当周最后一个工作日。未覆盖的日期默认周一至周五工作、周六日休息。
3. 按企业实际安排维护例外日期，每行使用 `YYYY-MM-DD 工作` 或 `YYYY-MM-DD 休息`。系统不会自动下载国家节假日安排。填写区域代表完整例外表，修改时保留仍需使用的已有日期。
4. 保存后查看提示的生效周。配置从**下一个完整周**生效，并保存当时的日历和政策版本；本周以及已经生成的周期保持已保存的截止。下周周期若已存在，系统拒绝覆盖，需要先核对数据。

例如，企业确认 2026-10-01 至 10-07 休息、10-10 工作时，应逐日录入这些例外。新政策下 09-28 周截止为 09-30 16:00，10-05 周截止为 10-10（周六）16:00。示例不代表正式环境已配置。

这份日历与「进展、催办与摘要」共用。协作功能关闭时，周提报仍可使用日历；修改共享日历也会影响协作功能后续的工作日判断。从协作设置修改日历时，已启用的提报截止政策同样从下一完整周更新。版本冲突应重新读取并核对，不能覆盖其他管理者刚保存的配置。

在已生效的“最后一个工作日”模式下，整周没有工作日时，该周没有“本周完成情况”和“下周计划”的正式提报义务，不计缺交、不发提报催交；仍可安排任务和记录进展。与该提交周期对应的下周计划也不要求走无法完成的整份提报审核。固定周五模式仍按周五截止，日历本身不会免除该模式的义务。普通工作周继续适用原有提交与审核规则。截止整点提交仍记为逾期。

## 已生成周期的显式修复

保存日历不会重算现有周期。需要修复时，在提报规则中点击“预览所选周期截止修复（只读）”，核对旧、新截止、工作日、涉及应交项和拒绝原因，填写修复原因后确认。

修复使用**当前已保存共享日历的最后一个工作日**，不取未保存的表单内容，也不取“固定周五”选项。它是一次例外更正，政策快照版本为 0，与后续周期的版本化政策区分。即使日期相同，首次补充日历依据也会形成有审计的修复。

只有同时满足以下条件才可修复：

- 周期已生成，且是当前自然周；应交名单已核对。
- 原截止与新截止都还未到达。
- 没有提交、缺交、调整、审核历史，也未进入报告或历史复盘快照。
- 周期与所有应交项的截止一致；不切换现有周期的“有义务／无义务”状态，也不删除应交项。

不满足条件时保留原记录，按[首批过渡预案](superpowers/plans/2026-09-24-expert-review-first-release.md)逐项处置。`frozenAt` 表示名单冻结，修复不会改名单。预览不创建数据，确认会重新检查权限、日历、版本、业务事实和操作环境；预览 10 分钟内有效，进程重启或相关数据变化后需要重新预览。同一确认重试不会重复修改或追加审计，失败不会留下部分修改。

提醒与管理摘要使用周期保存的实际截止日，已排队但不再匹配的旧提醒失效。历史提交、缺交事实、冻结报告和复盘不随日历更新。

## 发布和回退清单

- [ ] 在目标 Linux / Node 24.20.0 环境完成测试、构建、启动和关键角色验收。
- [ ] 创建并验证最新完整备份，在隔离环境恢复；记录新旧制品版本。
- [ ] 核对企业实际日历、当前周期事实及下周预期日期，明确是否启用新模式；不能直接把示例当作企业安排。
- [ ] 部署兼容制品后，以管理者设置后续政策；当前周期如需修复，先预览并逐项核对资格。操作避开该周期实际截止日 12:00–17:00。
- [ ] 验证成员可见日期、管理员统计、全休周和通知队列；观察 24 小时。通知渠道继续使用现有显式启用设置。

存储格式升级到 **v4** 是兼容性标记，迁移本身不改写历史业务记录。启动新版后，即使尚未启用新政策，也不能直接回滚到只支持 v3 的旧程序。已经用基线旧迁移程序验证它会拒绝 v4 数据库。

业务 JSON 包在包含新政策、截止快照或修复审计时使用 **v7**；没有新字段的数据仍使用所需的最低格式。v1–v6 包继续可读，新包按保存的政策依据验证，不依赖目标环境当前日历。运行时修复回执不进入业务 JSON；整库备份保留运行状态。

回退优先发布兼容 v4/v7 的修复制品。需要恢复为固定周五时，显式设置后续周期政策，已有截止及审计继续保留。整库恢复必须先隔离演练、保全升级后的新增业务记录，并按[部署手册](deployment.md)轮换 operation context；不能用旧备份直接覆盖新提交。
