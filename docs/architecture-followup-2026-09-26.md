# 架构改进第二批（2026-09-26）

分支 `arch/remaining`，基于已上线的 `perf/page-loading`。数据库存储版本仍为 6，未新增迁移；与线上版本可以直接互相切换代码。

## 变更内容

### 定时任务移出请求线程

周提报核对、定时报告、提醒和协作摘要原先在处理请求的线程上每 30 秒同步执行一次，执行期间所有请求都要等待。现在它们在独立的工作线程中运行，使用自己的数据库连接：

- 页面读取改用只读事务（`Store.readTransaction`，SQLite `BEGIN DEFERRED`）。WAL 模式下读的是快照，不等待定时任务的写锁。只读事务内如有写入会直接报错，防止以后误用。
- 只读检查找出一处“读的时候写”：操作环境标识原来在第一次读取时才创建。现在数据库打开时就创建；已运行过的线上数据库本来就有这一行。
- 目标负责人视图在读取时要写访问审计，这条路径仍使用写事务。
- 分页游标的数据修订号加入 `PRAGMA data_version`，定时任务线程的提交同样会使旧游标失效，与原来的行为一致。
- 诊断页的定时任务心跳由工作线程转发，显示方式不变。线程意外退出时记录日志，30 秒后自动重启；服务停止时会等线程关闭数据库连接。

### 权限判断收口

服务端 55 个文件中 236 处直接比较角色字符串的写法，全部改为 `server/authorization.ts` 中的 `isManager` / `isMember` / `isObserver`。以后调整角色定义只需改一处。`tests/authorization-usage.test.ts` 会拒绝新增的直接比较；230 个接口的权限矩阵测试结果不变。

### 字段规则统一，并修复标题长度限制

`shared/entity-rules.ts` 集中定义账号、项目、年度目标、月度目标、任务、周记录的状态枚举和字段长度上限。共享类型、业务校验、迁移包定义和前端表单都引用这里的值。

统一过程中发现并修复了以下问题：

- **年度目标名称、月度目标名称（编辑表单）、个人任务名称、合并后的成果名称**：这几个表单限 200 字，而服务端、新建表单和迁移包都允许 300 字。超过 200 字的已有标题在这些表单里一改动就无法提交。现在统一为 300 字。
- **成员姓名**：成员管理里限 80 字，注册页和服务端允许 100 字。现在统一为 100 字。

新增的防护：

- 编译期检查：六类核心实体的 TS 类型和迁移包定义必须字段一致、类型兼容，否则类型检查报错。
- `tests/entity-rules.test.ts`：把所有字段填到上限，保存、导出、恢复到新库后内容不变；同时禁止前端表单硬编码长文本上限或标题上限。

### 变更上下文按调用栈隔离

协作变更批处理、任务通知抑制、协作事件延迟发布这三个开关，原来以数据库对象为键挂在模块级变量上。设置期间对同一数据库上的所有操作都生效；如果中途出现异步等待，就会影响到其他请求。现在这三个开关和静默导入一起改为基于 `AsyncLocalStorage` 的 `storeScope`：值只在自己的调用链内可见，任何退出路径都会清除。

审计记录已经统一经过 `DomainBase.audit` 分发，对外发送已经通过持久化的投递队列完成（事务内写入，后台带租约重试）。所以没有另建发件箱。

## 验证

- 完整测试 1115 项全部通过，类型检查和生产构建通过。
- 性能门禁在 12/36 个月的数据规模下通过。
- 浏览器冒烟检查 12 项通过，使用生产构建和真实工作线程。
- 本地未验证 Docker 镜像构建，请以 CI 的 container 任务为准。
- 本地（Windows）无法发送 SIGTERM，未实测收到信号后的优雅停止；`startSchedulerThread` 的停止流程由单元测试覆盖。

## 发布与回退

- 无数据库版本变化，发布前的整库备份照常进行即可。
- 回退到 `perf/page-loading` 只需切换代码，数据库无需处理。
- 发布后请留意日志：`定时任务线程意外退出` 表示工作线程崩溃（会自动重启），`slow_scheduler_tick` 表示定时任务单轮较慢。它们现在不再阻塞页面，但仍值得查看。

## 未做：核心数据拆表

路线图 ER-18 计划把月度目标、任务、周记录、审计记录从通用的 `entities` 表拆成独立表。本批没有做，原因如下：

1. **性能上已无必要。** 加上索引后，36 个月合成数据下所有页面的服务端耗时在 55ms 以内（最慢的是部门概览的“全部历史”视图）。拆表不会带来用户能感知的变化。
2. **改动面大、风险高。** 需要改写 85 处直接写 SQL 的查询和 189 处读写调用，并调整迁移包、备份恢复和性能夹具。还要对线上数据做一次需要停机的迁移。
3. **是否停机、何时停机需要你决定。**

如果仍要做，建议的方式是：先把 `Store` 中按集合读写的逻辑收进各领域的数据访问层；再选一个停机窗口，离线迁移（整库备份 → 迁移脚本 → 逐表行数与校验和比对 → 恢复演练 → 切换），不采用路线图中“双写加 14 天观察”的方式。预计 8–12 个开发日。
