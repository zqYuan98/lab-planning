## 6. 性能与发布验收标准

### 性能测量合同

- 固定合成数据种子、采样方法、Node 版本和运行规格；覆盖 12/36 个月，多成员/目标/任务、发布快照、报告和审计历史。现有仅放大周记录的夹具不足以捕捉目标快照热点。
- CI 主要限制 SQL 次数、解析字节、响应大小；时延在固定环境记录 p50/p95，不能把随机 CI 主机的单次 300 ms 当稳定门禁。
- 临时 bootstrap 参考预算：SQL ≤25、解析 ≤25 MB；shell 参考 SQL ≤10、解析 ≤200 KB；任务分页参考 SQL ≤10、解析 ≤1 MB。ER-04 首次运行校准并提交固定预算，异常变慢先排查，不能自动按每次新基线抬高门槛。
- ER-02 的“12 个月 member bootstrap <300 ms”作为固定环境待验证目标；若未达到，记录瓶颈并继续优化或提前迁移相关页面，不借历史 4 个月数据宣布达标。
- R3 目标是普通页面分页/摘要 API 单响应 <100 KB、36 个月数据下服务端 p95 <150 ms。大报告正文、文件/附件、全量导出单列预算，使用详情读取或流式导出，不能为限体积而丢业务数据。
- 首次加载压缩后 <400 KB、可交互 <1.5 s；明确从空缓存导航到登录后首页的测量路径、办公室网络条件和包含资源。通用“页面 <1 s”是产品体验目标，需区分服务端、网络与渲染。

### 每批发布门禁

1. 针对性测试、完整 `npm test`、`npm run build`，以及当期性能/权限/迁移检查通过；测试数量允许增长，不以恰好 914 项为目标。
2. 使用合成或获准的隔离脱敏数据验证。热点输出对比必须有独立旧实现；`phase3-baseline.ts` 导入当前 helper，单用它不能证明本次优化等价。
3. 在目标环境创建并验证最新备份。数据格式变更先做恢复演练；回滚程序必须兼容当前数据格式，不能机械重部署不兼容旧镜像。
4. 平常避开周五 12:00–17:00；B1 上线后也避开该周期实际截止日 12:00–17:00。R1 最迟在 9/30 12:00 前结束变更，未满足门禁即使用过渡预案。
5. 小批发布后观察 24 小时错误率、接口 p95、读取量和业务异常。发布负责人保存可回退制品及操作记录，测试人员核验关键角色路径。
6. 回退不得用旧备份直接覆盖升级后的新业务记录。涉及恢复/克隆时按现有部署手册轮换 operation context，先隔离验证。

性能、CSS 和审核工作量目标均需实测，不把专家的样本结果直接当本系统新版本的验收结果。
