## 日常工作怎么流转

1. 管理者仍在月度目标、每周执行中安排工作。成员收到包含事项要求、期限和变化的通知，在平台确认接收。确认接收不改变执行状态。
2. 成员进入 **进展与催办 / 我的进展与回应**，选择任务，保存实际进展。任务整体状态与本周执行记录分开；需要回应催办时，明确勾选“同时回应这条催办”。
3. 管理者在该列表勾选事项，填写更新要求和回应期限，先按接收人预览，再确认发起。相同任务已有催办时复用原请求；修改要求或核实关闭都留原因。
4. 完成、重新打开、阻塞、解除、改期和催办回应向指定管理接收人回告。普通进展进入摘要。本人无变化也能回应，但必须说明原因和下一步，不伪造新的有效进展时间。
5. 启用延期审批后，成员对下发任务提出申请；批准前保留原截止日期。审批检查申请和截止版本，避免覆盖管理者随后修改的日期。
6. 成员仍需到每周执行核对并正式提交。任务相关的新实质进展会使关联提报显示需重新核对，原首次准时/迟交事实不被抹除。提报页面展示进展内容，核对后发生新进展则拒绝旧快照。
7. 管理者处理阻塞支持、月目标审核、成果验收和报告定稿。支持事项的“核实关闭”不会把任务或周工作伪装成完成。

## 开关与接收范围

**通知设置 → 进展、催办与摘要** 提供总开关、成员试点、默认管理接收人、工作日历和各项独立开关。每任务还可指定管理接收人。不从职位、项目负责人或姓名猜测管理关系；未配置接收人不会向所有管理者广播。

新功能初始关闭。历史任务通过显式纳入督办开始观察；启用后的有效新下达在试点范围内自动纳入。导入与恢复不产生历史群发，恢复的督办暂停。暂停可指定复查时间，恢复不会改写原截止日期。

| 通知 | 默认规则 | 防重复方式 |
| --- | --- | --- |
| 成员风险 | 工作日 09:00 汇总到期、逾期、无进展和催办超时；17:00 汇总下一个工作日临期 | 同任务每天一个风险条目，每天最多两张风险卡 |
| 逾期 | 逾期第一个可发送工作日开始，第三个逾期工作日升级给管理者 | 相邻两次至少隔两个工作日，成员每周最多三次 |
| 无进展 | 满配置数量的完整工作日后检查，默认三天 | 每周最多两次；本人实质进展重置观察起点 |
| 催办超时 | 回应期限之后的有效工作日检查 | 成员自动提醒两次后转管理者处理 |
| 阻塞 | 首次阻塞回告，默认满两个完整工作日仍未解除升级 | 区分任务和本周阻塞；周结束未解除转管理者核对 |
| 手动催办 | 先预览，同人多事项合并 | 每成员每天最多三张，同任务每天一次，跨管理者共享额度 |
| 关键回告 | 五分钟内合并 | 每管理者每天最多三张，多出部分进入摘要 |
| 最小管理摘要 | 17:30 处理风险与未回告事实，晚到事实合入下一工作日摘要 | 与完整日摘要共用日键，来源只消费一次 |
| 完整日/周摘要 | 可选日摘要；周五周摘要替代当日日摘要 | 周统计明确包含本期已回告事实，不冒充新变化 |

所有外发受原总开关、试点、身份绑定与发送窗口约束。成员可以关闭自己的可选行动摘要。原周提报的周五提醒和正式截止规则保持独立。规则预览纯读取，不写提醒额度、任务或队列。

## 钉钉原生能力

**通知设置 → 钉钉原生能力** 显示配置、真实验收状态、成员身份和待核查操作。原生待办、互动卡片、机器人、组织事件、离职补偿分别启用；主呈现渠道只能选一个。

- 原生待办对应一个明确业务义务：安排确认、催办回应、提报、审核/验收等。单事项摘要可映射原义务；多事项摘要保留平台详情入口，避免一个勾选替代多项处理。
- 外部待办打勾只触发核对，不能直接把任务完成或代替正式提报；平台业务完成后再同步关闭对应外部义务。
- 卡片或机器人写入先生成包含具体事项与字段的待确认操作。校验本人身份、当前版本、绑定及部署代际后执行同一业务服务；重复确认只执行一次。
- 结果未知的创建、投放或回复不会自动重发或换渠道。只有明确未受理，且没有其它已受理步骤时，才可按设置降级；外部缺失需核查后显式重建。
- 组织事件通过官方 Stream 接收，先持久化再确认，后台处理。经验证离职隔离身份与渠道并撤销会话，保留业务历史；重新加入不会自动恢复旧授权。

接口、权限、模板参数及真实验收要求见 [原生能力验证记录](validation-2026-09-20-dingtalk-native.md)。官方模板 ID、机器人权限、已绑定成员身份、Stream 和各端入口必须在实际企业测试后再标记已接入。

## 运行、备份与回退

运行诊断支持按成员、状态、类型和日期查询全部投递，用游标翻页；显示真实心跳、最早可处理项、下一处理原因、绑定覆盖、磁盘及备份状态。工作通知的受理、送达、查看和确认分别显示；未知结果不提供直接重发。

服务停机立即停止新领取，等待在途响应和收件处理完成后关闭数据库。容器与生产 systemd 停止宽限均为 45 秒，应用排空预算 35 秒。本次上线已验证新版服务实际停止与重新启动，systemd 使用 control-group 管理进程。不要用第二个实例共用同一数据库启动多个独立定时器。

加密备份工具提供创建、校验、受控异机上传、保留预览和隔离恢复演练；密钥放在数据和备份目录以外。尚未提供异机目标及独立密钥时，界面应显示待配置。模拟恢复通过不能代替真实 RPO/RTO 测量。详见 [P0 验证记录](validation-2026-09-20-dingtalk-foundation.md)。

发布前保留当前完整备份、部署标识、在途投递和配置记录。正常升级维持部署标识；换服务器、克隆或恢复数据库使用新的部署标识并重新确认范围。关闭新功能不影响已有业务读取，不扫描历史补发。存储已升级到版本 2，禁止直接使用只认识版本 1 的旧程序；不得用旧数据库覆盖更新后业务。兼容回退产物和限制见 P0 验证记录。

使用第一批一致性修复版本时，整库恢复、克隆或回退还须在启动前执行 `npm run reset-operation-context -- <恢复库路径>`，使旧浏览器承接命令失效；该内部命令环境与钉钉部署标识独立。业务 JSON 恢复实际写入时自动在事务内轮换，普通应用重启保持不变。具体命令见[部署手册](deployment.md#更新备份与恢复)。

## 验证边界

自动化覆盖业务事务、权限、幂等、旧 API 门控、日历/额度、发送前逐项裁剪、业务迁移、备份与模拟网络故障。浏览器使用独立测试账号和数据库。新开关没有在真实企业或生产数据库启用。

待实机验收的是钉钉各端的应用入口与免登、实际应用权限与配额、发布后的互动卡片模板、真实 Stream 事件及异机备份目标。生产服务管理器停止宽限与新版停启已验证；真实外发在途时的排空仍需在受控试点中观察。平台的进展、催办、延期和摘要页面已随版本上线，按对应权限与开关使用。
