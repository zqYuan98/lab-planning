# OpenProject 社区版与实验室部门管理融合评估

日期：2026-09-18。状态：可行性评估与推荐方向，尚未实施或完成 OpenProject 联调。

用户已明确：以 OpenProject 为主体，融入部门管理理念；以免费、可自部署的社区版为基础。

## 结论

可行。推荐 OpenProject 承担项目管理主体，在其中提供“部门管理”入口，用定制模块承接月度承诺、个人周提报、成果验收、报告快照及智能导入。现有 lab-planning 中有价值的是业务规则、历史数据和部分服务能力。

本次依据当前 lab-planning 代码、README 和相关文档，以及 OpenProject 官方文档进行评估。未部署 OpenProject、未访问生产实例、未迁移业务数据。具体版本的插件兼容性、免费版字段能力和权限边界需要试点验证。

## 应当保留的管理理念

1. 以交付结果组织工作：每个目标有主要负责人、预期成果、期限和验收要求；研发、测试、硬件及部门日常工作都能表达。
2. 年度目标独立记录方向和进展，不强制建立年度—季度—月度任务树。
3. 按当前实现，由管理者建立、审核整理并发布普通月度目标；成员可以提报本人负责的临时月度目标。成员围绕本人参与的目标安排个人任务和每周工作。
4. 一项个人任务可以跨周，每周承诺和实际进展独立保存。跨月承接保留前月事实和来源，成果不重复计算。
5. 成员自报完成与管理者确认月度成果是两类事实，分别统计。
6. 周五北京时间 16:00 前分别正式提交“本周完成情况”和“下周计划”；保存草稿不等于提交，补交不抹去截止未交事实，16:00 整点按逾期处理。
7. 调整计划可以发生，但原承诺、原因、操作者、时间和版本需要保留。报告定稿后不随源任务更新而改变。
8. 报告复用执行事实；统计由程序计算，AI 只辅助文字整理。重点展示不能改变全量统计分母，计划不能自动写成成果。
9. 普通成员仅可查看本人的个人任务和周记录，管理者按权限汇总。目标负责人身份不自动授予查看其他成员个人工作的权限。月目标本身也按负责/参与关系授权；离开参与关系仅保留获准的历史快照，合并来源中的他人个人说明需要裁剪。

依据：[当前系统说明](../README.md)、[接口约定](api-contract.md)、[集成接口](integration-api.md)。旧 AI-manage 的强制季度目标树和绩效权重属于历史方案，不作为本次默认要求；9 月 8 日草案中“成员先报普通月计划”的表述也应以当前规则为准。

## 三条路线

| 路线 | 收益 | 代价与适用性 |
| --- | --- | --- |
| OpenProject 主体 + 部门模块 + API 集成服务（推荐） | 保留项目管理能力，逐步吸收现有业务规则；现有 Node 导入和报告能力可先作为内部服务 | 需要身份映射、明确数据归属、定制入口和版本兼容维护 |
| 全部通过 OpenProject 原生配置实现 | 定制代码少，上手最快 | 难以完整表达周整单正式提交、截止事实、不可变报告快照和现有个人可见性；适合验证基础流程 |
| 深度修改 OpenProject 核心并全面重写现有功能 | 界面和规则可高度统一 | Rails/Angular 重写量与上游升级冲突较大，首期不建议采用 |

官方支持通过 Rails engine/gem 插件添加路由、页面和模型，也提供 API v3 与 Webhook。插件需要纳入部署镜像，不能理解成将现有 React 页面直接拖进去；纯前端扩展和混合插件还存在构建约束。[插件开发](https://www.openproject.org/docs/development/create-openproject-plugin/)、[API](https://www.openproject.org/docs/api/)、[Webhook](https://www.openproject.org/docs/system-admin-guide/api-and-webhooks/)。

## 推荐功能分工

| 现有业务 | OpenProject 承接方式 | 需要保留或开发的部分 |
| --- | --- | --- |
| 部门项目、负责人、协作与排期 | 原生项目、成员角色、工作包、关系和甘特图 | 现有人员与项目编号映射，归档规则核对 |
| 部门月度目标 | 权限等价验证通过后，以“月度目标”工作包类型表达当前目标；否则先由模块授权模型承载 | 月份、临时来源、参与资格、审核合并、发布版本及承接关系；验证非参与者不可读、离组历史权限和来源说明裁剪；字段按目标社区版能力选择配置或插件模型 |
| 个人任务 | 优先评估工作包承载稳定任务身份 | 必须先验证本人可见性；未满足前留在模块私有模型，不向共享项目投射私人内容 |
| 本周完成与下周计划 | 从关联任务提取草稿 | 独立周记录、应交名单、截止判定、正式提交版本、代录和豁免审计 |
| 月度成果验收 | 角色与状态流转表达当前阶段 | 验收结果、证据、审计及口径独立于任务进度百分比 |
| 年度目标 | 部门模块独立维护，可按需关联项目 | 独立年度进展，不由月计划条数推导 |
| 部门总览 | 项目与工作包汇总视图，加部门专属总览 | 应交情况、待验收、阻塞、临时工作与调整等管理口径 |
| 中文周报、月报 | 从 OpenProject 与部门模块汇总事实 | 报告快照、编辑、定稿、Word 导出和可选 AI 润色 |
| 表格、截图、文字导入 | 现有解析/校对服务适配 OpenProject API | 原始资料、来源行、幂等编号、人工确认与异常处理 |
| 钉钉与站内提醒 | 部门事件驱动通知服务 | 账号绑定、通知去重、深链接与真实客户端验证 |

OpenProject 的工作流配置可按角色和工作包类型限制状态转换；这只是承接当前阶段的基础，不能单独替代周期提交和报告快照。[工作流文档](https://www.openproject.org/docs/system-admin-guide/manage-work-packages/work-package-types/workflows/)。

## 以 OpenProject 为主体的具体含义

- 用户从 OpenProject 进入项目与任务管理，并从“部门管理”入口访问月度发布、我的周提报、成果验收和报告中心。入口、中文命名和成员常用路径需要原型验证。
- 目标是以 OpenProject 账号身份作为主身份，绑定现有人员 ID；身份委托与会话对接需选型验证，不复制密码，不默认宣称社区版已经具备所需单点登录方案。
- OpenProject 主持项目及由其承载的工作包当前数据；部门模块主持周期承诺、正式回执、验收事实、报告快照与审计。展示副本不能成为第二个独立可编辑主数据源。
- 已验证权限后才将月目标和个人任务迁移到工作包；若用模块授权模型承载，它也是 OpenProject 部门模块的一部分，继续执行参与资格、本人及管理者的服务端权限检查。
- 现有 Node 服务可先承接导入、报告生成和通知，逐步剥离原有重复的项目与任务维护页面。React 页面需要入口、身份、组件及数据访问适配；长期是否迁入 Rails 插件由试点结果决定。

当前 lab-planning 使用 React/TypeScript、Express 和 SQLite，OpenProject 使用 Rails、Angular 和 PostgreSQL。因此复用以业务算法、规则、测试场景和服务为主，数据库及页面不直接合并。[OpenProject 架构](https://www.openproject.org/docs/development/application-architecture/)、[数据库要求](https://www.openproject.org/docs/installation-and-operations/system-requirements/)。

## 免费版和集成边界

1. 社区版可自部署，基础看板可用；移动基础看板卡片不会自动修改任务状态。自动按状态等属性联动的 Action boards 属于企业版能力，本方案不依赖它。[官方说明](https://www.openproject.org/blog/create-configure-manage-projects-openproject/)、[看板行为](https://www.openproject.org/docs/user-guide/agile-boards/)。
2. 官方将工作包表单配置、部分高级字段能力列为 Enterprise add-on。目标版本需要逐项核对；不可把高级表单或层级字段当成免费的既有能力。必要业务字段可放入自行开发的部门模块。[字段配置](https://www.openproject.org/docs/system-admin-guide/custom-fields/)、[表单配置](https://www.openproject.org/docs/system-admin-guide/manage-work-packages/work-package-types/form-configuration/)。
3. OpenProject 权限围绕项目成员和角色组织。现有“只能查看本人个人任务”及“月目标按负责/参与关系可见”的规则需在选定社区版上实测，不能以“负责人=我”的筛选视图代替权限。验证范围覆盖列表、直接链接、API、搜索、关联、附件和导出，同时核对离组历史权限及合并来源说明裁剪；未证明等价授权有效前，相关目标及个人内容只存部门模块。[权限概念](https://www.openproject.org/docs/development/concepts/permissions/)。
4. 当前 Bearer 集成 API 主要开放导入和数据读取，尚不是通用项目、任务、发布、验收 CRUD API；持续对接要补适配层。OpenProject 官方也说明 API 尚未覆盖所有资源和动作，应按实际用例验证覆盖范围。[现有 API](integration-api.md)、[OpenProject API](https://www.openproject.org/docs/api/)。
5. API 适配按主数据归属路由写入；Webhook 校验签名、去重并持久化处理，配合定期对账。失败进入可重试队列，版本冲突显式提示；涉及 OpenProject 和模块的发布/验收动作要记录操作 ID 及待完成状态，避免接口部分成功却向用户报全部成功。
6. 对接不直接读写 OpenProject 核心数据库，官方明确提示数据库结构可能在升级中变化，建议避免数据库层集成。模块自身数据由自身迁移管理。[开发 FAQ](https://www.openproject.org/docs/development/faq/)。
7. 当前代码已含钉钉绑定、H5 授权和通知队列；真实企业应用、公网 HTTPS、真实客户端和送达验证尚未完成。迁移时按待联调能力处理。[钉钉接入文档](dingtalk-public-server.md)。

## 建议首期试点

选择一个项目、一个月份、管理者和两名测试成员，用模拟或获准复制的数据打通以下流程：

1. 固定一个正式发布的 OpenProject 社区版，核对原生类型、工作流、字段、插件构建和权限能力，使用独立测试环境。
2. 建立一个月度目标，完成发布；两名成员分别安排个人任务和每周记录。
3. 演示周五截止前提交、截止后补交、提交后再修改的完整版本变化。
4. 由成员报告完成，再由管理者验收月度成果，确认两套统计口径独立。
5. 生成并定稿中文报告，修改源任务后验证旧报告不变。
6. 导入一批历史计划，重复导入不得产生重复任务；核对来源及缺项。
7. 用第二成员账号通过列表、直接 URL、API、搜索和导出验证个人数据隔离；另验证同项目但未参与月目标者不能读取、离组者仅能读获准历史，以及合并来源中的他人个人说明继续裁剪。

首期结果应是可操作的纵向流程，以及免费版能力、权限、插件兼容和迁移差异的实测记录；不能仅以页面能打开作为验收。

## 数据迁移顺序

先备份并导出当前业务数据，建立用户、项目、月目标和任务的新旧 ID 映射；随后在测试环境迁移单月样本，核对数量、责任归属、附件与来源、状态、历史提交及报告快照。迁移创建时间与真实员工提交时间分别记录，不能伪造成员操作。

正式切换应安排明确写入冻结点、最终增量核对和恢复演练。过渡期每类实体只有一个主写入端；现有系统在切换后可保留只读历史。OpenProject 负责当前项目管理，旧提交与定稿快照由部门模块保留查询。

历史快照导入应保留原始内容、原编号和业务时间；无需强行将所有旧事件伪装成 OpenProject 原生日志。业务 JSON 导出不含全部运行状态，完整回退仍需数据库和原始资料备份。[备份说明](../README.md)。

## 部署成本与尚待验证事项

官方给出的服务器最低建议为四核、4 GB 内存、20 GB 可用磁盘；实际并发、附件、导入和报告服务还需要额外容量。该数字不是当前服务器已满足条件的结论。本轮未做服务器容量预检。[系统要求](https://www.openproject.org/docs/installation-and-operations/system-requirements/)。

生产安装优先考虑官方推荐的 Docker Compose 多容器方式；插件需构建定制镜像，并保持版本锁定、升级验证及备份恢复流程。[安装说明](https://www.openproject.org/docs/installation-and-operations/installation/docker/)。

本轮已经明确业务方向及免费版约束。实现前仍需通过试点确认个人任务承载方式、身份对接、原生字段/API 覆盖、插件与选定版本兼容，以及历史数据迁移差异；据此才能可靠估算开发与切换工作量。
