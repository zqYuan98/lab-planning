## 1. 部署结构和准备事项

使用 `compose.yaml` 在新服务器上运行一个常驻应用实例，宿主机 Nginx 提供统一 HTTPS 入口。Express 同时提供构建后的网页和 API；不要仅上传 `dist`，也不要把定时任务放在可能休眠的临时网页进程里。

| 项目 | 配置要求 |
| --- | --- |
| 统一入口 | 实际域名及有效 HTTPS 证书；手机、PC 与普通浏览器使用同一站点 |
| 应用端口 | 保留 Compose 的 `127.0.0.1:4310` 映射，由反向代理访问；公众通过443访问 |
| 运行实例 | 一个应用进程，持久 SQLite 位于本机磁盘；不要复制多个应用副本或使用网络共享数据库文件 |
| 持久卷 | `DATA_VOLUME_NAME` 指定数据卷，容器 `/app/data` 保存数据库；不得随容器替换丢失 |
| 后台任务 | 同一进程内，每30秒核对报告与提报提醒，每15秒处理通知投递；需常驻运行及服务器时间同步 |
| 出站网络 | 允许服务器通过 HTTPS 访问 `oapi.dingtalk.com`；另按实际需要允许模型服务商；DNS 和系统证书链正常 |
| 备份 | 使用 SQLite 在线备份并复制到独立的受控存储；另外保管服务器密钥配置 |

浏览器开发服务 `:5173` 不用于正式运行。通知队列、去重事实、绑定、查看和确认记录持久保存在 SQLite；不需要另配 Redis 或消息中间件。单实例架构和现有会话机制保持不变。

## 2. 先部署站点，保持外发关闭

以下命令在新的目标服务器执行，由部署人员替换真实参数。首次部署按[通用部署手册](deployment.md)准备 Docker、Compose、Nginx 和代码目录：

```sh
cp deploy/production.env.example .env
chmod 600 .env
docker compose config --quiet
docker compose up -d --build
docker compose ps
```

模板先使用本机 HTTP 入口，供受控 SSH 隧道初始化管理员。若迁移已有整库备份，先恢复数据，不要创建第二套空账号。完成初始化后配置 Nginx 域名、证书和 `deploy/nginx.conf.example`，再编辑 `.env`：

```dotenv
APP_ORIGIN=https://planning.your-company.example
COOKIE_SECURE=true
DINGTALK_NOTIFICATIONS_ENABLED=false
```

`APP_ORIGIN` 只写协议、域名和实际端口，不带 `/work`、`/entry` 或其他路径。`TRUST_PROXY` 只填已核实的代理 IP/CIDR；Compose 下应核对应用实际看到的 Docker 网关地址，不照抄他人的网段。反向代理继续覆盖客户端提供的转发头，不放宽现有来源校验、Cookie 或 CSP。完成配置后：

```sh
docker compose config --quiet
docker compose up -d
sudo nginx -t
sudo systemctl reload nginx
```

修改 `.env` 后用 `docker compose up -d` 重新创建受影响容器；仅 `restart` 不会重新加载 Compose 环境变量。含真实密钥时使用 `config --quiet` 校验，避免把展开后的配置全文复制到日志或工单。

先在普通浏览器验证 HTTPS 登录、注册审批、业务保存、页面刷新和导出，确认服务器重启后数据仍在。此阶段保留钉钉外发总开关为 `false`。

## 3. 企业管理员配置内部 H5 应用

由有权限的企业管理员在钉钉开放平台创建企业内部 H5 应用，并先限定少量试点成员的可见范围。应用创建、首页配置与发布可参考[钉钉官方内部 H5 免登示例](https://github.com/open-dingtalk/h5app-auth-demo)。控制台字段名称可能随版本变化，按实际企业应用页面核对。

| 控制台项目 | 本系统使用值 |
| --- | --- |
| 应用名称 | 如“实验室工作空间”，由企业确定 |
| 移动端应用首页 | `https://lab.notvitamin.com/work` |
| PC 应用首页 | 同一个 `https://lab.notvitamin.com/work`；优先独立网页窗口打开 |
| 应用身份 | 获取企业 CorpId、应用 Client ID / AppKey、Client Secret / AppSecret、AgentId，交由部署人员保存 |
| 成员可见范围 | 与试点名单一致；同时核对接口所需的成员数据范围 |
| 接口权限 | 按授权码获取当前成员身份所需的成员信息读取权限、发送工作通知和查询发送结果所需权限；按接口文档与控制台提示逐项授予 |
| 域名设置 | 按当前 H5 应用能力要求配置真实 HTTPS 域名及安全域名；使用实际生产域名，不填占位地址或临时开发域名 |
| API IP 白名单 | 若控制台要求，登记新服务器访问钉钉时使用的实际出口公网 IP；更换出口后同步更新 |

本实现使用打包在前端中的 `dingtalk-jsapi` 调用 `requestAuthCode`，将一次性授权码交给服务端验证当前企业成员。它不是个人扫码登录或钉钉管理员登录；不要因企业管理员身份而授予本系统管理者角色。JSAPI 见[获取免登授权码](https://open.dingtalk.com/tools/explorer/jsapi?id=11723)。

服务端当前使用以下接口，管理员据此核对最小权限：

| 用途 | 接口路径 |
| --- | --- |
| 获取应用访问凭证 | `/gettoken` |
| 授权码换取当前成员身份 | `/topapi/v2/user/getuserinfo` |
| 发送个人工作通知 | `/topapi/message/corpconversation/asyncsend_v2` |
| 查询通知发送结果 | `/topapi/message/corpconversation/getsendresult` |

工作通知及其结果查询依据[发送工作通知](https://open.dingtalk.com/document/orgapp/asynchronous-sending-of-enterprise-session-messages)和[获取发送结果](https://open.dingtalk.com/document/orgapp/gets-the-result-of-sending-messages-asynchronously-to-the-enterprise)。本期不申请原生待办、部门群发、全量通讯录同步等额外能力；也不需要开放平台事件回调地址。浏览器免登请求和服务端主动查询已覆盖当前流程。

配置完成后按企业流程发布应用到试点范围。若 PC 运行方式要求 iframe 嵌入，先单独联调承载方式；不要直接把站点防嵌入策略放开为通配。

## 4. 环境变量与启用条件

真实值只保存在服务器 `.env` 或等效的部署密钥配置中。当前阿里云为 `/etc/lab-planning/app.env`，由 systemd 加载。不要加入 `VITE_*`、源代码、URL、前端截图或日志。另行使用 Compose 部署时，`compose.yaml` 已显式传递以下变量。

| 变量 | 含义与默认行为 |
| --- | --- |
| `DINGTALK_CORP_ID` | 指定企业 CorpId；默认空 |
| `DINGTALK_CLIENT_ID` | 内部 H5 应用 Client ID / AppKey；不是 AgentId；默认空 |
| `DINGTALK_CLIENT_SECRET` | Client Secret / AppSecret，服务端密钥；默认空 |
| `DINGTALK_AGENT_ID` | 内部应用数字 AgentId；默认空 |
| `DINGTALK_NOTIFICATIONS_ENABLED` | 服务端外发总开关，只有字面值 `true` 才允许发送；模板为 `false` |
| `DINGTALK_DEPLOYMENT_ID` | 当前数据部署的独立标识；首次部署、克隆或恢复数据库时生成新值；模板为空 |

可用以下命令生成部署标识，将输出手工填入 `.env`；它是区分部署的随机标识，不是登录密钥：

```sh
node -e "console.log(require('node:crypto').randomUUID())"
```

正常重启、重新构建或不恢复数据库的日常升级保持该标识稳定。复制数据库到新服务器、克隆测试实例或恢复旧备份时必须换新值，不能复制源实例的完整外发配置直接启动。

免登与外发分别启用：应用凭据配置完整后可先联调身份验证，外发仍保持关闭。真正发送还要求 HTTPS `APP_ORIGIN`、服务端总开关为 `true`、非空部署标识、管理者保存启用设置、接收人在试点范围内且已绑定有效身份。仅填写凭据或打开设置页不会发送消息。

## 5. 注册审批、绑定与免登验证

成员先拥有本系统账号。新成员在普通登录页申请加入，管理者审批通过并启用后，才能登录或绑定；钉钉身份不会自动创建通过审批的本系统账号，也不会按姓名自动匹配。

1. 从钉钉工作台打开应用，取得并由服务端验证当前钉钉身份。
2. 未绑定时，使用本人已有的团队账号登录；进入消息页的“我的钉钉身份”。
3. 核对显示的团队账号、钉钉成员标识和企业，明确点击“确认是本人，绑定账号”。身份验证过期时重新获取，不复用旧链接中的信息。
4. 退出后重新从工作台进入，验证免登落到本人账号。再从本人通知链接进入，确认能恢复具体事项；转发链接不会转移事项访问权限。
5. 本人解绑后，相关系统会话失效，需重新登录。错误绑定应先核对双方身份，再解除并重新绑定，不按姓名直接改数据库。

普通浏览器继续使用原账号登录。钉钉免登失败时可重试或改用账号登录；失败原因不能通过放开跨域、改成不安全 Cookie 或接受客户端提交的 `userid` 来规避。

免登兑换按来源 IP 分别限制为每 15 分钟最多 120 次请求、20 次验证失败，适应办公室共用出口；成功兑换不会消耗或清除失败额度。平台暂时故障仅计入请求总量。服务同时限制最多 10 个并发兑换，以及各 1000 条短时挑战和已用授权码摘要；遇到限流按响应中的 `Retry-After` 等待，并核对可信代理配置，避免把所有访问误识别为反向代理地址。

## 6. 小范围启用个人通知

先完成身份验证，再开展真实发送试点。操作顺序如下：

1. 与少量试点成员约定验证时间；确认这些人在钉钉应用可见范围、本系统审批通过且已完成本人绑定。
2. 部署人员将 `DINGTALK_NOTIFICATIONS_ENABLED=true`，确认部署标识和实际 HTTPS 入口。当前阿里云执行 `sudo systemctl restart lab-planning.service`；Compose 部署执行 `docker compose up -d`。
3. 管理者进入“钉钉通知设置”，核对配置状态，勾选试点成员和“启用试点成员的钉钉个人工作通知”，保存。默认发送时段为北京时间08:00至20:00，可按整数小时调整。
4. 创建一项双方约定的试点周安排，正式纳入周记录，并确认只向责任成员产生一条工作通知；同次新建个人任务与周安排按周安排入口合并。不要用批量重放旧记录进行测试。
5. 在最近投递记录核对平台结果；成员进入消息后另核对系统查看和本人确认。平台已受理、平台报告成功、系统已查看、本人已确认、正式周提报分别验证。
6. 验证一项重要要求变更、新增或移出参与人员、临时目标审核结果，并核对接收范围；确认普通保存进展、成员自建、管理者代录、导入和草稿没有产生“已下达”通知。
7. 完成移动端与 PC 的验收记录后，由管理者逐步扩展试点范围。服务器和钉钉可见范围也应同步核对。

本版设置页提供配置状态、试点范围、发送时段和投递记录；不要把“凭据已配置”当成已经完成平台连通或真实送达验证。需要真实发送时使用上述有明确接收人的试点业务操作。

周提报提醒按正式应交项和回执计算。北京时间周五09:00、15:00各一个时段，合并本人的仍欠交项；已有回执但内容修改时提示重新核对提交。停机恢复只生成当前时段：09:00至15:00使用上午提醒，15:00至16:00只使用下午提醒，16:00后停止个人截止前催交。管理者汇总从16:05开始，只在同一周五恢复生成。不会补发前一天、前一周或已过时的上午时段；应交名单待核对时暂停自动催交。

消息在发送前再次校验账号、绑定、当前权限和应交状态。启用前或未绑定时记录的旧消息不会因为后来启用或绑定而批量补发；生效后由新业务动作及当前有效提醒生成新投递。

## 7. 失败排查与运行观察

| 表现 | 先检查 |
| --- | --- |
| 企业应用尚未配置 | 四个应用身份变量是否完整，AgentId 是否正确，修改环境变量后容器是否重新创建 |
| 服务端外发未启用 | 总开关、HTTPS `APP_ORIGIN`、部署标识；随后核对管理者保存的试点设置 |
| 钉钉身份验证失败 | 是否在钉钉内、企业与应用是否一致、应用已发布及成员可见范围、授权码是否已过期 |
| 身份与账号不一致 | 当前登录的团队账号是否属于当前钉钉用户；先退出核对，避免把他人身份绑定到本账号 |
| 已跳过 | 生成时外发未开、成员未绑定或不在试点，或发送前账号/权限/安排已变化；旧事件不补发 |
| 待发送 | 是否处于允许时段，应用进程和后台工作器是否在运行；核对配置后等待下一轮 |
| 平台明确失败 | 企业权限、人员范围、AgentId、出口 IP 白名单等；修复后只对明确失败的投递使用设置页重试 |
| 结果未知 | 请求可能已被平台接受；先核实平台和接收人情况，本系统不提供直接重发，避免重复 |
| 平台已受理 | 工作器会查询发送结果；这不表示本人已查看或确认 |

查看 `docker compose ps`、健康状态和有限条数的应用日志。平台接收后的结果查询可在暂停新外发后继续；停止新发送不会撤回平台已接收的消息。不要把授权码、访问令牌、应用密钥或完整包含密钥的环境配置粘贴到排查记录。

## 8. 备份、迁移和恢复

整库备份包括业务、账号、会话、身份绑定、通知及投递事实，也可能含模型配置密钥。它应与主库同等保护；钉钉应用密钥通过服务器环境变量保存，需要单独受控备份。

```sh
docker compose exec -T app npm run backup -- /app/data/backups/before-dingtalk-pilot-20260918.sqlite
mkdir -p ../lab-planning-backups
docker compose cp app:/app/data/backups/before-dingtalk-pilot-20260918.sqlite ../lab-planning-backups/before-dingtalk-pilot-20260918.sqlite
```

每次使用不同文件名，脚本拒绝覆盖并校验 SQLite 完整性。将备份复制到另一块受控存储；仅保留在同一个命名卷中不能覆盖整机或数据盘故障。定期备份与保留策略由运维安排，Compose 本身不自动备份。

迁移、克隆和恢复顺序：

1. 在源业务停写窗口取得最终备份，保留源数据和回退副本；由运维确保不会同时开放两个可写正式入口。
2. 新实例启动前设置 `DINGTALK_NOTIFICATIONS_ENABLED=false`，生成全新的 `DINGTALK_DEPLOYMENT_ID`。隔离验证实例同时留空钉钉凭据。
3. 停止目标应用，在新的持久卷或数据目录放入已校验备份，保留原库及 WAL 副本，核对容器用户权限和 `DATABASE_PATH`。**启动前对恢复副本执行 `npm run reset-operation-context -- <恢复库路径>`**，使旧浏览器承接命令失效；容器执行方式见[部署手册](deployment.md#更新备份与恢复)。这一步独立于钉钉部署标识，两者都需更新。不要覆盖唯一的数据副本。
4. 在受控入口核对账号、计划、历史回执、报告、附件和消息记录；恢复的历史投递保持不重发。
5. 切换正式域名与钉钉首页到新服务器，验证 HTTPS、绑定与移动端。确认正式运行不调用旧服务器接口或数据库。
6. 准备重新试点时，先在管理界面关闭并保存恢复来的外发设置；再按第6节显式启用新部署的试点。新部署标识及新的启用批次使旧投递不能沿用；旧站内记录保留查询。

恢复后不要把旧投递手动改为待发送，也不要为了继续旧队列而恢复源部署标识。确需通知当前安排时，通过核对后的新业务动作产生新消息。

## 9. 暂停与回滚

发现接收范围或内容错误时，管理者先关闭“启用试点成员的钉钉个人工作通知”并保存；部署人员再将 `DINGTALK_NOTIFICATIONS_ENABLED=false`。当前阿里云执行 `sudo systemctl restart lab-planning.service`；Compose 部署执行 `docker compose up -d`。这保留站内消息、业务保存、正式回执和原账号登录。已被平台接受的消息无法通过此开关撤回。

回滚应用版本前备份当前数据库和服务器配置，保留问题时段记录；使用经过验证的镜像或代码版本，保持外发关闭。若同时回退数据库，按第8节完整恢复流程使用新部署标识，重新核对绑定、业务状态与试点范围。只回滚消息能力时无需删除通知表、账号或业务资料，也不要清理持久数据卷。
