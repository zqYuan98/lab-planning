# 全面复盘（2026-11-18）

范围：仓库全部 88 个提交（2026-09-08 至 2026-11-06）、`docs/` 下 101 份文档、前后端源码，以及在沙箱里跑起来的真实页面。目的不是记录经过，而是找出反复付费的问题背后的共同原因，并把能预防的部分变成规则、自动检查和 Skill。

## 结论

系统的业务逻辑是扎实的：1333 条测试、230 条路由的权限矩阵、可恢复的备份。问题集中在“人用起来怎么样”这一侧，并且四类表面问题出自同一组原因：

1. **只加不减。** 每次改动都叠在上一次之上，没有任何环节要求删除。
2. **规则只说过，没有东西自动执行它。** 有检查的地方问题不再出现，没检查的地方持续漂移。
3. **验证的是“功能存在”，不是“人能完成任务”。**
4. **一次改得太多，反馈来得太晚。**

界面“AI 味重、字段乱、字号多”不是审美问题，是前三条在界面上的直接结果。

## 反复出现的四类问题

### 一、界面层层叠加

六次改版，每次新增一层样式文件去覆盖上一层（`styles.css` → `theme.css` → `shell.css` → `workspace-shell.css` → `workspace-tech.css` → `workspace-saas.css`），没有一次删除旧层。同一个指标卡 `.ow-metric` 在 2 个文件里定义了 9 次；每次改版带来一组新变量（`--tech-*`、`--ow-*`、`--wr-*`、`--auth-*`……）。字号多不是有人选了 43 种，是 6 套方案各自的刻度同时生效。

决定也没有留住：`shell.css` 里有一条注释写着登录页“是产品入口，给具体指引，不做宣传”，一周后的科技风改版把登录页做成了数字地球加三张宣传卡片。

### 二、页面在解释系统，而不是呈现工作

- 每周执行页在第一条周记录之前有多段规则说明（截止规则、工作日口径、审核生效周期、统计范围）。
- 卡片和详情上显示内部状态：`#08C751` 这类编号、`记录 V1`、完整 UUID、“已纳入周统计 · 整份提报另行确认”，同一张卡片上负责人出现两次。
- 工作事项编辑框有 16 个始终可见的字段；每个任务带 3 个标签，旁边还要一个“颜色说明”来解释标签。
- 登录页和页面副标题里是“连接协作，赋能创新”“让创新有迹可循”这类口号。

这些文字是实现每条边界规则时顺手写到页面上的。对写代码的一方它们是“说清楚了”，对使用者是每次都要绕过去的噪音。这就是“AI 味”的来源：文案和装饰来自通用推荐（旧设计规范里直接引用了某个 UI 技能包给出的 Glassmorphism 建议），而不是来自某个人要完成的某件事。

### 三、同一条规则多处定义

- 标题长度在部分表单里是 200，在服务端和其他表单里是 300，导致保存过的长标题无法编辑（a68283b）。
- 角色判断是散在 55 个模块里的 236 处字符串比较（fa593e9）。
- 同一事件里读两次时钟，毫秒边界上回应内容从通知里消失（3c9c3f4）。

这一类在 09-26 的架构批次里已经处理，而且处理方式值得注意：每一处都配了自动检查（`entity-rules` 的编译期校验、`authorization-usage` 测试、路由权限矩阵）。之后的提交记录里没有再出现这一类修复。

### 四、上线后才发现

- “restore”类修复：b167ef0 恢复内网周提报操作，2fc733e 恢复周计划提交和审核导航——都是之前可用、被后续改动弄坏的功能。
- 环境差异：钉钉内置浏览器没有 `AbortSignal.timeout`（1b01321）、弹窗定位（42b90aa）、钉钉未绑定成员登录循环（6e0d16a、1190038）。
- 每次修复再配一份发布记录和一份验收记录，所以文档数量和问题数量一起增长。

三个万行级的“同步”提交之后出现的回归，已经无法对应到具体哪一处改动。

## 共同根因

### 根因 1：没有“替换”和“删除”的定义

改版的完成标准是“新样子出来了”，不包括“旧样式删掉了”。加字段的完成标准是“能保存了”，不包括“表单还填得动吗”。写文档的完成标准是“记下来了”，不包括“过时的那份处理了吗”。于是样式、字段、说明文字、文档四样东西以同一种方式膨胀。

### 根因 2：规则没有落到会自动执行的位置

设计规范 `MASTER.md` 一直存在，里面甚至写了“静态流程说明默认收起”“页面先呈现标题再呈现内容”，但每周执行页和部门概览都没有遵守——因为没有任何检查会失败。对照组很清楚：权限、字段长度、路由这些有测试守着的规则，一次也没有再漂移。

同样，仓库里没有给 AI 助手的规则文件。每一轮开发都从对话里的临时要求出发，“科技风”“SaaS 风”“B 端参考图”依次成为当天的规范。

### 根因 3：用“测试通过”代替“人能用”

每份发布记录的结论都是“N 项测试、N 项公网检查通过”。界面的验收是逐页检查有没有溢出和可访问性问题，没有一次是“让一个成员更新一条周进展，看他要读多少字、点几下”。09-20 的使用体验审查本身也注明是静态审查，未做线上实测。所以功能越完整，页面越重，而所有指标都是绿的。

### 根因 4：批量太大

16 个工作日 88 个提交、三个提交占了大半代码量。改动大到无法评审，回归只能等使用者碰到。

## 补充：流程里的冗余（同日第二轮）

使用者反馈“发布要填原因、调整也要填原因”。排查后，服务端有 20 多处、界面有 30 多处要求填写原因或说明。它们是同一个根因 1 的另一种表现：每加一个操作就顺手加一个必填原因，没有人问过谁会读。

判断标准只有一条：**否定或代替别人的工作时才要求原因**，因为对方需要知道为什么；往前推进的操作和改自己的东西不要求，因为审计记录已经保存了谁、何时、改前改后的内容。

| 操作 | 之前 | 现在 |
| --- | --- | --- |
| 发布、补充发布月度目标 | 补充发布时必填 | 选填 |
| 修改已发布的目标 | 必填 | 选填 |
| 编辑自己的任务名称、说明、预期交付、截止日期 | 必填 | 不询问 |
| 管理者替成员调整上述内容 | 必填 | 仍必填 |
| 跨月承接、跨期向导的建立 / 关联排周 / 取消 | 必填 | 选填 |
| 合并提报、调整任务的月度归属、核对应交名单 | 必填 | 选填 |
| 退回、删除、作废、豁免、代录 | 必填 | 仍必填 |

另外去掉了一处“同一个人走两步”：管理者建立的月度目标原来要“提交审核 → 自己审核 → 发布”三步，现在提交即进入待发布，两步完成；通过后未发布的目标仍可退回修改。成员提交的临时目标仍由管理者审核。

界面上必填的原因输入框从 34 个降到 22 个（另有数处由条件必填改为选填，不在此计数内），计数已纳入基线，只许减少。规则写进了 `CLAUDE.md` 的“流程”一节，行为由 `tests/reason-requirements.test.ts` 固定。

第三轮（同日）按同一标准继续处理了：

- 临时目标、临时工作的“原因”改为选填的“来源或背景”，留空时记为“临时新增 / 临时安排”，数据约定不变。
- 授权、指派协调人、重新指派审核人不再必填原因；督办只在暂停或结束时要求原因，恢复时不要求。
- 跨期向导去掉“先勾已核对再点确认”的重复确认。
- 状态名“审核通过，待发布”改为“待发布”。

按标准保留必填的：退回、删除、作废、豁免、撤销授权、代录、核实关闭催办、延期申请及其驳回、补证、报告定稿前的版式与审阅说明。

## 关于 AI native

这次做的是开发过程这一半：规则进仓库、检查可由助手直接运行、常做的事有 Skill。产品这一半还没有动，方向建议如下，按投入从小到大：

1. **一句话录入。** 成员写“摘要评测卡在人工评分样本，等数据组这周给 300 条”，由模型拆成状态、阻塞原因、需要的支持、下一步，成员只确认。这是解决“字段太多”的根本办法：字段留给系统，不留给人。`server/ai-service.ts` 和导入解析已经有基础。
2. **页面只给结论。** 概览页不列六个指标让人自己读，直接给出“本周 3 件事需要你处理”，每条带原因和一键操作。“待我处理”已经是这个方向，应当成为首页主体。
3. **规则由系统执行，不由页面解释。** 截止时间、审核范围、统计口径这些规则，系统照着做，只在与某人有关时提醒那个人，不写在每个人每次都看到的页面上。

三条都应先在一个页面上试，用上面的任务走查方式验证，再推广。
