# 钉钉通知详情与原安排确认：实施验收

日期：2026-09-20。范围：用户确认的“本轮通知详情与确认链路”。本地实现、自动化测试和隔离浏览器验收已完成；尚未发布生产、未发送真实钉钉消息。

## 已实现的使用流程

1. 管理者正常下达或修改已生效安排，系统生成通知，正文展示事项名称、本人相关要求、负责人、已有截止日期与允许查看的变更。周安排优先展示本周承诺。临时目标结果可展示本人获准查看的退回意见。
2. 成员从通知进入对应详情。催确认通知关联原安排，确认在原安排中完成；已处理的提醒仍可打开有权访问的原安排，但不再要求重复确认。
3. 批量通知逐项区分待本人确认、已确认、已有新安排和仅协作查看。确认只处理当前待确认义务，不更改任务进度、完成状态或正式周提报。
4. 确认携带当前要求及义务版本。打开页面后要求被修改，服务端返回 409；页面重新读取要求，用户核对后重新点击确认，不自动代为确认。
5. 管理者可在通知设置及事项通知状态中预览接收人内容。点击“提醒本人确认”先显示预览，再由管理者发送。预览本身不产生通知、不占提醒额度、不记录成员已查看。
6. 手机窄屏选中消息后优先显示详情，并提供“返回消息列表”；桌面保留列表与详情并排。

## 内容、权限与投递

- 任务、周工作、月目标、临时目标审核、现有周提报提醒/截止汇总使用共用内容投影。已提交或已豁免的旧周提醒展示当前状态，不再声称待提交。
- 当前对象与字段权限均生效，合并/承接目标沿用原有字段裁剪。历史变更保存前后字段的成员可见性；无法证明可见的历史原值不显示，管理者降权后也不能继续读取此前超出成员范围的原值。
- 五分钟内尚未受理的同类变更，合并最早原值到最新新值；恢复原值的字段不显示假变更。批量事项按优先级、期限、稳定标识排序。
- 共用渲染器保留完整同源 HTTPS 详情入口，处理中文、emoji、Markdown 特殊字符与超长正文。最终 action_card 消息 JSON 满足项目的 2048 UTF-8 字节预算；最多先列 3 项，并说明其余可见数量。
- 在发送请求前，事务持久化最终正文、按钮、入口、载荷和哈希。外部已受理或结果未知的投递不会因正文更新而重发。快照不进入成员接口或业务导出。
- 模板升级不补发历史消息；旧通知安全展示当前可访问内容并注明历史信息不完整。草稿、历史导入保持静默；修复了管理员导入成员周草稿时，底层新建任务提前生成通知的问题，后续显式发布周安排仍正常通知。

## 配置与发布说明

`.env.example` 和 `deploy/production.env.example` 已增加 `DINGTALK_NOTIFICATION_CONTENT_MODE`：

| 值 | 行为 |
| --- | --- |
| `summary`（默认） | 钉钉显示接收人有权查看的结构化摘要及具体动作 |
| `minimal` | 钉钉仅显示通用提醒和入口，站内仍显示获准查看的详情 |

本轮不需要新的钉钉权限、回调地址或依赖包，也不自动改变服务端外发开关、管理员外发设置、试点成员或既有绑定。新字段可空；新增投递内容集合由现有 Store 保存，无需执行批量历史迁移。

发布时需同时更新后端与前端，保留现有生产环境秘密、数据库、部署标识和通知设置。当前工作区包含此前尚未提交的运行依赖，不能只用旧 Git HEAD 或只复制本次新增文件覆盖服务器；应按现有发布流程核对完整待发布源码并备份。已有前端缓存收到确认冲突时应刷新到新版本。

内容回退可设置 `DINGTALK_NOTIFICATION_CONTENT_MODE=minimal` 并按现有部署方式重启/重新创建服务加载环境；这只减少后续通知正文，不删除站内详情、确认历史或已发送快照。如需暂停后续外发，沿用现有总开关或通知设置，不重放旧队列。

发布后的剩余实机验收：在获准试点范围内，使用真实钉钉手机端和 PC 端核对卡片排版、入口承载、登录回跳及原安排确认。本轮没有执行生产发布或真实外发，现有线上通知不会因本地代码修改而改变。
