# 页面加载性能优化（2026-09-26）

针对“页面要等一会儿才显示数据”的反馈，本轮在不改变任何业务结果和权限的前提下，缩短服务端读取时间并减少无效请求。

## 变更内容

### 前端：减少无效请求

- **周/月页面首次进入只发一次请求。** 过去页面外壳先用部分参数请求，子组件挂载后补齐参数又请求一次；第一次被浏览器取消，但同步执行的服务端仍会完整算完。现在两处共用 `src/period-query.ts` 生成同一查询串。
- **搜索框防抖 300ms。** 周、月、项目、成员、部门概览、进展与催办、目标负责人、导入候选和管理者接收人的搜索，过去每输入一个字就发一次服务端查询。现在停顿 300ms 后才查询；清空搜索立即生效。周/月页面在等待期间仍先在当前页内即时过滤。
- **入口页面代码与身份请求并行下载。** 确认系统已初始化后立即预取当前地址对应的页面代码，不再等 `/workspace` 返回才开始下载。
- **第三方库单独分包。** React、Arco 等第三方库放入独立的 `vendor` 包，应用入口包从 548 KB 降至 91 KB（gzip 32 KB）。库版本不变时 `vendor` 包文件名不变，浏览器按长期缓存保留；发布新版本后用户只需重新下载应用代码，不再重新下载整个 548 KB 入口包及全部样式。钉钉 SDK、Word 预览等仅按需加载的库保持按需加载。

### 服务端：查询走索引

存储版本升至 **6**，新增的均为派生索引，不改写任何业务数据：

| 索引 | 用途 |
| --- | --- |
| `weekly_active_week_owner` | 周页面按周读取，不再解析全部历史周记录 |
| `weekly_task` | 任务详情按任务读取周记录 |
| `plan_month` | 月页面按月读取目标 |
| `plan_event_before_month`、`plan_event_after_month` | 月页面历史可见目标只解析该月相关的审计记录 |
| `followup_open_task_owner` | 协作页和风险计算按任务查未回应催办 |
| `blocker_parent_owner` | 风险计算按任务查阻塞记录 |

数据库从未执行 `ANALYZE`，SQLite 在没有统计信息时可能选错索引，因此关键查询使用 `INDEXED BY` 固定执行计划。`tests/period-query-indexes.test.ts` 记录页面实际执行的 SQL 并检查执行计划，防止以后退化为全表扫描。

其他服务端改动：

- `Store` 缓存预编译语句。页面查询语句较长，过去每次调用重新编译的开销常大于执行本身。
- 任务历史改为从相关对象出发按索引查审计记录，不再逐条检查全部审计历史。
- 历史目标快照在解析发布记录前先做子串预筛；含需转义字符的编号跳过预筛，结果不变。
- 部门概览的字段投影每字段只做一次 JSON 路径查找；排序复用同一中文排序器；分组改为原地追加。

### 可观测性

- 每个 API 响应带 `Server-Timing` 头：`app;dur=<毫秒>, db;desc="sql=<语句数> rows=<解析行数>"`，可在浏览器开发者工具 Network → Timing 查看。
- 耗时达到 `SLOW_REQUEST_MS`（默认 500）的请求输出一行 `slow_request` 日志，只含请求编号、方法、路径模式（编号与日期替换为 `:id`）、状态码、耗时和读取量，不含查询参数或搜索词。
- 定时任务单轮超过 200ms 输出 `slow_scheduler_tick`，列出各步骤耗时，用于判断页面偶发卡顿是否由定时任务引起。

## 测量结果

`npm run perf` 合成数据（36 个月、15 名成员），同一台机器前后对比，p50：

| 角色 | 接口 | 优化前 | 优化后 |
| --- | --- | ---: | ---: |
| 管理者 | 任务详情 | 30.5 ms | 2.0 ms |
| 成员 | 任务详情 | 31.7 ms | 2.5 ms |
| 管理者 | 进展与催办 | 30.9 ms | 6.1 ms |
| 成员 | 进展与催办 | 108.6 ms | 31.4 ms |
| 管理者 | 周工作 | 6.2 ms | 1.4 ms |
| 管理者 | 月度目标 | 5.5 ms | 1.2 ms |
| 成员 | 月度目标 | 13.5 ms | 8.8 ms |
| 管理者 | 部门概览（全部历史） | 77.4 ms | 54.5 ms |

以上是单个请求的服务端耗时。由于服务端单线程依次处理请求，一个页面的多个请求、搜索时的每次输入和被取消的重复请求都会累加排队，减少请求数量对实际等待时间的改善通常大于表中数字。时间为参考值，性能门禁仍以语句数、解析量和响应体为准。

### 浏览器实测

`scripts/browser-smoke.mjs` 通过 Chrome 开发者协议在真实浏览器中检查。它会创建首个管理者账号，只能在全新的临时实例上运行。同一脚本分别在改动前（`main`）和改动后的生产构建上运行：

| 检查项 | 改动前 | 改动后 |
| --- | --- | --- |
| 进入周页面时的周数据请求 | 2 次（先缺参数，再补齐） | 1 次 |
| 搜索框输入 4 个字 | 4 次查询 | 1 次（停顿后） |
| 周页面代码下载时机 | `/api/workspace` 之后（第 6 个请求，工作空间为第 5 个） | `/api/workspace` 之前（第 7 个，工作空间为第 17 个） |

改动后月度目标、进展与催办、工作清单、报告、周期复盘、反馈页面均正常渲染，无未捕获异常或控制台错误。

## 发布与回退

1. 发布前按[部署手册](deployment.md)做整库备份。
2. 新版本首次启动时自动执行迁移 6 并建立索引，数据量越大耗时越长（部门级数据通常在秒级）。
3. **旧版本不能直接打开升级后的数据库**：旧程序检测到存储版本 6 会拒绝启动，以防降级损坏数据。回退有两种方式：
   - 恢复升级前的备份（会丢失升级后的写入）；或
   - 停止服务后执行以下语句，只移除本次新增的派生索引与版本记录，业务数据不受影响，再启动旧版本：

   ```sql
   DROP INDEX IF EXISTS weekly_active_week_owner;
   DROP INDEX IF EXISTS weekly_task;
   DROP INDEX IF EXISTS plan_month;
   DROP INDEX IF EXISTS plan_event_before_month;
   DROP INDEX IF EXISTS plan_event_after_month;
   DROP INDEX IF EXISTS followup_open_task_owner;
   DROP INDEX IF EXISTS blocker_parent_owner;
   DELETE FROM schema_migrations WHERE version = 6;
   ```

## 尚未处理

- 定时任务、通知 worker 与 HTTP 请求仍共用一个线程。要真正分离，需要先让只读请求不再以 `BEGIN IMMEDIATE` 占用写锁，否则拆到独立线程后读请求仍会等待定时任务的写事务。已记入架构改进批次；上线后可先根据 `slow_scheduler_tick` 日志判断定时任务是否确实造成卡顿。
- 部门概览默认读取全部历史，其耗时仍随历史线性增长；后续可考虑默认“本月”或按月预聚合。
- 首次访问（无缓存）仍需下载约 556 KB JavaScript（gzip 约 170 KB），其中大部分是 React 与 Arco；进一步缩减属于组件与样式收敛批次。
