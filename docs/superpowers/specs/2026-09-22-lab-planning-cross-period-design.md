# 第三批：跨期流程、历史复盘与查询保障设计

日期：2026-09-22；状态：第三批开发与本地验收完成，尚未部署生产。范围：LP-08、11、18、20及配套 LP-19。
依赖[第一批](2026-09-22-lab-planning-consistency-design.md)承接合同及[第二批](2026-09-22-lab-planning-delivery-management-design.md)权限、进展和交付事实。LP-18 基线测量、LP-20 资料核对可提前开展。

## 1. LP-08 跨期处理向导

### 1.1 页面流程

月度目标详情提供“跨期处理”，顺序为：

1. **核对来源**：显示原目标、成果验收结论、已完成部分、剩余工作、参与任务和已有承接目标。
2. **建立承接目标**：选择同来源同目标月的既有承接目标，或明确新建/拆分；沿用第一批字段白名单和幂等合同。
3. **等待发布**：显示草稿、待审核、退回、已批准待发布等真实状态，链接原审核发布入口。通过审核但未发布仍不能关联任务。
4. **预览影响**：选择持续执行的原任务与目标周；逐条展示将重关联的任务、将调整的周草稿、保持不变的历史记录、已存在的目标周安排。
5. **确认关联与排周**：一个提交完成选中任务重关联、符合条件草稿归属调整和目标周安排。完成页显示沿用的任务编号及全部结果。

原任务持续执行时不复制任务。目标拆分仍可由多个承接目标表达，但同一个任务只有一个当前月目标，不能同时挂多个承接目标；确需把任务本身拆成多项时退出本向导，进入明确的新任务创建流程，不在后台自动克隆。

### 1.2 可恢复操作模型

新增内部 `CarryWorkflow`：`id、actorId、sourcePlanId、sourceVersionAtStart、targetMonth、targetPlanId、remainingWork、selectedTaskIds、targetWeek、status、version、stepReceipts、createdAt、updatedAt`。

status 为 preparing / awaiting_publication / ready / completed / cancelled。等待状态由服务端结合目标实时状态解释；不能仅依据客户端步骤序号继续。退回时仍停在等待步骤，并展示退回原因。管理者可查看和接续部门流程，接续操作记录当前操作者，不覆盖原创建人。

流程只保存选择、结果引用与回执，任务和目标仍是唯一业务事实源。取消流程停止后续编排，不撤销已有审核、发布或已完成的业务写入；已创建草稿保留并在取消确认中说明。不能通过取消流程删除历史。

接口建议：

| 接口 | 合同 |
| --- | --- |
| POST /api/carry-workflows/preview | 纯读，返回来源、候选目标、任务/周记录版本清单及影响，不产生草稿或额度 |
| POST /api/carry-workflows | requestId、sourceVersion、目标月份及选择；原子建立流程与承接草稿，或引用经验证的既有目标 |
| GET /api/carry-workflows/:id | 恢复流程，结合当前目标/任务计算可继续动作 |
| POST /api/carry-workflows/:id/preview-apply | 生成最后一步的完整 manifest 和规范内容指纹 |
| POST /api/carry-workflows/:id/apply | requestId、workflowVersion、manifest、选择和原因；原子完成关联与排周 |
| POST /api/carry-workflows/:id/cancel | 当前版本、requestId 和原因；只取消流程 |

预览指纹不是授权凭证。apply 在同步事务中重新读取目标、任务、周记录及曾提交记录集合，重算完整清单与指纹，任何新增/删除/版本变化均要求重新预览。任务重关联与排周复用现有服务和嵌套事务；任一任务失败整批回滚，避免页面显示“完成”但一半任务未排周。已成功的同 requestId 返回回执。

月度审核和发布可能跨人、跨天，不与最终 apply 放在一个长事务里。等待期间源内容变化，继续时展示差异并重新确认最新预览，不用旧输入默默覆盖。

### 1.3 历史与有效性边界

- `relinkTask()` 只调整**未删除、从未正式提交、与新目标月份相交**的周草稿。已经提交后撤回的记录仍属于历史，不重新归属。
- 月份相交按周一到周日判断，跨月交界周允许与相交月份关联。
- 目标周已有有效安排时展示并复用；不调用 carry 重复创建，不覆盖原承诺。已有安排归属不一致时必须在预览中解决，否则拒绝整批。
- 被删除周记录不能直接作为执行来源，已作废任务不能重关联或排周；原未完成且活跃任务可继续。
- 原月份成果、月发布快照、已提交周记录、周审核决定及定稿报告不修改。
- 不在业务包中迁移运行中向导；整库备份保留它。业务恢复后旧操作 epoch 失效，用户从现存对象重新核对。

## 2. LP-11 当前管理与历史周期复盘

### 2.1 两种模式

保留现有“当前管理”默认视图，用今天和当前截止日期判断现状。增加“历史周期复盘”只读模式，明确显示周期、期末 cutoffAt、生成时间 generatedAt、口径版本和证据覆盖率。导出沿用相同口径标签，不能将当前管理指标换个标题当成历史绩效。

历史范围按期末时点的责任与承诺筛选，使用当时的 owner/项目/月目标关系；不能按今天的责任人或当前关联回推。无历史依据的归属显示待核实。原已保存报告仍保持原快照，即使该报告在周期结束后才生成，也不宣称它等于期末快照。

### 2.2 事实来源与新增对象

新增 `TaskCommitmentEvent`，在基础业务写入路径记录期限、责任、交付范围的变更，包含 `taskId、kind、oldValue、newValue、effectiveAt、recordedAt、actorId、reason、sourceType、sourceId、sourceVersion`。首次有效承诺也记录；改期、延期批准、任务转派等必须覆盖，不能只接延期申请接口。管理者直接改截止日期也留下明确依据与生效时间。

新增 `PeriodReviewSnapshot`：`period、cutoffAt、generatedAt、ruleVersion、revision、status、sourceManifest、entries、unknownItems、evidenceCoverage`。每条 entry 保存 taskId、deliverableKey、期末责任、原承诺、各次批准变更、期末有效期限、提交/验收事实、逾期区间和来源引用。

新事实完整记录；旧数据优先采用正式回执、发布快照和可验证字段审计重建。无法覆盖某段历史时记录未知区间，不从当前 dueDate、updatedAt 或报告生成时间补造事实。人工补证采用单独的历史佐证记录，包含声称发生时间、录入时间和证据，显示为补证，不能成为原系统正式提交回执。

### 2.3 截止与计量规则

同时保留原承诺日期、每次改期批准时间、新期限、首次有效提交时间、最终通过版本的提交时间和验收时间。事后延期仅影响批准后的有效承诺，不删除批准前已经发生的逾期区间。

例如：9 月 10 日期限，9 月 12 日才批准延至 15 日，9 月 14 日提交，9 月 18 日验收。当前视图可显示 15 日新期限；历史保留 11 日零点起至 12 日批准之间的逾期事实，同时展示 14 日提交符合后续新期限，18 日验收不作为成员提交时间。

| 指标 | 规则 |
| --- | --- |
| 提交及时性 | 各版本 submittedAt 与当时有效承诺比较；首次、最终通过版本分别展示 |
| 按时达标交付 | 依据已通过版本的 submittedAt 及适用期限；没有通过结论时显示待确认 |
| 验收等待 | 决定时间减所验收版本提交时间，与成员迟交分开 |
| 历史逾期 | 按有效期限时间线和当时履约事实计算各区间，后续更正另留记录 |
| 周提报合规 | 继续使用现有整份回执、截止未交事实，不从任务完成状态推导 |
| 比率 | 未知项不进入已知事实分母，同时显示覆盖数、未知数和未完成数；分母为 0 显示“暂无可判定数据” |

期末尚待验收、期后才通过的成果在期末快照中保持“待验收”；如需期后结果复盘，新增带 laterEvidenceThrough 的修订，明确区分“期末已知”和“事后核实”。修订不能覆盖原定稿，不把事后知识伪装成当时已知。

### 2.4 冻结与接口

`POST /api/period-reviews/preview` 返回可解释草稿，`POST /api/period-reviews` 以 requestId 和来源 manifest 冻结草稿，`POST /api/period-reviews/:id/finalize` 使用当前版本与内容哈希定稿。补证或规则变化新建 revision，关联前版并展示差异。

管理者创建和定稿；成员在交付档案中只能看本人的投影；observer 的任务授权不包括部门复盘与分数。定稿后任务修改、延期和后验收不能修改其字节内容。冻结不代表永久授权，在线访问仍按当前权限。

## 3. LP-18 先测量，再拆读取

现状：`Domain.bootstrap():58` 读取多种全量集合，历史回补还在周记录循环内重复读取 events；`Store.list()` 读取完整 JSON 集合。通知投递已有参数化分页和索引，是可复用的实现模式。

### 3.1 测量方案

在隔离测试库构造小/中/大三组数据，例如 1 千、1 万、10 万历史周记录，活跃任务数量固定，另加缺任务快照回补和大报告正文场景。记录用户角色、数据规模、响应字节、p50/p95、SQL 次数、返回/解析行数、内存和运行机器配置。测试请求先热身；比较优化前后相同构建模式与设备，不填造当前性能结论。

建议验收预算：初始化 shell 未压缩正文不超过 100 KiB；历史数据增加十倍而当前工作量不变时，shell 字节与查询次数不增长、p95 不超过基线两倍；日常列表只加载当前页，默认 50、最大 100。绝对耗时 SLO 在首次基线测量后写入验收记录，本提案不把未经测量的毫秒数当作生产承诺。

### 3.2 查询拆分

1. 先将历史审计一次查询、按对象分组，消除循环重复扫描；这是低风险的第一步。
2. 新增 `GET /api/workspace`，只返回登录身份、功能能力、可见范围版本、操作 epoch、必要设置和轻量计数。用户/项目候选通过有权限的搜索接口按需取，不塞入全部历史字典。
3. 建立任务、周记录、月目标、历史、报告的独立查询。页面用范围、状态、owner、时间、includeCancelled 等参数表达需求；普通当前列表默认排除作废对象。
4. 报告列表仅返回元数据，打开详情/预览/导出时再取正文和快照。任务详情的进展及审计使用稳定游标。
5. 汇总指标使用同一授权与筛选谓词单独聚合，不能对当前页做总计。“跨期未完成”不受所选月创建日期限制，按活跃未结任务筛选。

引入固定集合和字段白名单的 Store 查询方法，不把任意字段/SQL 交给客户端。根据实际查询计划增加 entities 上的表达式/部分索引，候选为任务 owner/status/cancellation、周记录 taskId/weekStart/deletion、事件 entityType/entityId/createdAt、报告 type/period。实施前用 EXPLAIN QUERY PLAN 验证，避免对所有 JSON 字段建索引。

页内计数和列表在同一读取快照中形成。游标绑定查询、身份和权限版本，排序需带 ID；使用稳定排序字段，例如 createdAt＋id，展示更新时间不强制以可变字段翻页。跨页期间业务变化用“数据已更新，刷新查看”提示；授权改变游标失效并重查，不能缓存旧权限结果。

旧 bootstrap 保留兼容，逐页迁移后再收缩；新旧路径权限与统计结果须契约对比。客户端切换采用第一批读取序号保护，不因拆接口重新引入乱序。维持 SQLite 单实例，不因全量扫描问题直接换数据库或拆服务。

## 4. LP-20 功能状态与真实验收

建立单一发布状态来源 `docs/feature-status.md`，README 只展示摘要并链接此处；历史发布文档保留当时事实。运行设置页显示实际配置与开关，不让文档布尔值控制运行行为。

每项记录：功能 ID、能力范围、实现 commit、部署环境/版本/时间、启用范围/开关/观察时间、实机验收时间/执行人/证据链接、未验证边界。采用四个独立维度：**已实现、已部署、已启用、已实机验收**，不用一个“已上线”掩盖差异；不知道时填“未核实”。

钉钉至少分开记录普通工作通知、免登/身份绑定、原生待办、互动卡片、机器人/Stream，各自验收以下边界：本人身份、授权入口、真实回执、重复回调、未知结果、停用/撤权。正式汇报发送需要明确接收人和确认稿；本设计阶段不执行任何真实外发。

备份分开记录在线备份、异机副本、独立密钥、隔离恢复；恢复验收需启动独立实例、核对账号/对象/历史/报告与附件，记录实际恢复点和恢复时长。备份文件存在或模拟测试通过不能勾选“真实恢复演练完成”。

针对 README 与专项协作说明的冲突，以对应部署证据和实际环境核验更新当前摘要；保留原记录日期与环境，不能简单删掉所有“未部署”字样来宣称全部能力已启用。

发布步骤：完成自动化与隔离浏览器验收 → 记录兼容版本与完整备份 → 部署 → 核查数据和当前开关 → 经授权开展真实试点 → 填写证据。涉及存储升级时禁止回退到不识别新 schema 的旧程序；优先兼容修复或关闭新功能，不能用旧数据库覆盖新业务。克隆/灾备演练关闭外发并按现有规则更换部署标识。

## 5. LP-19 本批关键验收

| 类别 | 必过场景 |
| --- | --- |
| 跨期 | 中断/刷新后继续同一流程；批准未发布不能继续；同月目标已有安排不重复；一条冲突整批回滚；取消不删已建目标 |
| 历史 | 曾提交后撤回仍不改归属；原月成果和报告不变；事后延期保留先前逾期；晚验收不算迟交；无证据不填“按时” |
| 查询 | 多页与全量基准同口径；跨月未结不漏；授权统计不泄露；游标失效与乱序保护；十倍历史规模测试 |
| 发布 | 实现/部署/启用/实机证据独立；基础通知与原生能力分别核验；隔离真实恢复有执行记录和 RPO/RTO |

迁移验证同时覆盖新事实集合、旧 v1～v5 包、账号映射、冻结快照和存储升级失败回滚。真实企业验收尚未完成时如实保留待验收状态，不以 CI 替代。

实施与验收记录见[第三批验收](../../validation-2026-09-22-cross-period-review.md)，运行和发布状态见[功能状态台账](../../feature-status.md)。
