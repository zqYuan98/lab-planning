# 钉钉消息触达与工作入口设计

日期：2026-09-17。2026-09-18 更新公网部署决策与钉钉接入分工。适用项目：独立系统 `lab-planning`。

状态：设计已获用户同意，2026-09-18 已实施本地首期代码并进入验证。企业应用、正式公网部署与真实客户端联调尚待配置，未向真实成员发送消息。用户已确认：部门以钉钉为主，可以协调管理员创建企业内部应用；未来另选一台公网服务器，整套系统迁出37服务器，正式运行不依赖37。具体服务器、域名和上线时间尚未选择。实施与上线步骤见 `../plans/2026-09-18-dingtalk-notifications-access.md` 和 `../../dingtalk-public-server.md`。

## 1. 目标与建议

成员无需一直登录部门系统，也能及时知道新安排、变更和提报期限；点击钉钉消息后，进入对应事项并完成操作。管理者能区分消息发送情况、成员查看情况和业务处理情况。

建议首期建设：**钉钉企业内部 H5 应用 + 个人工作通知 + 工作台入口 + 身份绑定与免登 + 手机常用操作 + 站内消息记录**。任务、进展、提交回执仍由现有系统统一记录。

| 方案 | 成员体验 | 建设范围 | 结论 |
| --- | --- | --- | --- |
| 企业内部应用，通知与免登入口 | 个人收消息，点击直达事项，从工作台随时进入 | 身份映射、消息服务、深链接、手机适配 | 推荐首期，符合已确认的管理员配合条件 |
| 群通知与系统链接 | 群里看到提醒，进入后可能需要登录 | 群消息接入与链接；仍需解决访问网络 | 可作为公告补充，无法独立覆盖个人提醒和身份登录 |
| 内部应用加钉钉原生待办同步 | 在钉钉待办列表统一查看工作 | 额外处理创建、更新、关闭、事件同步和冲突 | 后续扩展，首期先打通通知到实际处理的闭环 |

工作通知用于告知和引导访问；需要出现在钉钉原生待办列表的事项，应另接待办能力。两者不能在产品中混称。依据：[钉钉工作通知](https://open.dingtalk.com/document/orgapp/asynchronous-sending-of-enterprise-session-messages)、[钉钉待办概述](https://open.dingtalk.com/document/orgapp/dingtalk-todo-task-overview)。

## 2. 当前系统基础与约束

- React + Express + SQLite，单部门、单实例。当前部署入口为 `http://192.168.0.37:4310`，参见 `docs/intranet-deployment.md`。
- 管理者已经可以给指定成员下发个人任务和周安排，来源由 `workOrigin` 区分成员自建、管理者下发、代录。不能把代录或历史导入都当成新下发。
- 月度目标存在草稿、提报、审核、发布过程；正式发布才触发任务下达通知。审核通过和发布分别表达。
- 单条周记录 `submitted` 表示纳入周统计；周五的整份“本周完成情况”和“下周计划”分别有正式回执，提醒必须调用 `WeeklySubmissionService` 的应交与回执判断。
- 目前导航由 `src/App.tsx` 内部状态与 `NavigationIntent` 控制，没有可供外部消息刷新后恢复的完整事项链接；首期需补充。
- `server/auth.ts` 已有服务端会话、账号启用检查、注册审批状态、角色权限和来源校验，免登应复用这些规则。
- `server/scheduler.ts` 已有30秒周期检查；`Store` 支持同步事务和持久数据。可增加独立通知工作器，首期无需引入 Redis、消息中间件或第二个业务服务。
- 当前未发现对外通知渠道或持久消息投递模块。已有集成 API 的访问令牌用于业务集成，不能作为成员免登链接凭证。

## 3. 成员和管理者的使用流程

### 3.1 新任务下达

1. 管理者选择责任成员，下发周安排；保存成功后，安排立即进入该成员现有“我的周计划”。
2. 同次业务提交记录一条站内通知及钉钉投递任务。页面显示“安排已保存，通知待发送”，消息失败不回滚任务。
3. 成员收到个人工作通知，看到事项标题、下发人、周期、截止时间和“查看安排”按钮。
4. 点击后进入钉钉内的系统页面；已绑定且有效的账号通过免登获得本系统会话，并直接定位该条安排。
5. 成员可以点击“确认接收”、填写进展、说明阻塞。确认接收只是表示知道这项安排；正式周提报继续按原流程核对并提交。
6. 管理者在原任务详情查看“平台发送结果 / 在系统中已查看 / 已确认接收”，并分别查看原有执行状态和周提报状态。

示例消息（演示数据）：

> **你有一项新的周安排**  
> 完成模型评测报告  
> 下发人：部门管理者  
> 周期：2026-09-14 至 2026-09-20  
> 截止：2026-09-18  
> 请查看安排，确认接收并补充执行进展。  
> **[查看安排]**

如果业务只设置截止日期，消息不虚构具体小时；周提报才明确显示北京时间周五16:00。

首期消息按钮统一打开页面，不通过链接直接执行“完成”“审批”或“提交”。打开页面和网页预览都不能产生业务确认回执。

### 3.2 工作台入口与手机页面

钉钉工作台增加“实验室工作空间”，打开“我的工作”，包含：新下发待确认、我的周计划、周提报、消息。普通浏览器仍使用现有登录入口。

手机优先支持：查看详情与变更、确认接收、填写进展/阻塞、核对并正式提交本周完成情况及下周计划。两份提报分别显示截止时间、当前状态、提交版本和回执时间；提交完成后留在回执页。已有草稿应能恢复，避免切换钉钉会话后丢失。

移动端采用事项列表和单栏详情，主要动作置于易触达位置。复杂合并、批量导入、部门报表编辑仍沿用桌面工作流。管理员收到审核提醒后可查看摘要并进入已有处理页；完整管理端移动重构不列入首期。

钉钉支持 H5 应用从 PC 和手机工作台访问，以及通过平台授权获取当前用户身份。依据：[官方 H5 免登示例](https://github.com/open-dingtalk/h5app-auth-demo)、[微应用免登授权码](https://open.dingtalk.com/tools/explorer/jsapi?id=11723)。

## 4. 首期通知范围与规则

所有规则使用 `Asia/Shanghai`。以下时间为推荐初始值，可由管理者调整；正式提报截止仍取业务规则，通知设置不能修改截止事实。

| 场景 | 接收人 | 触发条件和内容 | 处理入口 |
| --- | --- | --- | --- |
| 月度目标正式发布 | 当前负责人和参与人员 | 事务提交成功后通知；按同次发布、同一人汇总多个目标 | 定位目标；多项时进入对应列表 |
| 管理者下发个人任务或周安排 | 责任成员 | `workOrigin.kind=assigned`，操作者与责任人不同；同次新建任务及周记录只发一条 | 周安排优先，否则个人任务详情 |
| 已生效安排的重要变更 | 当前仍有权限的相关成员 | 截止日期、交付要求、月目标人员等实际变化；附简短变更摘要 | 最新事项详情 |
| 月目标撤销或成员被移出 | 原相关成员 | 仅在现有业务动作支持时告知“安排已变更/不再分配给你”，不继续展示私密详情 | 消息中心中的最小状态说明 |
| 临时月目标提报/退回/审核结果 | 有审核权限的管理者/提报人 | 管理者收待审核提醒；提报人收结果；审核通过文案不写成已发布 | 已有审核或提报页面 |
| 周提报截止前提醒 | 当前周期有应交项且尚未正式交齐的成员 | 默认周五09:00、15:00，仅列出仍需提交的那一份或两份 | 对应周期整份提报核对页 |
| 周提报截止后汇总 | 当前有效管理者 | 默认周五16:05，按业务核对结果汇总截止未交、当前仍欠交和补交情况 | 周提报管理筛选页 |

首期不自动推送每次保存、普通进展修改、成员自建任务、管理员代录、历史导入/恢复、自动报告草稿。月目标人员变更沿用既有权限和校验；通知功能不新增个人任务改派能力。普通任务截止催办、报告发布通知和每日摘要列入后续选配，避免首期覆盖过多场景。

补充规则：

- 草稿和未发布月目标不能向成员发送“已下达”。导入产生已发布记录也默认静默，管理员可以另行选择“通知相关成员”，显示人数和内容预览后执行。
- 批量发布按每人一条摘要发送；不同成员收到的事项集合按各自权限生成。个人任务和周安排同时创建时共享同一个业务动作编号。
- 频繁修改：同一人、同一事项5分钟内的未发送变更合并到最终状态；已发送消息不改写历史记录。初次下达可立即排队。
- 首期默认外部通知时段08:00—20:00（自然日），时段外延后到下一次08:00；站内记录立即生成。管理员可配置允许时段。首期不接入节假日历、不提供短信或电话加急。
- 发送前再检查账号、身份绑定、权限、对象状态和应交状态。已完成相应正式提报、已豁免、不属于当周应交名单、规则未生效或已失去权限的提醒取消。
- 周期 `needsReview` 为真时暂停个人催交，只在管理端提示先核对应交名单。下周计划用 `cycleWeek + kind=plan` 定位应交项，页面内容周取该应交项的 `contentWeek`，不能把两个周字段混用。
- 已有有效回执但 `changedSinceSubmission=true` 时，可在原09:00/15:00提醒中提示“内容已更新，请重新核对提交”，不称为“从未提交”，不改写原按时/迟交事实；没有待提交变化的有效回执才直接取消该项提醒。
- 09:00和15:00的催办可分别发送，但同一时点只有一条；两个时点之间补交后，后一次自动取消。催办文本带实际发送时点和当时待交事项，避免把同内容技术重试伪装成新提醒。
- 默认不因“未查看”重复催促；未确认安排在管理者页面中列出，管理员可手动提醒，须记录操作并遵守同事项、同人每天最多一次的手动提醒限制。
- 不推送“某某未交”的部门群名单。首期只做个人工作通知和管理者汇总。

## 5. 查看、接收和完成的定义

不使用一个“已读”字段概括全部状态，分别记录：

| 维度 | 状态/事实 | 数据来源 |
| --- | --- | --- |
| 消息投递 | 待发送、平台已受理、平台报告成功、失败、结果未知、已取消、未绑定 | 投递任务及平台结果 |
| 系统查看 | `openedAt` | 本人认证后成功加载详情，前端再调用已查看接口；列表预览不算 |
| 安排确认 | `acknowledgedAt` | 责任人点击确认接收，并通过服务端校验 |
| 业务进展 | 计划中、进行中、阻塞、完成等 | 原任务/周记录 |
| 正式提报 | 本周完成情况/下周计划各自的回执与版本 | 原周提报服务 |

首期需确认接收的范围：管理者下发的个人任务/周安排、正式发布月目标的负责人。月目标参与人员和一般结果通知只要求可查看。确认按“业务安排编号 + 实质变更版本 + 接收人”保存；重试和重复提醒不能生成新的确认要求，新的交付要求/截止变更则生成新一版。参与人员增减只让新增接收人产生新通知，其他人的确认不因无关人员变动失效。

平台已受理不能显示为送达；平台发送成功也不能视为本人看过或同意。钉钉发送结果接口的查询窗口有限，首期及时采集投递结果，但不依赖平台阅读状态作为业务证据。依据：[工作通知发送结果](https://open.dingtalk.com/document/orgapp/gets-the-result-of-sending-messages-asynchronously-to-the-enterprise)。

## 6. 账号绑定与免登

### 6.1 绑定

采用现有成员账号与钉钉身份的一对一映射，键为 `provider + corpId + userid`；`unionId` 可保存用于后续待办能力，但不凭姓名自动合并账号。

默认路径：成员首次从钉钉打开应用 → 服务端验证钉钉授权码并建立短时绑定流程 → 如无映射，要求登录现有系统账号 → 展示双方身份并明确点击“绑定”。只有审批通过且启用的系统账号可以完成绑定。绑定流程使用一次性随机挑战、短有效期、浏览器会话关联，验证后立即消费；客户端不能直接提交可信的用户编号。

未注册者继续走原有注册审批流程，审批通过后再绑定。重复绑定和一人多账号冲突阻止保存，交管理者核对。管理员可查看覆盖率、解绑和处理冲突；首期不设计按姓名批量自动绑定。

### 6.2 免登

H5 获取免登授权码 → 服务端用配置的企业应用凭证向钉钉验证身份 → 检查企业、绑定关系、账号启用/审批状态 → 复用现有会话创建机制 → 返回目标事项。

- 仅接受配置企业的身份；平台企业管理员身份不自动赋予本系统管理者权限。
- 企业应用密钥保存在服务端部署密钥/环境配置中。设置页只显示已配置状态、应用标识和验证结果；日志、链接、前端、业务导出均不携带密钥或访问令牌。
- 钉钉凭证缓存按官方有效期刷新，合并并发刷新；授权码只由服务端兑换，不写入日志或长期存储。
- 账号停用时，现有会话校验立即阻止访问并取消未发送通知；解绑/重绑时撤销相关会话，更新身份版本，待投递任务不得继续向旧钉钉身份发送。
- 首期不做全量通讯录同步。本系统停用是确定的访问控制入口；钉钉侧人员变化通过下一次身份验证、发送结果及管理员定期核对发现，不承诺瞬时同步。企业要求离职立即联动时，应在上线前另加入组织事件接入。
- H5 免登失败时展示可重试原因及普通账号登录入口，保留原目标地址。普通浏览器不冒充钉钉环境；扫码登录可后续扩展。
- 现有 Cookie 安全属性和来源检查继续生效；首期优先使用同源 H5 POST 兑换流程，真实验证 iOS、Android、PC 钉钉 WebView，不能靠全局放开跨域来解决兼容性。
- 当前生产 CSP 仅允许本站脚本，且禁止 iframe 嵌入。接入时优先将官方 JS SDK 随前端构建打包；确需外部资源时按实际依赖逐项增加精确来源。客户端优先使用独立 WebView；PC 如确需嵌入，应单独核对承载方式和安全头，不能直接把 `frame-ancestors` 改为通配。

依据：[钉钉免登流程](https://open.dingtalk.com/document/orgapp/logon-free-process)、[微应用授权码接口](https://open.dingtalk.com/tools/explorer/jsapi?id=11723)。

## 7. 深链接和网络访问

### 7.1 稳定链接

建议新增 `/entry?notificationId=<opaque-id>`，工作台首页使用 `/work`。通知编号只用于定位，不具有登录或授权能力。服务端校验通知归属和当前业务权限，再给出受控的 `NavigationIntent`；支持个人任务、周安排、月目标、周期提报和管理员汇总。

认证、绑定或重新登录后恢复原目标。刷新、返回和从历史消息再次进入都定位正确。若内容已改动，显示当前版本和必要的变更提示；已无权、已删除或已撤销的事项只展示最小状态及返回“我的工作”的入口。

转发消息不会转移权限。跳转目标仅允许本站明确列出的页面与参数，不接受任意 `returnUrl`。事项标题和业务正文不放在 URL 中。对已查看和确认接收使用独立的认证后 POST，不能用访问 GET 链接代替。

### 7.2 已选部署方向：独立公网服务器

2026-09-18 用户明确未来另选公网服务器，不继续部署到37。目标为前端、API、SQLite及常驻任务一并部署到新服务器，使用统一 HTTPS 域名；迁移现有数据后，日常运行不再调用37的接口或访问37的数据库。当前 `192.168.0.37` 仅作为迁移前现状，不是未来网络入口。

| 组成 | 配置 | 用途 |
| --- | --- | --- |
| 公网服务器 | 现有 Docker 应用单实例常驻，持久化 `/app/data` | 同时提供网页、API、数据库和后台任务 |
| 域名与 HTTPS 入口 | 实际域名解析到新入口，有效证书和反向代理 | 手机、PC和钉钉使用同一地址 |
| 服务端出站 | 能访问钉钉API以及配置的模型服务 | 消息发送、身份验证及可选AI处理 |
| 备份 | 独立于应用数据盘保存可恢复备份 | 不将37作为必需的备份或恢复节点 |

统一入口要同步配置 `APP_ORIGIN`、HTTPS Cookie、可信反向代理、钉钉应用首页/PC首页及实际使用能力要求的域名设置。应用4310端口保持在主机或容器内部，由HTTPS入口接入。公网部署仍需账号认证与原业务权限，不将部门数据作为匿名公开页面。实际采购、部署和迁移不属于本次设计修改。

以十几至几十人、低并发部门使用为前提，建议起配2核4GB、50–80GB SSD并监控附件增长；这是基于代码的估算，尚未压测。现有AI能力调用模型API，无需GPU。具体地域、域名及公司/手机网络的访问效果在选型和联调时核实。

首期使用服务端主动发送和查询结果，不要求为了通知额外开放平台事件回调地址。若之后使用原生待办或交互事件，再根据所选能力设计回调/事件订阅。

## 8. 系统页面变化

| 页面 | 增加内容 |
| --- | --- |
| 成员个人设置 | 钉钉绑定状态、企业、解绑入口、通知时段与可选消息偏好；管理要求的必需提醒由管理员统一配置并明确告知 |
| 成员管理 | 钉钉绑定覆盖率、未绑定名单、账号有效性；不把未绑定显示成成员已收到通知 |
| 消息中心 | 本人通知、待处理/全部筛选、未查看标记、点击回到事项；消息已查看和事项已完成分别显示 |
| 原任务/月目标详情 | 对允许查看的管理者展示通知情况和责任人确认情况；本人可确认接收 |
| 管理员“系统设置 → 钉钉接入” | 应用标识、密钥配置状态、规范访问域名、功能开关、试点成员范围、发送时段、连通检查 |
| 管理员“通知记录” | 按事件/成员/时间/结果筛选，失败原因、下次重试、取消和有记录的手动提醒 |

配置诊断与发送测试分开：诊断不发消息；“给我发送测试消息”只发送给当前管理者已绑定的身份。批量开启前展示生效成员和通知类型；开关默认关闭。

## 9. 实现边界与持久投递

### 9.1 模块责任

建议按以下小模块接入既有系统：

| 模块 | 责任 | 依赖 |
| --- | --- | --- |
| notification-events | 把明确的业务动作转换为通知事实；在业务事务内写入 | 计划/任务/审核服务、Store |
| notification-policy | 计算接收人、合并、发送时段、取消条件、周提报提醒 | 原业务可见性和周提报服务 |
| notification-worker | 持久队列领取、发送、结果查询、限流与重试 | Store、渠道适配器 |
| channels/dingtalk | 凭证缓存、工作通知请求、发送结果归一化 | 钉钉API、服务端密钥 |
| dingtalk-identity | 身份验证、绑定、解绑、创建现有会话 | 现有auth、账号策略 |
| notification-routes / entry | 消息查询、查看、确认、管理诊断、受控深链接 | 身份与业务权限 |

渠道接口只定义本期需要的发送、结果查询和身份解析能力；预留 `provider`，以后可增加飞书或企业微信适配器，不先做全平台配置系统。消息内容用固定模板生成，无需 AI。

### 9.2 数据设计

可沿用现有 SQLite `entities` 存储模式，以确定性ID提供唯一性；不新增一套“业务任务表”。

| 记录 | 主要字段/用途 |
| --- | --- |
| externalIdentities | provider、corpId、userid、可选unionId、localUserId、绑定状态/版本、验证时间、操作者 |
| notificationEvents | 业务动作ID、类型、对象ID、通知用实质版本、发生时间、来源、必要的最小快照 |
| notifications | eventId、recipientId、深链接目标、合并键、openedAt、acknowledgedAt、有效性及取消原因 |
| notificationDeliveries | notificationId、channel、身份版本、状态、attempts、nextAttemptAt、leaseUntil、平台taskId、结果与错误摘要 |
| notificationSettings | 开关、生效时间、试点成员、时区、时段、规则；仅存非秘密配置 |

业务事件ID在一次业务动作中确定并复用。通知唯一键由业务动作、接收人和通知类型确定；投递唯一键再增加渠道。定时提醒按“规则、周期、成员、提醒时点”去重，普通轮询不能重复创建。

当前周安排表单存在先创建 Task、再创建 WeeklyRecord 的两次请求。为让“一次下发只通知一次”有确定边界，首期增加统一的周安排服务入口：在同一事务内创建/关联个人任务、创建周记录及产生一条下发事件，表单改为调用该入口；请求带调用方生成的幂等键，服务端按操作者、请求内容和该键校验重放，相同键不同内容返回冲突。原有单独下发个人任务入口仍生成个人任务通知；以后为该任务另安排一周属于新的安排。不能凭两条记录相邻时间或相同标题猜测它们是否同一次下发。

消息摘要来自面向接收人的业务可见性投影，不直接复制审计事件的完整 before/after、合并来源或整月发布快照。个人任务关联尚未发布的月目标时，只展示该成员本就可见的任务字段，不借通知披露未发布目标内容。

新增记录纳入整库备份。身份映射、投递队列和平台结果不进入现有业务JSON迁移包；恢复业务资料不重放通知。整库恢复或克隆实例时默认关闭外发，检查未决投递与实际业务状态后显式启用，防止备份中的旧队列再次发出。

### 9.3 发送与失败恢复

1. **事务内记录，事务外发送。** 业务写入、站内通知与投递任务在同一个同步事务提交；回滚时一并消失。网络调用不进入 `Store.transaction`。
2. 工作器每次只领取一小批任务，原子写入处理租约；成功、失败与平台ID持久化。重启后恢复租约过期的任务，并按是否已有平台ID选择查结果或处理不确定状态。
3. 默认一人一条个性化请求，批量月目标按人汇总。明确用户ID，不使用全企业或整个部门广播参数；小部门规模优先可靠追踪。
4. 取得平台taskId后先记“平台已受理”，在约30秒、2分钟、10分钟、1小时以及查询窗口结束前进行有限次数结果核对。仅在平台明确返回对应成员成功时显示“平台报告成功”；窗口结束仍不明确则“结果未知”，不假定成功或失败。
5. 钉钉当前结果接口仅可查询24小时内的发送任务，接收人数超过100还有查询限制。因此本方案按人投递并及时保存核对结果；实际额度和频率在租户联调时核实，不写死套餐价格。依据：[官方发送结果说明](https://open.dingtalk.com/document/orgapp/gets-the-result-of-sending-messages-asynchronously-to-the-enterprise)。
6. 对明确未被受理的临时错误、平台可重试失败按1、5、15、60分钟退避，加入抖动，遵守渠道限流；最多5次发送尝试。无权限、无效身份等配置问题停止重试，给管理员显示处理原因。更新身份后只对仍有效事项生成重投，不向旧映射发送。
7. 请求超时且不确定平台是否已受理，或进程在发送后落库前崩溃时，可能无法获得taskId。此时标“结果未知”，不无限自动重发；管理员核对后可手动补发并记录原因。本系统能防止本地重复入队，但不承诺跨平台严格只发送一次。
8. 周催办最迟在该周期截止前有效。恢复服务时只考虑最新仍适用的提醒时点，已错过09:00且到了15:00不连续补发两条；过截止不补发截止前提醒。16:05管理汇总可在当日恢复后补发一次，超过当日则在站内提示管理员查看历史。新下达/变更积压默认最多保留7天，发送前核对并折叠为当前有效安排，超过窗口只保留站内记录和管理异常提示。
9. 外发关闭不影响任务保存、站内通知、登录或周提报；开启时记录生效时间，不追溯广播旧业务。暂时关闭后的重新开启只处理管理员预览确认过的仍有效积压。

失败不能被当作成员未执行的证据。系统页面分别展示“未绑定/发送失败”“平台报告成功”“系统未查看/已查看”和“未确认/已确认”；只有存在本人 `openedAt` 时才可显示“系统已查看但未确认”，平台成功不推导为本人已经收到或阅读。

## 10. 分期与上线依赖

**首期：完成一次完整工作闭环。** 身份绑定与免登、任务/月目标发布通知、关键变更和审核结果、周五催办及管理员汇总、消息中心、确认接收、深链接、手机常用流程、持久投递与诊断。

**后续按需要扩展。** 钉钉原生待办、组织人员变动同步、普通任务截止提醒、每天摘要、邮件备用渠道、飞书/企业微信。原生待办接入前必须约定外部完成的业务含义：不能让钉钉勾选完成直接代替本系统正式周提报、月成果验收或审批。

实施前需落实：

1. 企业管理员创建内部 H5 应用，提供必要应用标识，将可见范围设为试点成员并授予实际使用的最小权限；密钥通过服务端部署配置交付。
2. 运维选定新公网服务器和统一 HTTPS 域名，将整套系统及数据迁入新环境，验证服务器出站访问钉钉、手机和PC入站访问应用两个方向；新环境不得依赖37内网地址。
3. 选少量成员完成真实身份绑定，核对角色、停用/解绑和转发链接的行为。
4. 默认外发关闭，先测管理员本人，再对试点成员启用。验证成功后由管理者扩展生效范围，保留一键暂停渠道外发的开关。

公网服务器部署方向已经确认，具体主机和域名待选。钉钉接入开发可先以模拟渠道和测试环境开展；正式消息链接及外出访问验收必须使用最终可达的HTTPS入口，不能以“消息发送成功”代替访问验证。

## 11. 验收标准

- 成员退出本系统后，管理者下发任务；在正常平台和网络条件下，工作器60秒内发起首次投递（允许发送时段内），成员能从个人钉钉消息进入正确事项。此目标不承诺手机系统一定弹出推送。
- 第一次进入完成账号绑定，后续有效绑定能够免登；普通成员不能变成管理者，未审批/停用账号不能借免登绕过规则。
- 手机和PC分别验证工作台进入、消息进入、刷新、登录过期后的原目标恢复；外出访问须使用真实外部网络验证。
- 确认接收不改变任务执行状态、周记录纳入状态、整份提报回执或成果验收状态。
- 周五09:00提示欠交两份；成员只交一份后15:00只提示另一份；全部正式提交/豁免后不再催办。16:00整点提交仍按原业务逻辑记为逾期。
- 周中加入、暂停/恢复规则、管理员有原因代提交、补交和修改后重新提交，均按原应交名单与回执规则决定提醒，不自建第二套统计口径。
- 批量发布按人汇总；同次创建任务及周记录不重复通知；纯保存、代录、导入和恢复不群发历史数据。
- 钉钉限流、无效身份、查询结果窗口过期、断网、发送中重启、事务回滚分别有对应结果；不会因发送失败使业务写入丢失，也不会把不确定结果标为成功。
- 消息转发、修改通知编号、人员移出目标、解绑及账号停用后，均不能获取无权数据；旧消息不泄露当前私密内容。
- 通知详情、日志和导出不泄露凭证；测试发送只到操作管理员本人；新启用和整库恢复不突然发送历史积压。
- 关闭钉钉外发后，现有任务、计划、登录、周提报和报表继续正常工作。

验证分为规则与权限测试、故障恢复测试、真实钉钉试点验证；正式平台可见范围、企业接口权限、额度以及WebView表现以该企业实际联调结果为准。

## 12. 钉钉接入分工与落地顺序

接入完成后的角色关系：公网服务器保存和处理部门业务；钉钉提供个人消息、工作台入口和可验证的用户身份。成员从钉钉打开的是本系统的H5页面，无需另开发和安装原生手机应用。

### 12.1 一次性准备

| 负责人 | 准备或配置 | 完成标志 |
| --- | --- | --- |
| 用户/运维 | 公网服务器、可使用的域名、HTTPS证书、持久存储及备份位置 | 普通浏览器能通过规范域名使用系统，手机外部网络可达 |
| 企业钉钉管理员或获授权开发者 | 创建企业内部H5应用，命名“实验室工作空间”，配置图标 | 取得企业与应用标识，能够维护应用设置 |
| 企业钉钉管理员 | 设置手机/PC首页、按实际能力配置域名、核对免登/身份读取/工作通知所需权限，先限定可见试点成员 | 试点成员能够在工作台看到并打开应用 |
| 运维/开发 | 服务端配置 CorpId、Client ID（AppKey）、Client Secret（AppSecret）、AgentId；名称以实际控制台为准 | 后端可取得应用凭证并核验企业身份，密钥不进入前端、仓库或普通日志 |
| 开发 | 身份绑定与免登、通知队列和模板、业务触发点、深链接、手机常用流程、通知诊断 | 通过模拟测试和真实试点验收 |
| 试点成员 | 已获批准的系统账号与本人钉钉身份完成首次绑定 | 系统用户与企业内钉钉 userid 一对一对应 |

上述配置分工不表示需要开启全部通讯录或其他无关接口权限。平台默认已有的能力只需核验；实际新增权限限于所选接口。应用发布只针对配置的企业可见范围，不包含上架面向外部企业的应用市场。

### 12.2 两条接入链路

**通知链路：** 管理者下发/发布 → 本系统事务保存业务及投递记录 → 后端使用应用凭证向绑定的钉钉 userid 发送个人工作通知 → 保存平台异步任务ID并查询结果。消息携带标题、必要摘要和受控事项链接，原始业务资料仍在本系统中。

**访问链路：** 成员点击消息或工作台 → 打开公网系统H5页面 → H5取得钉钉授权码 → 本系统后端兑换并核验平台身份 → 查询现有账号绑定及有效性 → 创建本系统会话 → 打开指定事项。首次未绑定时按第6节完成现有账号登录和绑定，后续有效身份可免登。收到消息、进入页面、确认接收、完成业务仍是四类不同事实。

首期不要求建立群机器人，也不使用群内公开消息承载个人任务。工作通知是消息提醒；钉钉原生待办列表另属后续能力。此链路使用H5授权码与服务端主动发送/查询，无需为它专门建立钉钉事件订阅回调；后续组织同步或交互能力另行设计。

### 12.3 联调与发布顺序

1. 先完成开发与隔离环境验证，准备域名、应用和试点范围；完整接入方案不以采购服务器作为开始编写代码的前提。
2. 将系统部署到新公网服务器并准备或迁移账号，完成HTTPS访问验证，核对所有配置中不再依赖37。
3. 钉钉管理员配置应用访问地址和权限、向试点范围发布；管理员本人及2–3名成员完成身份绑定。
4. 验证“下发 → 收到工作通知 → 点击直达 → 确认接收 → 更新进展 → 正式周提报”，并验证未绑定、停用、无权限及重复发送情况。
5. 再开启真实定时提醒并扩展应用可见及通知生效范围。无需等待正式周五，可在隔离环境使用可控时间验证规则；生产环境不伪造提报日期或回执。

钉钉平台能力参考：[官方H5应用免登示例](https://github.com/open-dingtalk/h5app-auth-demo)、[微应用免登授权码](https://open.dingtalk.com/tools/explorer/jsapi?id=11723)、[发送工作通知](https://open.dingtalk.com/document/orgapp/asynchronous-sending-of-enterprise-session-messages)。
