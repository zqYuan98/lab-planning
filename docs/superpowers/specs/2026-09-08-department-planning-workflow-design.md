# 部门月度计划与周计划业务方案

日期：2026年9月8日  
状态：业务方案草案，已确定的需求与建议默认规则分别列出

本方案服务于部门项目和不同岗位的任务管理。成员先提报月计划，部门负责人审核、整理并发布，成员再拆分每周任务。系统以同一套计划和实际进展生成管理者周报、月报，减少重复填写。

## 用户已确定的需求

- 年度目标记录部门大方向，不强制分解到月，也不强制建立年度与月度关联。
- 月度与周度计划必须关联。
- 月计划由成员先提报，管理者审核、整理并发布，成员再拆分每周。
- 管理范围包括部门项目及不同岗位人员的任务。
- 月度计划允许修正调整。
- 支持自动生成管理者周报和月报。
- 后续开发可在用户 GitHub 创建独立仓库。

## 建议的主要流程

成员月计划草稿 → 提交审核 → 管理者审核整理 → 发布部门月计划 → 成员拆分周任务 → 填写实际进展 → 管理者确认月度成果 → 生成并确认汇报。

计划发布表示本月承诺已经确定；成果确认表示交付已经达到验收要求，两者分别处理。

### 成员提报月计划

每条提报填写所属项目或部门工作类别、本月预期成果、本人责任、建议截止日期、验收标准及所需协作。培训、申报、临时支持等工作可以归入部门工作类别，项目不是所有事项的必填项。

成员可以编辑自己的草稿，提交后进入待审核。管理者能看到已提交、退回待修改和未提交的成员。未提交只作为提报状态，不计作任务未完成。

### 管理者审核整理并发布

管理者可接受提报、退回并说明原因，或调整交付范围、优先级、负责人和日期。保留原始提报、修改内容和修改人，成员可以查看发布结果相对本人提报的变化。

默认按项目分组展示，不因项目相同就把不同交付物自动合并。如果多条提报确实描述同一成果，可合并为一项月计划，但保留来源提报及各人的交付责任。每项月计划明确一个主要负责人和协作者。

发布时保存部门月计划版本。正式周任务只能关联已发布且本人负责或参与的月计划项。任务拆分界面直接带出可选月计划、验收要求和期限，避免重复录入。

### 成员填写个人周计划与进展

一个月计划项可包含多个个人任务，一个个人任务可跨多个星期。任务保持稳定编号，每周分别记录承诺、实际成果、状态、证据、阻塞及下一步；周记录不覆盖此前的承诺和结果。

默认不再对每条周计划增加审批。成员提交后管理者即可查看，管理者主要处理资源冲突、阻塞和偏离月计划的事项。成员修改自己的实际进展无需重新审核月计划。

不同岗位使用统一的任务基础字段，按交付需要填写验收标准。例如算法任务可记录识别率及测试证据，测试任务可记录测试范围及结果，硬件任务可记录样机和评审材料。人天可用于辅助排期，允许小数和可配置的可用工作日，不要求所有工作都按整数五天分配。

成员自报周任务完成后，系统汇总相关进展；月计划最终是否完成，由管理者依据月度验收标准确认。周任务完成数与月度成果完成数分别统计。

## 变更与例外

| 情况 | 建议处理 |
| --- | --- |
| 发布后调整成果、负责人或截止日期 | 成员提出变更或管理者直接调整，管理者确认生效，保存修改前后值、原因和生效时间，生成新的计划版本 |
| 月计划未发布但要提前安排下周 | 允许保存周计划草稿；关联已发布月计划后才成为正式计划 |
| 临时工作必须立即开展 | 允许先记录临时工作及原因，明确标为待补关联；管理者之后归入已有月计划或发布新增项，不将其静默计入正式月计划达成率 |
| 同一任务连续跨周 | 每周新增承诺和实际记录，沿用任务编号；新一周的承诺状态初始化为未开始，不继承上一周完成状态 |
| 未完成事项跨月承接 | 成员在下月提报承接，管理者审核发布；保留上月承诺、实际结果、未完成原因及新旧月计划关系，任务成果不重复计数 |
| 项目结束或归档 | 停止新增正常计划，历史计划、任务、报告仍可查询 |

年度目标可以在汇报中独立引用其最新确认的进展，不根据月计划条数自动推算年度达成率。

## 最小业务对象

| 对象 | 保存的事实 |
| --- | --- |
| 月度提报及来源 | 成员原始建议、提交与退回记录、审核整理过程 |
| 已发布月计划及版本 | 当月承诺、责任、验收标准、发布版本和后续变更 |
| 个人任务 | 稳定任务编号、负责人及协作者、交付要求、关联月计划；跨月承接保留历史关系 |
| 周记录 | 所属周、关联个人任务及当期月计划、本周承诺、实际结果和证据 |
| 报告及版本 | 报告周期、引用的数据快照和计划版本、管理者修改、定稿内容和导出文件 |

项目和年度目标作为独立管理对象。项目帮助按业务汇总任务，年度目标提供方向性参考。

界面不要求成员分别维护上述每张数据表。成员主要使用“我的月计划”和“我的周计划”；管理者主要使用“月计划审核发布”“部门进展”和“报告中心”。

## 周报和月报生成

周报从全量当期记录生成月目标推进、本周成果、重点工作、风险协调和下周安排。选择重点展示的 TOP 项目不改变全量统计。未经过月度成果确认的进展标明为成员自报或进行中。

月报呈现原计划与调整后的承诺、确认成果、未完成原因、计划变更及下月安排。下月未发布时，下月安排标为待审核草案。年度目标作为独立章节引用。

数量和完成率由程序按明确口径计算；展示统计范围、截至时间和所用计划版本。没有分母时显示暂无统计口径。AI 只依据已有事实组织文字，并提示缺少证据、原因或下一步的条目；计划内容不能自动当作实际成果，交付物名称不能当作纠偏措施。

报告支持保存草稿、人工编辑、确认定稿及 Word 导出。生成时固定引用数据，后续源计划变化不自动改写已保存报告；重新生成形成新版本。仅修改汇报措辞不回写任务事实，事实纠正从原任务进入并形成记录。

自动生成采用可配置的周期和截止时间，生成待确认草稿；具体每周、每月生成时点及通知方式尚未确定。

## 开发安排建议

优先建立成员月度提报、审核发布、月周关联和实际进展这条流程，再接入报告生成、调整对比和归档。项目、账号权限、导入导出及报告模板等现有能力可评估后复用。

后续开发在独立 GitHub 仓库进行，建议默认私有。仓库所属账号、名称、技术选型和部署位置尚未确定。本方案不代表远程仓库已经创建，也不包含向 GitHub 上传现有公司仓库或附件的操作。

## 验收场景

1. 两名成员为同一项目提交不同交付，管理者分组发布后，个人责任和提报来源均可追溯。
2. 普通成员能提交自己的月计划，并从已发布、本人参与的事项建立周任务；不能修改他人的任务。
3. 月计划被退回时保留原因；未发布提报不能直接成为正式月计划统计数据。
4. 三个岗位共同参与同一月度成果，各自状态与证据独立；部分周任务完成不会自动将月成果标为已验收。
5. 发布后改期保留原日期、原因和新版本；历史报告仍能显示当时承诺。
6. 跨周、跨月承接保留历史，成果不重复累计，新周承诺不继承已完成状态。
7. 本周十项中三项完成，即使只展示这三项为重点，总量仍为十项、按对应口径的完成率仍为百分之三十。
8. 保存汇报编辑稿后刷新可以恢复，定稿后新增未来计划不改变旧报告。

## 待确认的建议默认规则

- 周计划提交后直接可见，不逐条增加管理者审批。
- 月计划未发布时可提前拟周计划草稿，正式执行以已发布关联为准；临时工作使用明确的例外入口。
- 月度成果由管理者确认，周进展由成员直接更新。
- 仓库默认私有；自动生成时点、通知方式及部署安排在开发前明确。
