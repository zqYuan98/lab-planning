# 钉钉工作通知：事项摘要与变更详情设计

2026-09-20，设计增补，待用户审阅。关联[总体方案](2026-09-19-dingtalk-collaboration-v2-design.md)、[P0](2026-09-19-dingtalk-foundation-design.md)、[P1](2026-09-19-progress-followup-design.md)、[P2](2026-09-19-dingtalk-native-actions-design.md)。本文件规定各阶段共用的通知内容规范；仅完善设计，尚未修改或上线通知模板。

## 1. 问题与目标

用户截图中的正文为“管理者提醒你查看尚待确认的工作安排。确认知悉不会改变执行或提报状态。”，按钮为“查看工作安排”。读者无法直接知道提醒涉及哪项工作、具体要求或期限。

这不只是钉钉页面折叠问题：当前 manual_reminder 在 server/notification-routes.ts 中生成固定正文；server/dingtalk.ts 的单按钮文字也是固定值。现有 work_assigned/work_changed 已带部分任务名、发起人及日期，但月目标发布、变更等仍缺具体要求或变化内容。不能把所有现有通知都描述为没有任何详情。

目标：成员在工作通知正文内，未经点击就能回答“哪件事、为什么提醒、要求是什么、何时截止、下一步做什么”。管理者能判断“谁的哪项工作、发生什么变化、是否需要处理”。完整要求、附件和操作保留在有权限的事项详情页。

## 2. 三种呈现方式

| 方式 | 收益与限制 | 选择 |
| --- | --- | --- |
| 事项摘要 + 明确行动 + 详情入口 | 大部分日常通知可直接判断轻重；复用现有工作通知，正文长度可控 | 推荐，P0 开始 |
| 全文、所有附件和全部历史直接放通知 | 信息完整，但容易超过消息预算、淹没关键动作，也扩大外部披露 | 不作默认 |
| 先接入高级互动卡片再补内容 | 展示与操作更丰富，但依赖租户能力及回调开发 | P2 沿用同一内容规范，不能成为 P0 的前置条件 |

采用确定性字段模板，不引入 AI 自动概括需求。正文节选必须可追溯到原字段，不能编造完成比例、审核意见、期限或成果。

## 3. 单事项信息结构

按以下顺序展示；每种事件只选相关字段，避免堆满全部数据。

1. **事件 + 事项名**：例如“待确认安排｜接口联调报告”。在正文首行重复关键标题，不依赖客户端是否展示消息 title 字段。
2. **归属**：负责人；必要时增加项目/月目标、所属周或月份，区分重名事项。提醒发起人单独标明，不将系统定时器写成人工管理者。
3. **事项内容**：最相关的工作要求、成果要求或当前变化，默认一至两条短句；截短时标记省略并保留详情入口。
4. **时间**：任务截止、催办回应期限或正式提报截止，必须带明确标签；确有多个独立期限时分别显示。
5. **当前所需动作**：确认安排、更新进度、核对变更、审核成果或正式提报。已办结事项不能继续显示待处理动作。
6. **一个主按钮**：准确描述进入后的主要动作。P0/P1 按钮均为跳转，点击本身不会确认、保存进度、验收或正式提交。

任务只有日期时显示“任务截止：2026-09-25”，不伪造 17:00 或把提醒发送时刻当期限。P1 的日期计算规则仍按 P1 文件执行。催办有小时期限则显示“回应期限：2026-09-22 17:00（北京时间）”。截止缺失且属于下达/临期相关信息时显示“截止日期未设置”；不存在的成果、原因等不补猜测。

### 示例一：替换截图中的催确认通知

以下均为虚构示例，不代表平台真实任务或已投递消息。

> 待确认安排｜接口联调报告\
> 负责人：张三 · 9 月 21 日—27 日周安排\
> 工作要求：完成接口联调，提交测试结果及异常清单。\
> 任务截止：2026-09-25\
> 李四提醒你确认是否已知悉以上安排。\
> 【查看并确认原安排】

“确认知悉不等于完成任务或正式提报”的解释保留在确认界面；卡片可在预算允许时用简短尾注展示，不能挤占事项内容。如果只存在任务而没有周记录，不添加虚构的所属周。

### 示例二：安排变更

> 安排有更新｜接口联调报告\
> 负责人：张三 · 变更人：李四\
> 截止日期：2026-09-25 → 2026-09-28\
> 交付要求：测试结果 → 测试结果及异常复现步骤\
> 变更原因：新增一组兼容性验证。\
> 请核对本次变化并确认知悉。\
> 【查看变更并确认】

仅当业务保存了该原因、原值及有效确认义务时，才展示相应内容。没有原值的历史消息不能生成猜测的差异；没有确认义务时，按钮改为“查看变更”，正文不要求确认。

## 4. 各类通知内容与入口

下表是目标模板清单，阶段表示业务事实可用时间。P0 只增强已有事件，不能为了套模板提前实现或伪造 P1/P2 业务。

| 类型 | 正文必须包含的相关内容 | 主按钮 | 阶段 |
| --- | --- | --- | --- |
| 新工作安排 | 事项名、负责人、任务/本周要求、已有截止、安排人；相关时注明周次 | 查看并确认安排 | P0 |
| 手动催确认 | 原安排名、本人相关要求、原安排当前截止、提醒人、仍待确认的动作 | 查看并确认原安排 | P0 |
| 工作要求变更 | 事项名、变更人、变更字段的原值 → 新值；有原因则展示；区分需确认或仅知会 | 查看变更并确认 / 查看变更 | P0 |
| 月目标发布 | 月份、本人角色、本人可见目标前几项的名称、成果要求、截止及总数 | 查看本月安排 | P0 |
| 月目标变更 | 目标名、分工/成果要求/截止/验收标准的有效变化，明确需执行的最新要求 | 查看目标变更 | P0 |
| 目标审核待办及结果 | 目标名、提报人、成果要求；结果包含真实决定及意见，批准未发布须明确 | 查看并审核 / 查看审核结果 | P0 现有临时目标；P1 扩展 |
| 周提报提醒 | 周期、真实待提交类型及数量、已有条目前几项名称、正式截止；已有未提报变化单独提示 | 核对并正式提交 | P0 |
| 催更新进度 | 任务名、负责人、主管此次要求、回应期限、发起人；有本人最近进展则附时间及短摘要 | 更新进度并回应 | P1A |
| 完成/受阻/解除/重新打开 | 人员、事项、状态变化、实际完成内容或阻塞原因/需支持；注明任务或本周层级 | 查看成果 / 查看并处理 | P1B |
| 临期/逾期/久未更新 | 事项名、真实截止或最近有效进展、提醒原因、下一步；按规则区分日期逾期与工作日升级 | 查看并更新进度 | P1B |
| 成果提交及验收结果 | 目标名、本人提交成果摘要、验收标准摘要；结果含真实状态及意见 | 查看并验收 / 查看验收结果 | P1B |
| 日/周摘要、正式提报管理回告 | 统计周期及截至时点、可见范围内数量、关键事项及变化、待处理入口 | 查看摘要 | P1B 最小摘要；P1C 完整摘要 |

原工作确认是否适用由现有通知义务服务确定，不能仅靠模板种类设置 actionable。默认只向当前规则确定的个人接收人发详情；本增补不扩大接收范围。

手动催确认只列原通知中当前仍待本人确认的义务，不能把所有仍可见 targets 都标成待确认。混合批量通知中的已确认、已替代或仅协作可见事项，从催确认清单和数量中剔除。participation_removed 等退出/移除通知继续用概括状态提示，不添加已撤权对象详情。

## 5. 内容来源与变更语义

复用已有事实：Task.title/description/ownerId/dueDate，WeeklyRecord.commitment/weekStart/actualOutcome/blocker/nextAction/status，MonthlyPlan.expectedOutcome/acceptanceCriteria 等。姓名通过当前授权可见的成员映射取得。周安排优先展示该周 commitment；必要时补任务 description，避免用长期任务要求替代本周承诺。月目标要求不能自动当作每位协作者的个人分工；若没有具体分工字段，展示“协作目标要求”。

首版不增加任务完成百分比、自动评分或要求全员补写新字段。内容确实为空时，在事项名、归属、真实时间之外显示“具体要求待补充”，详情页供有权者补充。

业务事件在事务中保存**最小字段差异**、事件时间、对象/义务版本及操作者；不复制完整业务对象。新差异按允许列表保存：任务标题/要求/负责人/截止、周承诺、月目标成果要求/验收标准/相关分工等。页面通用 updatedAt 不足以证明这些变化，保存无实质差异不创建变更通知。

变更顺序优先展示：负责人与截止、交付要求与验收标准、承诺/范围、标题等辅助信息；超过预算的字段显示“另有 N 项变更”。删除字段显示“已清空”，不要空白箭头。连续编辑在原设计允许的合并窗口内从首个旧值归并至最终新值；不得为 P0 新设隐性延迟。原值最终恢复时不展示不存在的净变化。负责人更换后，新接收人只看对其有效的新安排；旧接收人撤销待确认义务，不获得新负责人的个人工作详情。

所有差异字段都通过当前接收人的对象与字段权限检查。历史值可能包含其从未获准查看的信息：无法证明可见时仅展示“该字段已更新”及获准展示的当前值，不外发原值。P0 不要求建设全量历史权限系统。

## 6. 发送前检查、展示快照与兼容

流程：业务事实/最小差异 → 接收人权限投影 → 当前资格与义务校验 → 模板渲染与预算校验 → 受控投递 → 对应事项详情。继续使用现有持久队列，复用 P1 的 notification-projector 职责，不为内容增强新建独立消息服务。

当前 worker 会在临时目标后来发布、周提报发送时重算正文；这些路径也必须统一返回结构化事实后交同一 projector/renderer 处理，不能最后又覆盖成固定提示。周提报动态事实按发送时重新计算，并附截至时间；保存单条周记录不因此被算作整份正式提报。

建议为新通知增加可空的 contentSchemaVersion、templateKey、eventTime、subjectRefs 与最小 eventFacts；sourceNotificationId 沿用 P0。外发首次请求前保存 recipientId、对象/义务版本、renderedAt、模板版本、实际正文/按钮/完整入口及 payloadHash，作为受控可审计的投递内容记录。该记录不进入普通日志或可移植业务导出；复用投递记录或附属 entities，P0 即具备，不依赖 P2 的 DeliveryAttempt。保留与原通知审计策略一致，不引入无限期冗余副本。

发送前重新检查：绑定与账号有效、接收权限、原义务仍存在、截止与要求是否已变化、原通知是否已确认/替代、草稿是否正式发布。静默时段或暂停后恢复也执行此检查。过期的行动提醒跳过并记录原因；仍有意义的历史变化须注明事件时间与“当前已更新/已处理”，不能伪装为当前待办。最新内容超出当前通知的义务版本时，由原义务服务选择最新可访问版本或取消旧候选，不能只换正文却确认旧版本。

同一确定失败重试仍是同一逻辑投递，不增加通知或催办次数；重试前再次校验，若尚未被外部受理且内容需更新，记录新的发送尝试版本。accepted/unknown 不因正文更新再次发送，沿用原查询/核查流程。已经成功发出的普通工作通知视为历史快照，不能承诺随平台实时改字或可靠撤回；P2 可更新的卡片另行验收。

详情页以当前权限和业务事实为准。显示“通知发生于…；当前事项已更新”等必要提示，分开历史通知摘要与最新安排。旧字段缺失的历史通知仍可打开：能安全解析来源则展示当前授权事项并标明是当前内容；无法解析时，原文只有通过当前权限裁剪才能显示，否则使用通用状态提示及安全的个人消息入口，不能凭同名任务猜关联。升级模板不重发历史通知，也不批量补发现有截图中的旧消息。

## 7. 多事项合并与消息预算

合并沿用 P1 已定义的窗口、优先级和频率；P0 月目标发布及现有批量事件仅增强原有单条通知的内容，不擅自新增群发或改变业务触发频率。

同一接收人多事项默认最多显示前三项，实际数量由编码后预算决定。每项至少有事项名、本人相关要求/变化和相关截止；不要只发“你有 5 项工作”。注明“另有 N 项，查看全部”，总数与条目仅基于当前接收人可见范围。排序沿用业务风险优先级，其后按截止、事件时间、稳定 ID 排序。原通知需要逐项确认时，详情页保留各自义务和确认状态，不将汇总点击当作批量确认。

现有适配器对完整消息 JSON 采用 2,048 UTF-8 字节保守上限，并有 title/正文限额。这是本地实现约束，不作为已核实的所有钉钉消息类型统一额度。实施前核对选用接口的当前限制；总预算取已核实接口限制和本地保守预算中较小者，不能仅因中文内容放不下就取消校验。

先计算完整入口、按钮及 JSON 开销，再分配正文。压缩顺序：去掉重复身份/尾注 → 缩短要求和长差异 → 减少列表项 → 缩短长标题且保留辨识上下文。保留事项识别、提醒原因、相关期限与主动作；使用 Unicode 安全截断并标明省略。完整单按钮 URL 绝不截断，必要时使用服务端映射的短入口：短 ID 仅定位，不是授权凭据，解析后仍需登录和验权。最小合法消息仍放不下时记录确定的内容错误供管理诊断，站内详情继续可见。

静态模板负责有限 Markdown 结构；对每个业务文本片段转义，再组合模板。不能继续把整份富文本模板作为业务输入整体转义，也不能允许用户字段注入链接、图片、@全员或 HTML。正文中的外部 URL/附件凭据默认不透传，使用“证据：已附，进入查看”等摘要。当前单按钮适配器需接收受允许列表约束的 buttonText，不接受客户端任意操作地址。手机/桌面各端需实测换行、中文、特殊字符和按钮显示。

## 8. 可见范围与预览

私聊通知正文也是向外部平台披露数据，可能出现在推送预览或被截图转发。默认字段为任务名称、本人要求、角色、已有期限、必要变化与所需动作；不给普通通知附整份成果、证据地址、访问令牌、无权访问的其他成员个人进展或管理备注。指定且有权的管理者仍可按 P1 接收成员进展与成果的必要摘要。

补充字段若混在自由正文中不能靠敏感词自动可靠识别。提供部署级内容策略 `summary`（上述摘要）与 `minimal`（只显示最少事项提示及受控入口），默认按获批的摘要方案灰度；组织要求严格保密时选择 minimal。当前没有事项密级字段，P0 不假称已经支持按密级自动过滤，也不为此新增一套权限系统。权限收回后能阻止后续发送/访问，不能抹除已经送达的正文。

管理者下达、手动提醒及通知设置提供“接收人所见预览”：使用与发送完全相同的 projector、renderer 和预算，显示实际正文、按钮、截短提示、接收人数和预计发送时段。预览不发送、不标记查看、不消耗催办额度。批量逐接收人预览，不能用管理者完整视角生成所有人的卡片。发送时再次校验，预览不是对未来数据的冻结或绕权授权。

## 9. 分期与验收

**P0 本次优先加入**：现有通知结构化摘要；手动提醒关联原安排；已有变更的最小差异采集；明确单按钮；模板预算/安全转义；发送前权限及版本核验；预览与历史兼容。不依赖新进展模型、高级卡片或机器人。

**P1**：新催办、进展、阻塞、验收和摘要事件按本规范提供内容；沿用 P1 的路由、频率、主管摘要和独立业务状态。**P2**：将相同投影用于高级卡片/待办；展示更多信息与直接操作分别验收，不能重复增加一轮通知。

| 验收场景 | 必须看到的结果 |
| --- | --- |
| 截图同类催确认 | 正文能识别具体安排及已有要求/截止；点击到原安排，确认不影响执行/正式提报 |
| 重名任务、任务与周记录并存 | 可区分归属，周承诺不被长期描述覆盖 |
| 只改截止、同时改要求、字段清空 | 精确原值/新值或明确变更提示；没有猜测原因 |
| 多事项及超过预算 | 至少保留可辨识事项及动作；有可见总数/剩余数；详情可查看全量 |
| 中文、emoji、Markdown、超长链接 | 编码后满足预算、无乱码或格式注入，完整入口不截断 |
| 无要求/无日期/只有日期 | 明确缺失或省略非必要字段，不编造内容和小时期限 |
| 多负责人/协作者/不同角色 | 每人仅见自己可访问的字段及计数，历史原值也不过界 |
| 已确认、负责人变更、撤权、静默窗口积压 | 当前资格不成立的提醒不发送，不展示已失效动作 |
