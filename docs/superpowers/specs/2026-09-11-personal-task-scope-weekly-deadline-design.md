# 个人任务权限、月度目标与周五提报设计

日期：2026-09-11。适用项目：lab-planning。状态：用户已批准，已实施；验证记录见 docs/validation.md。

## 已确认的需求

- 非管理员只能查看自己的个人任务；共同参与目标不授予彼此个人任务的读取权限。
- 月度目标是团队大项，指定负责人、关联项目与参与人员；成员的个人任务只需关联月度目标，无须重复指定项目人员。
- 每周五北京时间 16:00 前更新本周完成情况，并提交下周计划；系统记录缺交与补交事实。
- 日计划仅讨论过，尚未获明确实施授权。本次不增加日计划、每日考核或外部消息通知。

## 现状与调整范围

当前 MonthlyPlan 已保存月份、项目、负责人、协作者、预期成果、验收要求及发布状态。Task 关联 MonthlyPlan，WeeklyRecord 保存任务每周的承诺与进展。复用这三层，前台明确称为月度目标、个人任务、周计划与进展；个人任务可跨周，不另建一套重复的个人月度提报表。

Domain.bootstrap 当前按共同参与月计划扩大 tasks 和 weeklyRecords 的读取范围，并可能补入他人的历史任务快照。该行为需收紧。现有计划历史、发布快照、导出及导入候选项也需采用一致的范围规则。

现有 scheduler 只按当天生成报告，不能直接承担缺交认定。增加独立的周提报服务和持久化记录，复用定时器的运行入口，保持报告调度行为不变。

## 月度目标和个人任务

管理员定义、调整和发布月度目标，保留目标成果、验收要求和截止日期；人员部分使用一个负责人及若干参与者。参与者由管理员在目标上明确指定，现有项目没有人员名册，本次不另建项目成员管理。

成员只能选择本人负责或参与的有效目标建立任务。任务所有者由服务端固定为本人；关联项目和目标月份由目标带出，成员填写个人工作、交付说明和截止日期。管理员可为成员分配任务。沿用已有周与月份相交校验、跨月承接、目标发布及临时工作例外。

成员不再承担新建团队目标、选择协作者及目标审核发布的流程；旧成员提报草稿保留，由管理员处理。旧目标、任务、周记录与报告编号不变，不按人员复制目标、不删除历史数据。目标负责人汇总整体成果，管理员验收；个人任务完成不自动等于目标验收通过。

## 读取及操作权限

- 管理员读取、管理全部目标、任务、周记录和提报状态。
- 成员读取本人负责或参与的目标，以及本人所有的任务和周记录。目标负责人同样不能读取别人的个人任务与周记录。
- 目标退出参与后的历史：成员只能读取本人曾有权访问的目标历史快照及本人任务所需的目标引用，不返回退出后更新的目标全文。计划历史接口与发布快照按快照权限过滤；不得因为曾参与而返回整个当前目标或全部变更事件。
- 共享目标可显示整体成果；旧合并目标中包含他人个人提报的来源明细必须剔除或改为通用目标摘要，源事件不能借历史接口泄漏。仅在成员读取时生成安全摘要，保留管理员原文和审计；无法可靠区分的旧正文不向成员直接返回，不用字符串猜测来拆分个人内容。
- 后端执行全部归属检查，前台筛选不作为权限边界。列表、详情或关联读取、搜索数据源、导出、导入候选、历史与报告快照使用同一范围；不得通过猜测 ID 越权。
- 成员不能代填、改变提报人或修改系统时间；管理员代录须保存实际操作者和代录原因。

## 周五 16:00 的明确口径

使用 Asia/Shanghai 和服务端时间。W 表示当前周一至周日，截止点为 W 的周五 16:00:00；本周总结对应 W，下周计划对应 W+7 天。严格早于截止点为按时，截止点及以后为补交。界面显示具体日期与时间。

每人每个 W 有两个独立的应交项：本周完成情况、下周计划。两项均已提交才显示本周期填报完成，一项缺失就明确显示缺哪项。与任务完成率分开统计。

只允许对已开始且不早于规则生效周的截止周期 W 整份提交，历史周期允许补交。未来截止周期可以提前保存任务草稿，但不能提前正式确认，更不能提交空说明获得未来周期的按时事实。

### 本周完成情况

成员更新本周所有正式周记录截至提交时的实际进展，再点击“提交本周完成情况”。每条记录需填写状态与实际进展；阻塞或本周未完成须说明原因，进行中可照实提交，不强制周五把工作全部标为完成。周末可以继续更新进展，保存修订，首次有效提交时间不被覆盖。

本周没有正式周记录时允许提交“本周无工作记录”说明，由管理员查看，不伪造任务。已有正式记录不能用无工作说明跳过。草稿不算正式周记录，但提交时提示尚存草稿并要求明确处理为纳入提交或保留草稿。

### 下周计划

成员维护下周各任务的承诺和交付安排，点击“提交下周计划”，原有逐条提交状态不能代替整份确认。整份提交需包含下周所有未撤销的正式记录，并明确处理已有草稿；纳入的草稿须满足正式提交校验，包括目标已发布及跨月关联有效。事务中同时保存正式周记录与整份提交快照，任何一条校验失败则全部不提交。

下周确无安排时可填写说明提交空计划；已有正式记录不能用空计划说明跳过。未发布目标导致不能正式提交时保持草稿，管理员先发布目标或按实际情况豁免，不能绕过目标发布校验。

整份提交后仍可新增任务或修改内容，保存修订并显示“提交后有更新”。重新提交增加版本，不覆盖首次提交的内容和时间，也不取消按时提交事实。不能删除首次有效提交来消除历史；作废或管理员纠错只能追加带原因的记录。

## 持久化、缺交与补交

新增周提报周期配置，固定默认周五 16:00、上海时区。首次启用从下一个完整周开始；明确保存生效周，不追溯旧周期，不依据旧导入数据推断按时提交。

按用户、周期周、应交类型建立唯一应交记录，保存截止时间、应交名单依据、首次提交时间、提交修订快照和记录版本。两个类型分别以 W 和 W+7 作为内容周；唯一键始终以截止周期 W 归档。

每周周一零点冻结当时启用、注册审核已通过的 member 角色账号为应交名单；审核通过沿用 canUseAccount / registrationApproved 语义，包括未带 registrationStatus 的旧账号及管理员创建账号，不能仅匹配 approved 字符串。manager 默认不纳入员工缺交统计，但可保存本人周内容。周期中加入者从下一周开始计入；停用不删除已形成的应交事实。请假、调岗、停用等例外由管理员对明确的人、周期和应交项豁免，填写原因。豁免及撤销均留痕，截止后豁免保留原缺交认定，可从当前应交统计中排除。

服务停机跨过周一时，通过当时的账号快照和账号变更事件重建名单；若历史不足以可靠判断，不推断缺交，将该周期列为“名单待核对”，由管理员确认后再认定。正常运行提前固化周期及名单，避免只在周五临时扫描当前账号。

状态由真实事实推导：截止前待提交、按时提交、逾期未提交、逾期补交、豁免。缺交认定记录与提交记录分开保存；补交只改变当前状态，不删除“截止时未提交”事实。即使补交早于定时器扫描，也根据首次有效提交时间补记缺交。

定时器启动及每次巡检补检查启用后所有已到期、尚未核对的周期；同一人、周期、应交项使用持久唯一键和事务避免重复。获取提报看板与提交时也核对相关到期状态，不依赖浏览器在线或定时器刚好在 16:00 执行。不补记启用前的缺交。

## 页面、接口与数据边界

周页面增加“本周完成情况 / 下周计划”两个区域，保留已有任务进展维护入口；显示目标周、截止时间、草稿数、提交时间与逾期状态。提供两个独立提交按钮，均先校验内容及版本。

管理员增加按周期查看的提报名单，逐人展示两项状态、应交和缺交人数、补交时间、豁免原因，可筛选缺交项。普通成员只返回本人提报记录。缺交人数按人去重，同时展示缺交项数，避免把一个人缺两项当成两人。

后端集中提供应交周期读取、本人整份提交、管理员代录及豁免操作；基于 DomainBase/Store 实现独立服务，由 HTTP 层与 scheduler 调用。服务端确定身份、周期截止及提交时间；客户端仅传目标周期、内容版本和必要说明。提交带幂等标识，重复请求不新增修订；乐观锁冲突提示刷新，不覆盖别人修改。

新提交快照和缺交记录需纳入管理员业务迁移包及备份；成员导出仅含本人范围。升级迁移格式并兼容读取旧包，旧包未含提报事实时不合成缺交。正式报告原有冻结快照不回写，新增提报状态只用于新生成报告的独立管理记录，不修改成果统计口径。

## 验证标准

1. 两名成员参与同一目标，分别只能取得自己的任务、周记录和提报状态；管理员能取得全部。覆盖 API、导出、导入候选、历史及合并来源。
2. 成员创建任务只能关联有效参与目标，无法伪造所有者；无需重复指定项目人员。
3. 上海时间周五 15:59:59 提交为按时；16:00:00 为补交；服务器操作系统时区不改变判断。
4. 仅完成其中一项或只存草稿，不能显示整周期已提交；本周仍进行中可提交真实进展。
5. 截止后补交保留缺交事实与补交时间；修改进展及新增下周任务不改首次提交时间。
6. 重复请求、并发提交、反复启动巡检只生成一次对应事实；版本冲突不部分提交。
7. 服务器停机跨截止、跨周后恢复能补检查；启用前历史不被追罚，历史不足以重建名单时不误判缺交。
8. 周中入职、请假豁免、账号停用及截止后管理员纠错有明确名单与审计结果。
9. 年末跨年、跨月周按正确 W/W+7 归档；未发布目标不能借整份提交绕过约束。
10. 旧计划、任务、导入资料和固定报告仍可读取；迁移包往返保持提报事实和时间。
