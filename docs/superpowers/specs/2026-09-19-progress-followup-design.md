# P1：进度、催办、业务回告与摘要设计

2026-09-19，待用户审阅。依赖 [P0](2026-09-19-dingtalk-foundation-design.md)，是[总体方案](2026-09-19-dingtalk-collaboration-v2-design.md)的业务闭环实施包。本文件中的规则为建议值，尚未生效。

## 1. 业务边界与角色

平台的 Task、WeeklyRecord、MonthlyPlan、WeeklySubmission 和 Report 继续是业务事实源，不新建第二套任务/审核表。新增进展事件、催办请求、通知路由及跟踪策略。

角色沿用 manager/member。成员只能更新本人工作、回应本人催办；管理者能下达、催办、配置规则并按现有权限审核。协作者可见月目标，不自动获得他人个人任务的编辑权。指定通知接收人不等于授予管理或验收权限。

管理通知路由按“事项明确配置 → 仍有效的原下发管理者 → 管理员配置的默认管理者”确定；一个事项可指定一个主接收人及最多两个管理者抄送。默认管理者为空时展示待配置，不静默群发全部管理者。项目级默认只允许管理员显式配置，不能直接取 Project.ownerId；P1A 可先只支持事项和部门默认，项目级继承属于后续同包可选配置。

平台每次处理与发送前均核验接收人的有效账号和现有访问权限；排除操作者本人的普通回告。自己发起的操作在页面和站内保留结果。若没有其他管理者可通知，管理待办仍可见，按原角色权限办理，不伪造一位审批人。

## 2. 督办范围与事实定义

### 2.1 纳入范围

开启 P1 后新正式下达的任务/周安排自动建立 TaskTracking。既有、导入和历史来源不完整的工作，由管理者预览后显式纳入；手动对单项发起催进度时，也应在页面明确显示将纳入该项。每项记录 enrolledAt、activeFrom、规则版本和管理通知路由。

单独任务默认 activeFrom 为正式下达时间；只通过未来周安排创建的任务，从该周周一开始计“久未更新”。已纳入的任务新增周记录不重置起点。草稿、未发布月目标下任务、已合并目标、停用负责人、归档项目不自动催办；缺截止日只参加进展/阻塞检查，不参与到期计算。

TaskTracking 的状态为 active/paused/closed，不冒充 Task.status。暂停必须有原因和复查日期；到期提示管理者恢复或继续暂停，不静默恢复群发。关闭督办不代表任务完成；Task.done 则关闭当前催办要求，重新打开任务后需恢复或新一代跟踪事实。P1 不新增业务层“取消任务”枚举；任务删除、上级对象失效等按当前业务动作解除跟踪，并保留审计。

没有本人进展时，久未更新的观察起点取 max(enrolledAt, activeFrom)。暂停后显式恢复建立新的 reminderBaselineAt，久未更新重新观察；既有进展时间、真正截止日、催办迟回应事实不改写，逾期仍按原截止计算。恢复预览提示当前风险数量，不能补发暂停期间所有时段。

### 2.2 有效进展

新增追加式 ProgressEvent。人工更新任务状态，或有效周记录的 actualOutcome/evidenceUrl/blocker/nextAction/status 实质变化，以及明确提交的新进展说明，生成事件。同一次页面提交修改多个字段，只生成一个进展事件和关联业务审计。

lastMeaningfulOwnerProgressAt 只接受本人操作的实质进展；要求编辑、管理者代录、空保存、仅格式变化、重复同一内容、查看消息、确认接收、通知同步和正式提报重试均不刷新该时间。管理者代录另记 lastRecordedProgressAt 和代理原因，界面不得标为本人回应。

“暂无变化”可以作为诚实的催办回应，但须填写原因和下一步；标为 no_change，不重置有意义进展计时。系统按字段差异和明确类型判断，不用 AI 推测内容真实性。

### 2.3 多层状态

- Task.done 是整项任务自报完成；必须附完成说明，可引用已填写的成果记录。不自动验收月目标。
- WeeklyRecord.done 是本周该项工作自报完成；不自动把长期 Task 标 done。页面另有明确的“同时完成整个任务”操作，默认不选。
- WeeklyRecord.submitted 只代表该行正式生效，不创建 WeeklySubmission。
- MonthlyPlan.acceptanceStatus=accepted 只由现有管理者成果验收服务产生；not_completed 文案为未完成/需处理，不冒充不存在的正式退回状态。
- 新进展会使已正式周提报的内容需要重新核对，但不抹去原准时/迟交事实。

新增完成说明要求在统一 Domain 命令中实现，所有人工入口一致；旧历史导入不追溯要求补字段，也不因读取历史而生成事件。

## 3. 手动催更新进度

管理者在任务或周安排详情点击“催更新进度”，填写更新要求、回应期限和管理接收人。周记录入口归并到 parent Task，保存可选 recordId 作为上下文；同一负责人同一任务最多一个 open 催办。

默认回应期限为下一工作日 17:00，管理员可调整为明确的未来时间。催办正文展示任务、要求、期限和发起人；按钮为“更新进度并回应”。批量操作先按负责人分组预览，提交后每人合并一张提醒。

FollowupRequest 状态：open → responded；或 open → cancelled/superseded。是否逾期由 dueAt 和 respondedAt 计算，超期后仍能回应并保留迟回应事实，不自动变成失败或任务完成。

同一任务已有 open 请求时展示它，管理者可以追加说明或调整期限并留痕，不能另建重复请求。再次外部提醒受同任务/成员每工作日一次、每位成员每日最多三次手动催进度卡片限制；多个管理者共用额度。达到额度后保留站内请求，并在预览说明下次外发安排。

回应必须显式携带 requestId、请求版本、任务/周记录版本和进展内容；正常保存页面可以让本人明确勾选“同时回应此催办”。事务内保存进展和 response 关联，重复提交返回同一结果。仅看卡片、确认收到或任意其他保存都不自动关闭请求。

管理者代录不记本人 responded；可用“管理者核实关闭”并填原因，状态 cancelled，界面保留执行者和代理事实。原事项完成、对象失效、负责人变化或跟踪关闭时结束旧请求，通知保留历史但不再要求处理。正文已变、请求已关闭时不接受旧卡片直接写入。

## 4. 自动规则与时间

时区固定 Asia/Shanghai；业务时间落库 UTC。当前 dueDate 只有日期，默认截止为该日 23:59:59.999；P1 不偷偷添加小时级截止。通知规则日历默认周一至周五，支持管理员逐日设置假期/调休并记录版本。未配置中国法定假日时明确显示“按周一至周五”。

“完整工作日”指起点日期之后、当天之前，被日历认定为工作日的日期数量；在 09:00 定时评估。例：周一 15:00 更新，周二/三/四三天无更新，周五 09:00 达到久未更新阈值。只有 activeFrom 之后才开始计时。

总外发窗口沿用 08:00–20:00。新增风险自动提醒只在工作日规则时点发出；业务动作回告可在任何自然日的总窗口内发送。日历和免打扰只控制通知，不改变实际截止日期或原周提报事实。

| 规则 | 触发与接收人 | 默认频率 | 停止/升级 |
| --- | --- | --- | --- |
| 临期 | 未完成 Task，截止前一个工作日 17:00 → 本人 | 每截止版本一次；纳入晚于该时点不补临期，交给当日/逾期检查 | 完成、改期、暂停、失效则取消 |
| 当日到期 | 截止当天为工作日，09:00 → 本人 | 每截止版本一次 | 已完成不发；周末截止不自动延期 |
| 逾期 | 当前日期晚于 dueDate，且仍未完成 → 本人 | 工作日 09:00 检查，同任务每两个工作日最多一次、每周最多三次 | 第三个逾期工作日首次进入主管风险摘要；随后每两工作日最多汇总一次 |
| 久未更新 | active Task 满三个完整工作日无本人实质进展 → 本人 | 09:00，每任务每周最多两次 | 新实质进展、暂停、完成、失效取消；仅 no_change 回应不消除该事实 |
| 催办超时 | open 请求过回应期限 → 本人 | 超时后前两个可发送工作日 09:00 各最多一次 | 持续未回应进入主管摘要，不无限逐条催本人 |
| 首次阻塞 | 首次 entered blocked，需原因、影响、需要支持 → 管理通知负责人 | 业务事件产生，5 分钟合并编辑 | 已解除时改为最新状态，不发送过期“仍阻塞” |
| 阻塞升级 | 同一有效阻塞阶段满两个完整工作日 → 主管 | 次日 09:00 首次升级；以后每两个工作日最多进一次摘要 | 解除/终止/有期限暂缓后停止或推迟 |

任务阻塞以 Task.status 及其 episode 为准。周记录的 blocked 也产生独立 episode 和回告，界面明确“本周工作阻塞”，不自动改 Task；周记录所属周结束仍未解除时，停止对成员重复升级并生成一次“上周阻塞待核对”管理事项。管理者需核对承接、关闭或明确上升为任务阻塞，不能自动认定已解决。一个任务多个相关风险在卡片中合并，保留来源层级。

新截止版本重新计算未来提醒，但在同一工作日反复改日期不突破任务/成员频率上限。停机恢复仅处理当前仍适用时段，不补所有历史提醒。所有候选在实际发送前重新校验。

规则采用固定类型模板及有边界的参数，不开放任意脚本/表达式。配置更改产生新规则版本，旧候选发送前作废并重新计算当前资格；不能通过反复保存规则绕过每日额度。

## 5. 关键变化、审核与验收通知

| 事件 | 接收人 | 业务动作与去重 |
| --- | --- | --- |
| 完成、重新打开、受阻、解除阻塞 | 管理通知负责人 | 按状态阶段和 mutationId，5 分钟内合并成最新变化；普通成果文字修改入摘要 |
| 已下达任务截止日期改变 | 负责人及管理接收人，排除操作者 | 保留旧/新日期及原因；与现有 work_changed 合并为同一事件，不重复发两种卡 |
| 普通/临时月目标提交审核 | 明确管理接收人 | 以提交版本产生一份审核通知；临时目标原有分支迁移到统一路由，避免并发双发 |
| 目标批准、退回 | 负责人 | 审核决定版本；批准文案明确尚待发布；退回包含原因和入口 |
| 月成果提交 | 管理接收人 | acceptanceStatus 首次进入 submitted 或提交一个明确新成果版本；内容编辑不假装重新提交 |
| 月成果验收结果 | 负责人 | accepted/not_completed 的决定版本；取消旧待验收提醒 |
| 正式周提报成功 | 本人站内回执，管理者摘要 | 以 WeeklySubmission.id/requestId，重试不多发；管理者代交时另通知本人并注明原因 |
| 报告定稿 | 选定且仍有报告权限的管理者 | reportId+revision；草稿生成不通知，成员不因收到链接获得报告访问权 |

本人操作成功默认不再额外发一条“你刚刚提交成功”的钉钉卡，页面与站内回执足够；可选偏好允许开启。正式周提报仍使用原 09:00/15:00/16:05 规则；新日历不静默重写已冻结的周五 16:00 截止。若将来调整节假日提报，另加经管理者确认的周期截止覆盖和审计。

### 延期申请（P1B 的独立开关，默认关闭）

现有成员可改自己任务日期；基础版本保持该权限，合法改期回告管理者。若团队启用“下达任务改期需批准”，所有人工写入口对已纳入且原生 assigned 的 Task 都改为：成员提出 requestedDueDate+原因 → 有权管理者批准/退回。直接 PATCH dueDate、卡片和机器人不能绕过。

每任务最多一个 open 申请；申请期间保留原截止和逾期事实。批准时校验申请对应的 dueDateVersion；主管已另行改期则提示冲突，不能覆盖新日期。批准原子更新日期、关闭申请、生成要求变更事件，取消旧提醒。成员自建任务不默认套此审批；MonthlyPlan 跨月仍走现有承接流程，不用延期绕过所属月份校验。

## 6. 汇总、合并与免打扰

- 09:00 个人风险摘要合并逾期、催办超时、久未更新；17:00 临期摘要补充明日事项。每天最多两张自动风险卡，同一任务当天最多一个风险条目；已在早卡通知的任务新增风险留站内并进下一有效摘要。
- 条目顺序：阻塞升级、逾期、催办超时、当日到期、临期、久未更新；同事项保留多个标签，不因选主原因抹去其他义务。
- 主管的关键更新先按接收人 5 分钟汇总，每人每日最多三张关键变化卡；更多事件进入 17:30 摘要。审批/验收待处理可另有一张待处理合并卡，不受普通进度限额而完全丢失；仍受总时段约束。
- 17:30 日摘要默认给主管，含新进展、完成、阻塞、逾期、待回应、待审核；成员“我的明日行动”默认可选关闭。无新变化且无待处理不发空摘要。
- 周五 17:30 周摘要吸收当日日摘要，保留既有 16:05 正式提报统计但以链接引用，避免重复整段名单。统计标明周期、截止时点和生成时刻，节假日不自动创造新的正式提报规则。
- 手动催更新独立额度为每成员每日三张，跨管理者共享。重试同一投递不占新卡额度；unknown 保留已占额度，不能通过未知结果补发绕开。
- 摘要超过卡片字节限制时只呈现前若干项和总数，全部详情在权限校验后的摘要页面；不截断操作链接。摘要条目冻结为当次最小可见快照，打开时再次脱敏/撤权。

优先级不是短信或夜间加急授权。所有必需通知类型在成员界面明确标识；可选摘要允许关闭。关闭外发不影响业务保存、站内消息、催办请求或正式提报。

### 最小摘要的分期及交接

P1B 即交付用于风险升级、催办超时及超额度关键变化的最小主管摘要，使用 notificationDigests/digestItems，17:30 发出；不能等到 P1C 才提供这些事件的外发去处。该摘要只列当前待处理/风险和尚未回告的关键变化，暂不计算完整日报统计。

P1C 在同一 daily_manager 摘要类型和去重键上扩充统计，并增加 weekly_manager 周摘要，不重新消费已包含的来源事件。接收人+统计日+类型唯一，来源 eventId/occurrenceId 只能归属一个实际外发摘要；周摘要引用已发日摘要中的事实时是新统计周期汇总，不冒充新业务提醒。升级 P1C 当天已发的日摘要不再重发。

17:30 后产生的溢出事件保留待汇总，到下一可发送工作日 09:00 合入主管风险摘要；发送前检查当前状态，保留“期间发生、现已解除”等必要事实而不制造过期行动要求。停机错过的历史日摘要不逐日补发，恢复后仅合并尚未回告且仍有意义的事件。修改新规则时点或总发送窗口时必须预览交集，无可用发送时点时阻止该组合生效并提示调整，不能让新增摘要永久 pending。

## 7. 页面与操作

| 页面 | 新内容 |
| --- | --- |
| 我的工作 | 今日到期、待回应催办、阻塞、待正式提报；每项标明真正要做的动作 |
| 任务/周记录详情 | 进展时间线、更新进度、明确回应催办、需要支持、跟踪状态；任务完成与本周完成分开 |
| 管理工作台 | 按负责人/规则筛选风险，批量催进度预览，查看回应、迟回应、代理关闭与阻塞处理 |
| 月目标/成果 | 待审核/待验收通知入口、结果说明，沿用现有审批与验收组件 |
| 通知设置 | 类型开关、范围、管理路由、发送窗口、工作日历、阈值、额度及预计生效时间 |
| 消息/摘要详情 | 直接进入目标操作；已失效、已处理、已更改时解释原因，不显示失效按钮 |

成员进展表单包含状态、已完成内容、证据、阻塞/需支持、下一步；填写“暂无变化”时要求原因与下一步。首次只展示当前动作必要字段。同步状态、接口名、ID 和重试次数不混入日常表单，放管理诊断页。

## 8. 数据与模块

| 实体（建议名） | 关键内容 |
| --- | --- |
| taskTracking | taskId、generation、state、enrolledAt、activeFrom、暂停原因/复查日、managerRecipientIds、ruleVersion、dueDateVersion、lastMeaningfulOwnerProgressAt |
| progressEvents | mutationId、taskId、可选 weeklyRecordId、actorId、source、before/after 实质差异、noteType、代理原因、occurredAt；追加式 |
| followupRequests / followupResponses | 请求人、负责人、任务、上下文周记录、要求、dueAt、状态、请求版本；回应绑定进展事件、响应人、时间、迟回应事实 |
| blockerEpisodes | sourceType/sourceId、parentTaskId、openedAt、resolvedAt、reason/support、延期复查、阶段 ID；不与 task.done 混淆 |
| deadlineChangeRequests | 可选申请、旧截止版本、新日期、原因、审核人、决定、幂等请求标识 |
| businessNotificationEvents | 同一业务事务产生的 eventId、kind、target、actor/source、实质版本、occurredAt；不扫描旧审计制造新事件 |
| reminderRules / reminderOccurrences | 配置版本、生效时间、事件资格；每事项/规则/接收人/阶段/时段的持久去重和取消原因 |
| workCalendars / notificationRoutes | 工作日例外与版本、默认/事项路由及变更审计 |
| notificationDigests / digestItems | 接收人、范围、统计周期、项目化条目、来源事件映射、发送/查看关联 |

不要求上述每项必须独立 SQL 表；先沿用 entities 存储，但接口边界和引用必须明确。通知投递从“id=notificationId”扩为按 notificationId+channel+operation 唯一；旧工作通知 ID 保留，新能力不重写旧记录或把成功渠道重发。

模块按职责拆分：progress-service 记录进展；followup-service 管请求回应；rule-evaluator 只计算资格；notification-projector 生成接收人可见内容；digest-service 汇总；channel-worker 执行网络投递。都依赖现有 Store/权限服务，不直接互相修改私有数据。

各集合新增后同步检查业务导出/恢复、成员删除引用、业务审计和整库备份。进展与催办业务记录进入新版本业务迁移格式；旧格式读取时缺失部分初始化为空。身份、投递、回调、外部 ID、密钥和发送去重不进入可移植业务包。导入迁移包统一标记 restore/import、关闭新外发并重新建立纳入范围，不能克隆原投递队列继续发送。

## 9. 命令接口与幂等

以下为平台新接口设计，非钉钉官方接口；实施可沿既有 API 风格命名，语义不能改变。

| 接口 | 权限与结果 |
| --- | --- |
| POST /api/tasks/:id/progress | 本人/有权管理者；version、requestId、进展、可选周记录版本；返回业务版本与进展事件 |
| POST /api/tasks/:id/followups | 管理者；明确要求和 dueAt，已有 open 时返回既有请求/冲突 |
| PUT /api/followups/:id | 管理者；请求版本、补充要求/调整期限及原因，留痕，不额外创建重复请求 |
| POST /api/followups/:id/respond | 本人；请求版本+业务版本+进展，同事务完成回应 |
| POST /api/followups/:id/close | 管理者；关闭原因，不能冒充本人回应 |
| PUT /api/tasks/:id/tracking | 管理者；显式纳入/暂停/关闭、原因和配置版本 |
| POST /api/tasks/:id/deadline-requests | 开启审批时本人提出；不直接改 dueDate |
| POST /api/deadline-requests/:id/decide | 管理者；旧截止版本+批准/退回+意见 |
| GET /api/work-risks 与 /api/digests/:id | 服务端按身份和范围投影；不接收可信的客户端 ownerId 代替授权 |
| PUT /api/reminder-rules、/api/notification-routes、/api/work-calendar | 管理者；版本控制、预览受影响范围、生效时间和审计 |

所有写操作 requestId 作用域为 actor+command；规范化 payloadHash 检查同键不同内容返回 409，重复相同请求返回原结果。版本冲突不得静默覆盖。业务、事件、请求回应和幂等回执同事务提交；网络发送在事务外。旧人工更新 API 也必须经过相同 Domain 钩子，不能只保护新页面。

规则生成键为 task/generation+rule/version+recipient+businessEpisode/截止版本+slot；发送前核验当前 generation、账号、身份绑定、权限、规则版本、事项状态和义务是否仍存在。同事务重复和重复 tick 只产生一条。摘要按接收人、周期、类型唯一；事件与摘要映射持久化，避免进程重启再次汇总。

## 10. 迁移、验证与实施包

P1A：管理路由、跟踪资格、进展事实、催办请求/回应、必要页面、兼容导出/恢复和删除引用。只开手动催办，不启用新自动规则。

P1B：规则引擎、工作日历、风险合并、关键事件回告、目标/成果通知，以及风险/溢出事件所需的最小主管摘要和持久去重；延期审批独立默认关闭。先 dry-run 只统计预计接收人/数量，不落真实外发意图；确认范围后仅对启用后事件发信。

P1C：在 P1B 摘要基础上扩展完整主管日报、周摘要、成员可选行动清单，加入报告定稿通知、运行指标和容量验收。复用原摘要键和事件消费映射，不在升级时重发当日摘要。原有周提报继续运行，新增部分不得重复发已有通知。

必测场景：

1. 周一到周五、周末截止、调休/假期、月/年边界、夏令时无关的固定上海时区；完整工作日起算一致。
2. 同任务重复催办、多个管理者共同额度、批量按人合并、超时后回应、暂无变化、代理关闭。
3. 空保存、要求编辑、通知状态、管理员代录不伪造本人新进展。
4. 本周完成不等于整项完成，任务完成不等于成果验收，单行生效不等于正式提报。
5. 任务完成/重开、改期、目标合并、周记录撤回、暂停、停用、解绑时及时取消旧候选。
6. 普通和临时目标只发统一审核事件；成果新版本、重新提交、同 requestId 重试只保留正确通知。
7. 20 点后排队、次日资格已变、节假日、超额度、队列重试、unknown 不重发。
8. 旧数据纳入预览不发信，开启不追历史；恢复包、整库克隆、关闭后重开均不重放。
9. 日摘要、周摘要和正式周提报统计分别计算；未绑定或渠道失败不被当成成员未回应的证据。
10. 全部接口、旧 API、卡片和聊天入口的同一权限/版本校验；真实客户端定位及无权限降级。

发布条件：与 P0 基线兼容，旧测试及新增业务用例通过；小范围核对至少一个完整周提报周期和模拟时间日历用例。关闭新增规则可立即停止新自动外发，已受理仍查回执；平台业务数据和已记录回应保留。
