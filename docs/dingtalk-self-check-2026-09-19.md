**日常协作模式**

业务数据、任务规则、进度与正式提交事实由平台保存；钉钉负责工作台入口、身份验证和工作通知。当前是企业内部 H5 应用及个人工作通知卡片。

1. 管理者在平台正式发布目标、下达任务/周安排，或修改已下达要求。
2. 平台按事件和参与人生成站内消息，为符合条件的成员创建钉钉投递。
3. 成员从钉钉工作台或通知进入系统，查看安排并明确确认接收。
4. 成员在系统页面填写进展、成果、证据、阻塞和下一步。这些操作可以在钉钉内完成，写回同一平台。
5. 周五核对并正式提交本周完成情况和下周计划。只保存进度、点击确认接收，都不等于正式周提报。
6. 管理者在平台查看最新进度和提报汇总；当前每次成员更新不会自动发钉钉回告。

平台受理、平台报告成功、系统已查看、本人已确认、任务已完成、正式周提报分别记录。深链接首次展示详情目前只做 GET，未必记录系统查看；点击列表或“查看事项”才记查看，所以“尚未查看”不等于没有打开过钉钉卡片。

绑定后，在没有有效系统会话且被识别为钉钉环境时会自动尝试免登。新会话免登、账号切换及不同客户端仍需分别实机验收。

**功能覆盖**

“通知已实现”均须满足外发开关、接收范围、本人绑定、有效账号、发送时段和发送前事项检查。

| 场景 | 状态 | 实际边界 |
| --- | --- | --- |
| 管理者下发个人任务 | 已实现通知 | 为别人创建原生 assigned 工作；关联月目标须已发布，或属于合法临时任务 |
| 正式下发周安排 | 已实现通知 | 周记录须生效；一次新建任务与周安排合并成一条 |
| 修改已下发任务要求 | 已实现通知 | 标题、说明、截止日、月目标关联；仅改执行状态不通知 |
| 修改已下发周安排要求 | 已实现通知 | 修改 commitment；相同内容重复发布不重置确认；变更等待 5 分钟并合并近期同事项变更 |
| 发布月目标 | 已实现通知 | 按接收人分组，通知负责人和协作者；负责人需要确认 |
| 修改已发布月目标 | 已实现通知 | 标题、预期成果、验收标准、截止日及部分参与人变化；只改优先级/分类/项目不通知 |
| 新增/移除月目标成员 | 已实现通知 | 按受影响者通知；移除者收到脱敏提示；仅新增协作者不重发给现有参与者 |
| 临时目标提审/批准/退回 | 已实现通知 | 提审给其他管理者，结果给负责人；通过后还需正式发布 |
| 普通月目标提交/审核 | 未实现逐条通知 | 与临时目标通知不同 |
| 成员填写进度/成果/阻塞 | 业务操作已实现 | 可在钉钉内系统页面保存，但不会自动通知主管 |
| 手动催确认接收 | 已实现提醒，有入口缺陷 | 同事项同成员每日一次；已确认后不能用于催进度 |
| 手动催更新进度 | 尚未实现 | 需要独立动作和业务规则 |
| 临期/逾期/久未更新/阻塞升级 | 尚未实现 | 现有周提报催交不是任务进度催办 |
| 周提报自动催交 | 已实现 | 周五 09:00、15:00，仅仍应交或修改后待重交的成员 |
| 周提报截止汇总 | 已实现 | 周五 16:05 给有效管理者：截止未交、当前欠交、补交、待重交、豁免 |
| 成果提交/验收、正式提报成功回告 | 未实现逐条通知 | 管理者需在平台查看，或等待已有提报汇总 |
| 钉钉聊天指令、聊天中直接改任务 | 尚未实现 | 未接收机器人消息，未实现交互卡片业务回调 |
| 钉钉原生待办双向同步 | 尚未实现 | 当前工作通知卡片不会自动变成原生待办 |
| 定时生成报告 | 有报告草稿能力 | 不等于自动发送钉钉报告 |
| 绑定/启用后补发历史 | 明确不补发 | 站内历史保留；后续新事件或有效提醒产生新投递 |

调度器每 30 秒核对提报提醒，工作器每 15 秒处理投递。停机恢复只处理当前周五有效时段，不补前一天/前一周或过期上午时段。已完成、豁免、停用/未审批、应交名单待核对等情况不应自动催交。

正常草稿、成员自建、代录和历史导入不应当作正式下达；本轮发现的特定草稿导入例外见下。历史数据可能在页面上显示“管理下发”，却缺少通知要求的原始来源字段，后续修改不一定触发通知，不能靠批量重发补齐。

**优先修复与验收项**

| 顺序 | 发现与证据 | 建议和验收标准 |
| --- | --- | --- |
| 1 | 手动提醒确认断点：新提醒 actionable=false，卡片指向新提醒自身，无确认按钮或原通知直达入口。本地真实 HTTP 路由复现：原安排可确认，新提醒不可确认 | 提供“查看并确认原安排”，保留独立投递记录，只确认当前有效义务，不替用户确认、不重复创建义务 |
| 2 | 草稿导入提前通知：管理者给他人 draft 导入周记录，新建临时任务或关联已发布月目标的新任务时，createTask 被视为正式下达。两例复现均生成 work_assigned/pending，周记录仍 submitted=false；四个对照不通知 | 保留导入来源并抑制草稿通知，正式下达再通知，加针对性回归。不能承诺所有 draft 导入静默 |
| 3 | 卡片容器未固定：single_url 是普通本站 HTTPS /entry，未封装 H5 AppLink，不能保证 PC 点击后始终在钉钉内打开 | 严格校验内层同源事项地址后使用官方 AppLink，保留定位，实测手机和 PC；首页不能改成循环打开自己的链接 |
| 4 | 账号切换条件风险：有效系统 Cookie 存在时直接沿用会话；若切换钉钉账号但保留 WebView Cookie，可能显示旧系统账号 | 实机核验 Cookie 行为，钉钉入口检查身份一致性，冲突明确提示。此为条件风险，未宣称已发生越权 |
| 5 | 重启投递中断风险：SIGTERM 后 10 秒强制退出，token 与发送各允许 10 秒，串行慢请求可能被打断并转 unknown | 合理延长停机预算，停新发送并等待在途；保留未知结果不重发原则，验证慢请求停机 |
| 6 | 手机深链只选中消息，不滚动/聚焦；详情排在完整列表下面 | 深链自动定位详情或移动端先显示详情，验收长列表 |
| 7 | 钉钉识别只查 UA，部分桥接环境可能被漏判并隐藏验证按钮 | 使用 SDK 能力检测并显示诊断，需实机确认具体影响 |

**建议下一阶段的进度闭环**

先修确认、草稿误发和入口，再补以下功能，平台保持唯一业务记录来源：

1. 独立“催更新进度”：管理者选择任务、说明、更新期限，成员通过钉钉通知进入填写，管理者查看催办回应。
2. 到期前、逾期、久未更新、阻塞提醒：分别定义触发/停止条件，按成员合并、设置冷却时段；完成、取消、改期、离岗任务停止提醒。
3. 进展回告：完成、阻塞、延期申请等关键事件通知主管，普通保存以汇总为主，避免每次保存都打扰。
4. 按团队作息确认发送时段：当前晚 8 点后等待是配置结果，本轮未改为全天外发。
5. 原生待办、聊天指令作为后续可选能力，另行设计权限、回调、幂等、冲突处理，避免平台和钉钉各存一套不一致状态。

**运行保障与体验优化**

- 最近投递固定返回 200 条，无分页/异常优先；旧 failed/unknown 会被挤出界面。增加状态筛选、异常数量和待处理队列。
- 同机每日备份本次成功；已有运维记录仍缺异机副本、保留策略、容量/失败告警。落实受控异机副本和恢复演练，本轮没有恢复生产数据库。
- worker 每 15 秒多次扫描全部投递历史。数据增长后按状态/时间查询并加合适索引，减少主线程负担。
- 主 JS 732.83 kB（gzip 215.46 kB），构建提示超 500 kB，两张品牌图片合计约 2.6 MB；分包与压缩可改善钉钉手机首次加载。
- 在管理界面明确显示“等待明日 08:00”“成员未绑定”等原因，减少误判。
