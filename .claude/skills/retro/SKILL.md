# 复盘

## 1. 收集事实

- `git log --format='%h %ad %s' --date=short`，标出 fix、hotfix、restore、revert 以及紧跟在 feat 之后的修补。
- 看反馈记录和使用者原话。
- 能量化的就量化：出现次数、涉及文件数、从引入到发现隔了多久。

只写能指到提交、文件或数字的事实。推测要标明是推测。

## 2. 归类，再问为什么

把问题按“如果早有 X 就不会发生”归类，而不是按模块归类。对每一类连续追问，直到落在流程或结构上，而不是落在某个人或某次疏忽上。常见的落点：

- 没有定义“完成”，所以只加不减。
- 规则只说过，没有任何东西会自动执行它。
- 验证的是功能存在，不是人能完成任务。
- 一次改得太多，出了问题无法定位。
- 同一条规则有两处定义。

## 3. 选预防手段，按这个优先级

1. **让错误写不出来**：单一定义、类型、编译期检查。
2. **自动拦住**：测试、lint 脚本、CI 步骤。数量型的存量问题用“只减不增”的基线。
3. **写成规则**：进 `CLAUDE.md`，一条一句，写要做什么，不写故事。
4. **做成 Skill**：需要多步判断的流程，放 `.claude/skills/`。

能用上一级解决的，不用下一级。每类问题只留一个预防手段。

## 4. 产出

- 一份 `docs/retrospective-YYYY-MM-DD.md`：问题分类、共同根因、每个根因对应的预防手段和它的位置。
- 对应的脚本、测试、规则改动，和复盘文档在同一个合并请求里。
- 明确写出这次没有解决、留到以后的部分。

## 5. 一个月后

回看：基线数字是否下降，同类问题是否再次出现，哪条规则没有被执行。没被执行的规则，要么升级成自动检查，要么删掉。
